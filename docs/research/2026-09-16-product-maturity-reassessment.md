# Short Drama Studio：当前成熟度复核与下一步

日期：2026-09-16。检查对象是当前工作树，包含 9 月 15 日四批功能改进及 9 月 16 日存储改进。本文是重新评估与实施建议，不表示下列新建议已完成。

实施范围更新：用户在后续推进中明确“生成视频先只用 MiniMax H3，不用 Kling”。下面关于原视频修改的行业比较仍是研究结论，当前第四项交付调整为 H3 单镜头/生成组定向重做与局部采用，不承诺原视频像素级修改。最新状态与适用验收见[成熟化实施与验收](../product-commercial-delivery.md)。

**判断：系统已经具备完整产品骨架、真实制片和编辑能力，适合熟悉系统的人持续制作；工程基础比较扎实，但还不足以称为稳定、低返工、普通用户可独立交付的成熟自主制片产品。** 最需要推进的是现有能力之间的正确衔接、实际作品质量和返工效率，以及当前版本的原生交付。

这个判断针对“单用户本地 Agent 视频制片桌面产品”。没有用专业剪辑软件的全部功能、多租户云平台规模或论文榜单作为不合适的验收门槛，也没有给没有统计依据的成熟度百分比。

## 2. 本次确认的剩余问题

### 2.1 观察的前镜边界可能不是实际采用的切点——优先修复

本地复现：前镜 Take 长 5 秒，当前剪辑只采用前 1 秒。H3 已有的 `previous_adopted_media_boundary` 正确识别 1 秒切点，但 `video.inspect_take(include_previous_boundary=true)` 仍提取前镜 **4.6 秒、4.95 秒**的帧。于是后续连续性判断可能依据已经剪掉的动作和道具状态。

原因明确：`service.py:14216` 按分镜顺序与 selected Take 找前镜，`video_inspection.py:515` 按原 Take 或 shot window 末尾取样；没有复用 `production_media_context.py:16` 已实现的当前采用位置、trim、speed 和 reverse 解析。

**最小改进：**明确区分“原素材观察”与“当前剪辑采用边界观察”，后者统一使用已有解析器。允许指定 timeline/clip 以消除多处采用歧义；不新增平行 SceneState。

**验收：**1 秒裁切、非零入点、变速、反放、调序和多处采用下，抽出的前后镜帧时间都对应当前采用位置；信息不够时返回具体未确定项。原素材观察仍能按原区间使用。

[复现代码](../../output/maturity-next-review-2026-09-16/reproduce-editorial-boundary.py) · [实际输出](../../output/maturity-next-review-2026-09-16/editorial-boundary-observed-output.json)。这次只验证取样位置，没有调用视觉模型评价其影响。

### 2.2 检查报告的来源和覆盖范围没有贯通所有使用方——优先修复

整集审阅在 `service.py:14608` 为每个 Take 只保留最后一份检查；`episode_review.py:103` 直接使用其接触表、观察和结论，没有核对当前来源，也没有把覆盖时段传给 Reviewer。新做的“只看 2–3 秒道具”报告会替代较早整段报告；分镜或引用改变后的旧报告也可能被带入。

导演建议读取音频报告时，`service.py:11957` 没有比较报告已有的 `source_editorial_revision`。此外，当前相邻镜头上下文的 `audio_observation_status` 始终是 `UNKNOWN`；不是没有音频分析工具，而是已有声音检查尚未接到这里。

**最小改进：**沿用 `inspection_source_context`、`inspection_matches_request` 和现有来源字段，为各使用方选择当前适用的报告；保留每份证据的实际范围和缺失范围。声音使用已有音频检查，不能用静帧替代听审。无关镜头变化不应全片作废。

**验收：**依次产生整段报告、局部报告，再修改相关分镜/参考或剪辑；审阅仍能区分当前适用、历史、未观察的部分，不能把局部结论推广到全片。裁切后的台词和声音检查对应当前采用区间，未分析的内容保持未确认。此项源码路径已确认，本次没有新调用 Reviewer 测量误判率。

### 2.3 Agent 的能力说明落后于真实实现

`tools/studio/__init__.py:442` 的导出工具仍告诉 Agent：text 和非 none 转场不能导出。但 `studio_visual_export.py` 及最近实际导出已经支持基本标题、黑场淡入淡出和相邻溶解。这可能使 Agent 拒绝可完成的要求，或绕到 PNG 图版；本次没有新跑 Agent 验证其选择。

另一个层次是精确编辑合同：已有 `timeline.edit_clips` 支持剪辑与字幕局部修改，尚未覆盖标题和转场。整项目保存能承载这些字段，不等于 Agent 已有合适的窄修改入口。

**最小改进：**同步工具描述、可编辑字段和实际运行能力；补必要的标题/转场局部编辑字段，保留对象 ID、当前修订与无关内容。能力随当前实现维护，不引入大框架。

**验收：**Agent 在已有片段上加中文标题、淡入与相邻溶解并以 25 fps 实际导出；预览和文件一致，原片段、声音、字幕及其他时间线保持。仍未支持的高级标题样式和调整层准确说明。

### 2.4 自动保存会屏蔽整个剪辑区域的鼠标操作

`StudioEditor.tsx:154、231、313` 在修改后 650 ms 保存，并给整个编辑器标记 busy；`studio.css:112` 随即设置 `pointer-events: none`。受影响范围包括时间线、播放和工具栏。这是代码确定的行为；本次未实测用户可感知的停顿时长，不能直接把仓库保存耗时当成 UI 卡顿数据。

**最小改进：**后台串行保存，确认所提交的快照，保留请求期间的新编辑；只限制必要的重复提交。继续使用已有合并和冲突处理。

**验收：**本地保存响应延迟 1 秒时，仍能编辑、停止播放、撤销；最终保存最后一次编辑。失败保留草稿，晚返回的旧快照不覆盖新输入。

### 2.5 后端重连保留已完成，进程退出后的草稿恢复仍不完整

`StudioWorkspace.tsx:39` 的分镜草稿只在 React state；场次草稿使用 `studio-scene-drafts.ts:45` 的 sessionStorage；局部剪辑 store 仍在内存，等待用户明确保存。当前 App 已能在后端断开后保留 Workspace，但不能由此推出窗口重建或应用意外退出后仍可恢复所有草稿。

**最小改进：**给场次、分镜和局部剪辑提供一致的临时恢复副本，保存对象和基础修订；保存或明确取消后清除。恢复草稿与正式内容分开，不能自动覆盖后台已生效内容，不增加内容版本列表。

**验收：**两集各有场次、分镜、局部裁切和字幕草稿，应用退出重开后能继续；保存/取消清理正确，后台发生修改时按现有冲突语义处理。本次未强杀应用，缺口来自持久化路径检查。

### 2.6 导出拆表解决了写入，进度仍触发全量项目读取

`studio_export.py:415` 更新独立导出记录并产生 `export.updated`；`studio-activity-refresh.ts:38` 把它归入全项目刷新，`StudioWorkspace.tsx:88` 再取完整 ProjectAggregate、集列表和审阅。独立导出状态轮询也已经存在。150 ms 合并能减少密集事件，但不是只在终态刷新。

**最小改进：**进度只更新对应导出状态，终态执行必要刷新；内容事件再取相关内容。先复用现有记录接口，不急于迁移数据库。

**验收：**既有大项目导出时，进度事件不触发整正文 GET；记录请求次数与传输量，取消、重连、完成预览和下载仍正确。进一步按测量决定是否提供当前内容投影、按需读取历史或代理预览。

### 2.7 已有 H3 恢复机制仍有一个范围限制

`h3_worker.py:262` 的未知提交候选只读首批 50 条；`minimax_h3_client.py:258` 的列表请求固定 `offset=0`。任务多时，目标可能不在候选范围。不能把“首批未找到”当作“未提交”。

**最小改进与验收：**先核实当前代理的分页合同，再增加有界分页与实际查询范围说明，以确定 ID 和现有匹配规则对账。用现有 Fake 验证第 51 条及更后候选能被找到、空页/错误正确结束，再按实际接口补必要集成检查；未找到保持未知，已执行的生成不盲目重发。源码确定，本次未请求真实供应商列表。

### 2.8 当前源码还没有成为最新、可独立使用的原生交付物

只读检查确认现存 `app.asar` 及包内后端仍为 9 月 11 日，不能代表 9 月 15–16 日能力已经交付给安装包用户。当前包只验收 macOS arm64。`App.tsx:60` 启动失败只有通用提示与重新加载；已有打开日志目录 IPC 尚未接入 Studio。

本地 Whisper/WavLM 在 `audio_inspection.py:161` 首次分析时才加载。已有机器缓存下成功不代表新环境资源已准备；相关状态没有在当前设置页展示。Torch/Transformers 被声音分析实际使用，不能为缩小包而直接全部删除。

**最小改进与验收：**当前候选包分别以空用户目录、旧案例副本运行；检查启动、创建、保存重开、迁移、带声音/标题/转场的导出和项目包迁移，以及麦克风实际授权与拒绝。缺少本地声音资源时能看懂准备/失败状态，启动失败给具体阶段和日志入口。正式外部分发再处理签名、公证与更新渠道；不把它们变成本机研发的前置审批。

### 2.9 次优先级的体验收尾

- **支持的窄窗口缺少素材入口。** 最小窗口宽 880 px，但 CSS 在 1250 px 以下隐藏编辑素材库，未见替代抽屉。验收 880/1100 px 下仍能加入已有视频和声音。
- **资产用途没有完全接成精确定位。** 后端已有 timeline、clip 和时间，前端点击主要只切到镜头/成片页。验收跨集、多处采用、非当前时间线和无镜号配乐都能定位到实际片段。
- **大项目包缺少过程可见性。** 已经包含媒体和 Trace，并在解锁后复制；剩余是收集/导入进度、取消和结果找回。先以实际大包测耗时、磁盘占用，再补最小任务状态，不预设内存必然溢出。

## 3. 成熟平台最值得借鉴什么

成熟平台的共同方向是让用户持续处理同一个作品：复用已有素材、精确控制输入、在已有视频上修改、快速预览，然后进入真实时间线。它们不都能稳定解决复杂剧情、人物接触与多镜对白，也不能由产品宣传推出可接入的 API。

因此最值得继续做的是：**理解当前作品的实际状态、准确判断故事要求是否表达、从已有素材找到可复用片段、在返工时保住成功部分。** 现有 `SceneContinuitySummary`、`ContinuityState`、带时段的 `VideoObservation`、音频检查及采用边界已经提供基础，不需要再建一份项目状态。

具体可沿现有观察记录补少量有关事实：人物位置/视线、谁拿着什么、动作结束状态、对应帧/音频区间。只有观察到的事实进入后续上下文，计划、推断和未知保持区别；只检查与本次目标或问题相关的区间，不强制每段素材跑固定 Critic 循环。

## 5. 最值得增加的产品能力：保留原视频的定向修改

现有纯剪辑修改、字幕对齐和 H3 组重做都是真实能力。但 `video.retake / extend / gap_fill` 的注册仍明确写 Mock，`service.py:15851` 固定 mock Provider。不能把这些名字算作已接通的原视频编辑能力。

建议从一次高频返工开始，只接一个真实可用操作，例如修改画面中的一个对象，或者保留场景和人物表演、修一段对白。先依据实际 API 和运行资源选择 Provider，记录原 Take、选中区间、期望变化和保留要求。生成结果作为候选回到同一镜头与时间线；失败保留原片，选区外继续使用原片。

验收同时看“问题修好了吗”和“好内容保住了吗”：目标对象/对白、人物和道具状态、动作与镜头运动、接缝、原声/字幕、未选片段及其他镜头。不同执行器的保留能力不同，不要求生成部分逐像素相同，也不把整段重新生成冒充精确修复。

在这个能力之前，先修本报告 2.1–2.3，确保 Agent 选择的源区间、检查证据和工具能力本身可信。

## 6. 建议的推进顺序与验收

| 顺序 | 交付内容 | 最小完成条件 |
| --- | --- | --- |
| 1 | 观察与工具合同对齐 | 修采用边界、报告来源/范围、声音当前性、标题转场工具说明及必要局部字段；补 H3 对账分页。先用实际本地媒体和确定性服务验证，再对必要的 Agent 使用做小范围实跑。 |
| 2 | 编辑不中断与草稿可恢复 | 延迟保存期间继续操作、最后输入正确落盘；应用退出可恢复分集草稿；导出进度不重读正文；支持窗口尺寸始终能取用素材。 |
| 3 | 当前 macOS 候选包与代表作品 | 包含最近改动；空目录首用、旧库迁移、声音资源状态和实际导出通过。随后用当前版本从新要求到实际成片验证，不沿用旧作品导出证明生成质量。 |
| 4 | 根据真实返工接入一种原视频修改 | 选定实际最常见的问题，用一个可用执行器验证修复效果与保留程度；失败保留原片、无关内容不改。 |
| 5 | 由使用数据决定扩展 | 素材语义检索与区间复用、相关连续性事实、代理预览、大项目包进度；依据瓶颈做内容投影或移出历史，不提前全面重构。 |

第 3 步的首轮作品建议保持小而完整：两部 30–60 秒、约 4–8 镜的独立作品，一部双人对白与反打，一部明确道具交接/接触动作；另在已有作品上完成两类已接通的定向剪辑、字幕或声音修改，不依赖第 4 步的新生成编辑能力。只要求剧本的独立任务也应正常收尾。任务数量是控制首轮范围的建议，不是据此宣布系统稳定的统计标准。

每个作品在开始时记下用户必须看到/听到的少量关键要求，在结束时记录：

- 实际成片、关键事件与顺序、人物/道具连续性、对白与字幕、声音和最终播放是否可用；看不清、没听审的内容保持未确认。
- 首次可用与最终采用的视频数量/秒数，重做数量与原因，目标修改以外被迫改变的内容。
- 总墙钟时间、模型/工具调用、输入用量、重试、实际提供的供应商消耗；缺失不估装成真实账单。
- 人工介入次数、原因与耗时；人工补图、改提示、改库/代码都记录，不能只计产品内点击。
- 暂停、语言短暂断开、已提交视频恢复、重开后的结果与无关人工修改保留。普通恢复路径可先用已有 Fake/local fixture 验证，不用付费反复制造故障。

两次通过只说明这两部作品达标。后续正常使用继续积累相同口径的数据，才判断成功率和波动。论文或一个优秀样例不能补齐这一证据。

历史 9 月 11 日精确字幕修改曾用 201.37 秒、9 次语言调用、5 次工具；修复后的精确只读任务为 27.51 秒、2 次语言调用、1 次读取。真实 H3 编译仍花 367.54 秒，视觉观察 245.66 秒，候选发现质量缺陷。这些不同任务只说明真实成本值得继续测量，不能计算整体加速率。更早“409 次语言调用、0 视频”的运行发生在多轮修复之前，也不能作为当前性能。保持 Astra/xhigh 配置，先消除无关上下文、重复读取和不适用检查，再用实际任务衡量效果。[原始验收说明](2026-09-11-mature-video-production/09-implementation-delivery.md)

## 7. 当前不建议扩大建设的方向

继续维护已有 SQLite/文件混合存储、ProjectDocument 与本集时间线、现有 Harness 和 Provider 适配。当前证据没有显示需要改成多份 JSON、迁移远程数据库、扩大 Agent 数量、换掉语言模型、恢复主画布或建设内容分支/版本 UI。

27 项方法的存在不代表 27 类生产任务都成熟；下一步应验证真实高频作品和返工，再决定补哪种方法或外部执行器。工程测试数量、旧完整成片和当前本地导出各自有价值，但都不能单独证明稳定的自主制片质量。

本文列出的顺序聚焦当前最直接的产品收益：准确处理已有内容，让用户连续工作，以最新作品验证结果，再有针对性地增加生成编辑能力。
