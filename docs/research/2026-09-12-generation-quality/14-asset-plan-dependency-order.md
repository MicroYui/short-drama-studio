# 资产清单顺序不应决定依赖是否合法

日期：2026-09-12。范围：资产计划结构校验、局部保存、就绪状态与依赖上下文。当前《一起签》仍为调试项目，未进入新空项目验收，未提交视频。

## 真实故障

03:27:29，素材规划师通过 `artifact.patch_asset_plan` 为许岚追加第 8 镜近景工作项 `wi-yqq-s08-xulan-seated-closeup`。它依赖已经完成的角色母图 `wi-yqq-reuse-xulan` 和会议室母图 `wi-yqq-reuse-room`。角色条目排在会议室条目前，原校验将对象清单展开为线性顺序，报错 `dependencies must precede it`。

依赖存在、已完成且无循环；错误来自展示顺序。Agent 随后读取失败参数，去掉房间工作项依赖、改用同一房间的精确 AssetVersion，03:28:04 保存成功。这是实际额外往返，不因 Agent 绕过而视为问题已经解决。

本地隔离回归以“角色派生图依赖后列道具母图”复现了相同 Tool 失败，未修改实验数据库或生成媒体。

## 一手参考和采用范围

Python 标准库 `TopologicalSorter` 用节点到前置节点的映射表示依赖，提供循环检测和就绪处理。Dask 同样以任务图表示计算关系，由调度器遵守数据依赖；声明位置不是依赖合法性的依据。[Python graphlib](https://docs.python.org/3/library/graphlib.html)、[Dask Task Graphs](https://docs.dask.org/en/stable/graphs.html)。

采用“全局 ID 的依赖图与清单展示顺序分离”这一成熟做法，直接复用标准库检测循环。没有引入 Dask 运行时、新调度器或强制阶段；也没有公开证据可据此声称 MiniMax Design、即梦或 Kling 的内部资产调度就是这种实现。

## 修复

- 保留 item / work-item 全局唯一 ID，先检查依赖、参考图、拼图来源和母版血缘指向的对象存在。
- 引用工作项作为真实媒体来源时，仍须在本工作项声明对应依赖；依赖本身不自动成为图像输入。
- 按全局图拒绝自环和跨项循环，不要求依赖在 JSON 清单中先出现。
- 不重排或重写原有清单。局部保存仍合并后整体校验，失败不写入半份更新。
- 同步移除 service 和执行合同检查中“canonical 必须更早”的位置条件；母版角色、血缘和显式依赖仍按实际对象校验。

已有索引先收集所有已完成工作项，工作上下文按全局 ID 展开依赖，实际媒体解析也按精确版本取用，因此不需要另造执行器。显式 canonical 迁移功能中有意调整清单的行为保留。
