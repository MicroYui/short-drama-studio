# 从实际调用减少无效往返

日期：2026-09-12。依据当前调试轮的真实 Trace，具体用量见 [运行记录](03-real-production-record.md)。

## 观察与原因

Writer 的 20 次语言调用包含 13 次 Tool 操作。六份已确定的文字资产逐个创建，另有五次参数 Schema 查询；刚写入资产的 brief/descriptor 未保留在后续工作集，导致再次读取历史 Tool 结果。该阶段模型请求累计约 735 秒，Tool 执行约 0.29 秒，主要等待来自语言往返。不能把累计请求时间与并行任务墙钟时间混为一谈。

图片 Worker 的八项 Tool 记录里，两次 `image.advance` 是执行器的确定性续跑，不应算成八次语言决策。当前观察工具已将真实语言事件与 Tool 事件分开。图片审核和采用各有语义判断，不能为了减少计数直接把成功图片自动批准。

文字图版又暴露了另一类合同缺陷：Schema 看似允许普通字符串数组，运行校验却拒绝用来排版的空行；自然语言 `layout_description` 不控制真实字号与位置。此类问题需要修工具的输入和实现，仅让 Agent 再试不能消除根因，详见对应文字图版修复记录。

## 针对性一手资料

[Anthropic《Writing effective tools for agents》](https://www.anthropic.com/engineering/writing-tools-for-agents) 建议从真实任务和原始调用记录反推工具设计，合并经常一起使用的操作，返回相关信息，并用可操作的错误说明输入和约束。它同时要求查看结果正确性、时间、调用量、Token 和错误，不能只优化某个计数。

[Anthropic《Introducing advanced tool use》](https://www.anthropic.com/engineering/advanced-tool-use) 说明按需发现工具可减少上下文，但发现本身也增加调用延迟；例子可以表达 Schema 难以表达的参数惯例。本文借鉴这些设计原则，不接入其私有平台能力，不将其公布的内部提升比例当成本项目效果。

## 本地采用

1. `artifact.create_assets` 一次保存已确定的相关文字资产，整体验证并保留现有内容；旧单项调用仍可用。后续工作集按对象 ID 保留当前 brief/descriptor，避免回读刚写入的事实。
2. 通用实际运行提示说明：当前一小段工作已知所需工具时，一次请求其中尚未加载的多个 Schema；不预加载整个目录，不猜尚未读取的参数。现有发现接口本来支持 ID 数组，不增加一个新的工具。
3. 文字图版使用能实际控制渲染的参数，明确文字与留白、装饰线的区别；错误需指出当前字段与可改内容，不让对象用途被迫随工具限制来回切换。
4. 视频输入准备的目录说明由“approved media”改为“current usable media”，与已经允许明确选择可用 DRAFT 图片的实现保持一致，避免无必要的批准轮次。没有放宽缺文件、失效或来源不匹配的检查。

当前回归只证明保存、读取和协议行为。Schema 合并提示是否被真实模型合理采用、资产批量保存能减少多少语言往返、补充规划增加的语言用量是否被更短等待抵消，都需由新空项目视频前端到端记录回答。不同新故事的资产数量和镜头数量可能不同，因此同时报告工作量和总耗时，不将单次时间差直接宣称为固定加速比例。
