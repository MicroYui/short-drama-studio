# Short Drama Studio：成熟实现调研与改进建议

调研日期：2026-09-11。结合调研时的源码、最近真实制作 Trace、7 个公开项目的源码，以及即梦 / Dreamina / Seedance、Kling、MiniMax Design、Flow、Runway、LTX Studio、Luma、Adobe 和 Agent 官方技术资料。本文记录实施前的诊断与建议；调研阶段没有修改产品代码、运行外来代码或调用付费生成服务。随后用户授权的代码改造与真实验收，见 [Research 改造交付与验收](09-implementation-delivery.md)，不回写成此前已经具备的能力。

## 1. 核心判断

**当前最值得做的是重写制片链中失效或低效的衔接，并加强实际媒体之间的连续性。** 统一项目内容和目标驱动的产品形态继续成立；具体 Harness、Tool、Skill 实现都需重新评价。当前已经有不少需要的功能名称，但深入检查发现：有些读取了不充分的参考，有些仍使用错误的范围或旧数据，有些提示词带着两套互斥格式，还有大量机械往返与批次等待。不能以“已有”作为保留理由。

质量和效率需要同时推进两个方向：

1. **执行效率与可靠性**：模型主要负责创作、选择和修复判断；运行时直接完成已确定的读取、保存、等待、回收与同步。现有媒体可复用时应及时复用，局部失败应就地修。
2. **作品质量与低返工**：在生成前确定适当的空间、构图和动作难度；生成后用真实画面与声音指导后续制作和局部修复。优秀提示词必须落到具体媒体、实际 Provider 能力和对应操作上。

本轮查看的公开项目没有给出一套可以原样搬来、就能同时保证高质量、快速、少返工和无人干预稳定运行的完整系统。闭源产品的可见成熟做法，主要体现为更细的创作控制、明确的参考用途、实际帧复用和局部编辑；其内部 Agent 通信与 system prompt 通常未公开。MiniMax Design 已保存 Workflow 可以研究其设计合同，仍不能等同于实际运行时源码。本报告区分产品可见行为、官方接口、设计文件、当前代码与真实运行结果。

## 2. 最近一次真实制作暴露的问题，比“提示词不够好”更具体

《午饭时间》交付了 **18 镜、57.11 秒**的竖屏成片。该过程的两个作业包含剧本、完整视频及结尾修改，期间有工程修复、换包、用户补图和明确要求的文本审阅。

| 观察 | 实际数据 | 对改进方向的含义 |
| --- | --- | --- |
| 语言调用规模 | 1,832 个唯一开始调用，1,831 条 Provider 完成记录 | 不能把大量角色活动等同于大量有效创作 |
| 工具定义请求 | **802 次原始输出只索取工具 schema，占完成记录 43.8%** | 优先处理工具发现的生命周期 |
| 更保守的重复口径 | 每次暂停、失败、重新排队或审阅交接后清空发现集合，仍有 **458 次全部请求本运行段已发现的 Tool ID** | 重复有明确定位；schema 可能随工程修复变化，不能保证这 458 次全部直接删除 |
| 已报告输入 | 92,995,579 tokens，包含缓存输入 14,130,744 | 是整次含修复过程的累计输入，不是未缓存计费量 |
| 单次上下文 | 最大实际输入 179,555 tokens；末尾后期仍有一次 96,040 tokens | 当前局部工作继续携带过多正文与旧读取结果 |
| 完整视频作业跨度 | 约 16 小时 12 分，包含修复、暂停、审阅和修改 | 不能作为净机器生产时间或当前稳定吞吐 |
| 在途请求区间 | 视频作业至少有一个语言请求在途的区间并集约 9 小时 6 分；7 个成功 H3 任务的提交至回收区间并集约 40 分 25 秒 | 有重叠且统计范围不同，不能直接相减；证据不支持“慢主要因为视频渲染” |
| 交互与故障 | 用户文本 22 条；paused 33 次、waiting_user 4 次、failed 2 次 | 多次暂停来自修复换包；4 次等待是用户明确要求的审阅，不能全部算不必要交互 |

最典型的一段：**5 次后期读取用了 13 次语言决策**，还未写入新剪辑，输入已经从约 15.7k 增至 51.2k tokens。另一个开场准备链，4 次确定性操作之前用了 8 次语言决策。此类开销增加提示词或增加 Critic 无法直接解决。

统计已按 `call_id` 去重，并检查原始模型输出；独立运行了只读复算脚本。缺少完成记录的唯一调用没有被当作用量为零。完整口径、10 项诊断、当前源码位置及真实调用链见[现场诊断](01-current-diagnosis.md)，聚合数据见[JSON](01-current-metrics.json)，复算入口见[脚本](01-measure-trace.py)。

## 3. 当前仍应改的机制，以及已经修过的部分

| 优先级 | 当前问题与依据 | 建议变化 | 改动面 |
| --- | --- | --- | --- |
| P0 | Worker 的 `loaded_schema_ids` 在每次新决策中重建，普通成功调用所用定义没有持续保留；Leader 也需覆盖 | WorkOrder 保留已发现工具 ID，每次从当前 Registry 取定义；首次加载本任务常用工具，长尾按需发现 | 较小：请求构造、WorkOrder 兼容、恢复 |
| P0 | 读取缓存用原始参数区分，默认值差异造成同一时间线多份长期正文；大结果进入之后每次机械决策 | 规范化默认参数；按对象、视图和范围替换当前结果；模型输入只携带本次必需字段与正文引用 | 中：工作集构造和读取结果组织 |
| P0 | 执行器等待同批所有 Future 才返回；H3 在途查询仍占 Worker，可能推迟后继工作 | 在途任务保存下次查询时间并释放槽位；完成结果逐个唤醒依赖任务与 Leader | 中：Runner/Executor，需小场景验证静态风险 |
| P1 | 多次“读—决定—保存—再读”只为搬运确定信息；参数、长度或 ID 错误会引发较大修复 | 将有明确边界的子操作组合；保存返回精确变更回执；确定性错误回原 Worker 局部修复 | 中：先选一条真实高频链 |
| P1 | `audio.inspect_manifest` 已读取当前剪辑，`audio.align_subtitles` 仍走旧 Manifest 并写回旧结果 | 复用已有音频对齐，将时码应用到当前选中字幕/镜头，保留其他轨道及人工改动 | 较小至中：音频与 editorial 桥接 |
| P1 | H3 连续性编译读取前镜设计中的结束状态，未直接使用已采用视频的实际结束状态 | 对确有连续关系的镜头，复用实际观察、可用帧与空间锚点；把未达成动作传给相关后继 | 中：现有观察、引用与编译衔接 |
| P1 | H3 编译最终才发现长度问题，曾出现 7,047 字符超过 7,000；还存在输入重复整理 | 稳定标签、顺序、计数由代码处理；模型只处理创作部分；超限时针对具体段落压缩 | 中：编译入口及精确错误反馈 |
| P1 | 一个待审阅变更就令整个 run 进入 waiting_user | 按用户要求合并一次语义修改的审阅；仅等待依赖这个决定的工作，无关工作继续 | 中：变更关联范围与 Runner |

已经修过的包括：H3 状态查询无需新模型决策、就绪步骤优先、外部操作不长期持有项目写锁、Worker 各自连续执行、多处无关全局版本阻挡、部分打包依赖和导出问题。**本报告没有把这些历史问题重新列为未实现能力。** 对最后版本尚未复现的执行器等待影响，仅标为源码风险，后续用 Fake 场景核实。

### 深入实现后新增的质量问题

用户提醒“已有功能也可能实现不好”后，继续核对了具体输入、执行与下游使用，发现以下问题：

| 现有功能 | 实现中的具体问题 | 保留 / 改写判断 |
| --- | --- | --- |
| 视频观察的参考图 | `_semantic_reference_images` 将明确绑定图片与兜底图片一起要求 APPROVED，明确选中且文件可用的 DRAFT 也被过滤 | 改写参考解析：遵循本次实际选择和文件可用性，不能用旧审批状态省掉关键证据 |
| 候选 Take 比较 | 观察已支持整组 `shot_windows`，比较仍以单一 ShotPlan 搭配完整候选接触表，缺少对应分镜时窗 | 改写比较输入与时间范围，保留全拒绝和相对比较语义；本轮未调用比较，属静态设计缺口 |
| 检查结果复用 | 比较器只找最新 COMPLETE 报告，未区分关注问题和观察范围；本次确有仅检查图版区域的 COMPLETE 报告 | 保存检查用途、实际媒体和区间，按当前问题判断能否复用；局部图版报告不能作为整组叙事质量依据 |
| 导演修复 | 修改 `document.shots/reference_plan`，未同步 managed Storyboard；后续组重编可能把旧分镜时窗与新 Shot revision/正文混合 | 重写为当前分镜、生成组和剪辑的局部变更操作；时长/拆镜尤其需处理。不能声称所有修复必然失败；本案例 repair_history 为 0 |
| 实际视频再制作 | `video.retake/extend/gap_fill` 是 Mock；导演 loop 只给出 REGENERATE_SHOT，不自动建立真实 H3 新候选 | 当前真实修复应编译、生成受影响 H3 组并选择采用区间；不能把它宣称为已有视频局部重绘能力 |
| Leader 分工说明 | 最终真实请求同时包含“可制作与自查、不强制独立复核”及“媒体后另交 ASSET_VERIFIER” | 首轮合并成一致规则，按真实任务复杂度决定是否分工；不能把 55 个工作项全部归因于此 |
| H3 专业 Skill | 当前 manifest 仍加载 Design 的逐字中文骨架，编译器又加载公开 Prompt IR，再声明忽略前面的固定格式 | 源资料保留归属；运行方法只摘编有效制作知识，格式和参数由单一 Provider 编译层持有。9 月 8 日真实输入已出现该结构，不能把具体失败全部归因于它 |
| 画幅能力 | 当前生成组主链明确拒绝非 9:16；上游规格可变、其他编译与传输层又有固定值 | 统一能力展示与各入口约束；未来支持横屏时贯穿修改。不能说当前主链会悄悄把横屏生成成竖屏，也不计作本次返工原因 |

这些问题应与减少机械轮次一起进入首轮改进。相关源码、实际命中与适用边界见 [MiniMax Design 深研](06-minimax-design.md)、[现有实现质量评审](07-implementation-quality-audit.md)。候选比较、导演修复、检查缓存是否值得保留，要以改写后的端到端效果决定。

## 4. 最值得借用的成熟做法

| 来源 | 可以借什么 | 如何接到现有产品 | 应保留的边界 |
| --- | --- | --- | --- |
| **即梦 / Dreamina / Seedance** | 多模态参考按用途输入；任务模式显式区分；部分参数在创建任务前校验；结果尾帧作为后续输入 | 重审当前 Tool 是否把首尾帧、身份参考、动作参考和编辑意图混为一谈；把约束及结果复用接到当前生成组 | 应用、海外产品、底层模型、火山 API 分开；模式与支持规格按版本核对，不能把一种模式参数推广到全部模式 |
| **Kling / 可灵** | 自动多镜与自定义分镜分开；每镜时长、景别、机位、叙事和运动；Element 的多图身份与声音绑定 | 让镜头设计能编译为实际可控制输入；区分 Agent 决定拍法和 Provider 自动分镜，避免两层反复重写 | 本次核得 3.0 官方资料及后续 4K 更新，不声称绝对最新；公开产品能力不等于已验证 API 或内部 Agent 架构 |
| **MiniMax Design** | 当前 Stage 的完整执行合同；最终 prompt、有序 refs、依赖与稳定工作项；局部更新；规则只放最窄层 | 可改写当前编译到执行交接，收敛重复读取与重复编译；把有效专业方法从原运行协议中摘编出来 | 学习保存 Workflow 的设计方法，不复制私有前端、画布或固定确认流程；文件写了不等于内部运行时已验证 |
| **ViMax** | 同一任务持续携带工具定义；按身份、空间、角度选择参考；输入齐全的镜头立即开始 | 优先改工具生命周期和任务调度；参考选择复用已有视觉重排 Tool | 不搬整段历史不断累积的 Agent loop；不默认生成过渡视频来取得每个新机位 |
| **Google Flow** | 明确的 Ingredients / `@` 引用、保存实际生成帧、首尾状态复用、选中片段直接编辑 | 继续完善现有引用关系，让实际采用帧能成为相关后续镜头的输入 | 参考关系只在确有需要时建立，不能把所有镜头串成必须逐个等待 |
| **Runway** | 图像确定外观构图，视频提示集中于运动；表演与角色外观分开控制；对已有视频做局部变化 | 先改善本项目输入分工与修复判断；若真实失败集中于表演或视频局部修改，再评估对应 Provider | Act-Two 的多人方案包含驱动表演与后期合成，不能宣传成自动一键多人对白 |
| **LTX Studio / Adobe** | 可复用人物场景、镜头级控制、相机运动参考、音效在时间线定位 | 沿用当前镜头与成片入口；改善声音、采用区间及局部修改工具 | LTX Studio 云功能不等于 LTX Desktop 已接入能力；不要误启用本地模型底座 |
| **Toonflow** | 动作密度、空间朝向、镜头覆盖、人物基础身份与场次状态的具体知识 | 补充现有方法中的成功/失败小例子和关键帧 brief | 其固定六阶段、多处确认、全表一次输出等不适合本产品目标 |
| **NarratoAI / MoneyPrinterTurbo** | 时间戳/ID 的明确校验与有限局部修复；真实音频时长、已有音频与素材缓存复用 | 对照已有能力补差异，特别是字幕向当前剪辑的应用 | 这些系统主要覆盖解说/素材型视频，不能拿来证明剧情连续性质量 |
| **OpenAI / Anthropic / 持久工作流资料** | 少请求、独立工作并行、结构化委派、紧凑结果、热工具常驻与按需加载、外部操作持久恢复 | 改善现有 Harness；继续使用同一 WorkOrder、ProjectDocument 和 SQLite | 不需要另建群聊系统、第二套 Agent 状态或分布式服务 |

## 5. 真正改善观感：让前后镜头使用同一组已成立的事实

### 5.1 从“上一镜计划是什么”补到“上一镜实际发生了什么”

现有片段中餐盘起态、人物站位、重复加菜等问题，提示我们需要对连续镜头更好地衔接实际结果。比如计划写“阿姨把菜放入盘中”，实际视频却没有完成这一动作，下一镜直接出现已盛好的餐盘，就会造成跳变。

建议只对相关镜头读取前镜实际可用结束区间和已有观察，决定：复用其中的帧；修正下镜起态；换一个采用区间；用反应镜头连接；或重做真正失效的动作。连续性信息保存在已有媒体观察和引用关系中，避免另建每镜必填表。

同场多机位可以采用可选的空间锚点：先确定人物左右、视线和主要物件，再从同一构图派生相关近景和反打。其他场次及无关镜头继续并行。Flow 的实际帧复用与 ViMax 的机位关系提供了可借鉴的具体机制；它们是否能改善本项目的某种失败，需要小样本实测。

### 5.2 根据失败类型选择最小修复

| 实际缺陷 | 优先检查/修复 | 何时需要重新生成 |
| --- | --- | --- |
| 人物身份、服装、持物错误 | 当前实际参考、使用目的、引用冲突 | 输入或已有候选无法支持正确画面 |
| 多人动作交叉、手物接触失真 | 动作复杂度、表演控制、覆盖镜头与剪辑可能性 | 可用区间和剪辑仍无法表达必要动作 |
| 字幕、数字、必要图版不准确 | 当前剪辑的字幕/叠加层；明确文字用可编辑内容表达 | 必须融入场景且现有跟踪/遮挡能力不足时另选生成或编辑路线 |
| 对白切断、字幕时码错位 | 实测原声、当前裁切、字幕对齐 | 原始声音本身缺失或错误，编辑无法恢复 |
| 跨镜站位、动作或道具状态跳变 | 相关前后边界、采用帧、换取用区间 | 必要状态缺失且无法通过覆盖镜头或声音衔接 |
| 节奏或情绪不成立 | 镜头长度、反应镜头、表演选择、声音和场次表达 | 当前媒体缺少承担叙事作用的内容 |

这里可以利用现有观察、候选比较、关键帧、导演修复和音频能力，但应先修正上文的范围、参考、时码与当前项目写回问题。**相同 Tool 名称不意味着其结果已可用于生产。** 新工作包括重写输入与判定、精确时间定位、可靠的局部修复以及下游使用。只有媒体、范围和相关要求仍然适用的已有观察才可复用。

### 5.3 Provider 扩展按缺陷决定

H3 继续作为当前真实主链。优先把现有参考与编译用正确，再判断剩余失败是否属于模型能力边界。如果高频问题是特定表演还原或保留原视频的局部改动，Kling、Runway、Seedance/Luma 等公开能力值得做窄范围对照；官方 H3-Context-IR 也可与当前自建编译器分别比较，不能默认串联两次扩写。如果问题是参数搬运、字幕同步或等待调度，更换视频 Provider 不会解决。

目前值得补充或对照的具体能力有三项：**H3-Context-IR 多模态提示词编译、真正保留原视频的局部生成编辑、精确时段的视听观察。** 前两项要验证与当前输入的匹配；第三项先改好已有抽帧与音频工具的时间范围，确有难以识别的运动问题再比较原生视频理解。它们是有具体用途的候选，不是越多越好的 Tool 清单。详见 [MiniMax 专项](06-minimax-design.md)与 [观察能力建议](08-context-tools-and-runtime-options.md#7-需要补充的观察能力精确时段与运动过程)。

对比应使用同一简报、相同可用素材和相当的人工参与记录。产品演示、厂商样片和单个最好候选都不能替代首次可用率、返工成本与实际交付耗时。

## 6. Agent 通信、Skill 和专业 prompt 怎样调整

**Agent 通信**继续用已有 WorkOrder、ContextManifest、AgentResult/摘要。委派包含本次目标、对象范围、必要输入、需保留内容和完成标准；返回包含结果位置、实际改动、相关影响和未解决问题。正文放在项目中，后续只读需要的部分。Leader 只在目标、依赖或重要选择变化时重新规划，机械登记与等待由执行器完成。

**Skill**已经有用途、职责、体裁、Provider 和来源的分层。当前样本中工作集明显大于 instructions，继续删 Skill 无法替代上下文修复。适合补的是可执行的专业差异与简短例子：

- 人物一致性具体看身份、服装、朝向、视线和持物状态。
- 一张输入图主要解决身份、空间、姿势还是首尾状态，逐项明确。
- 一个动作怎样拆成可拍、可生成、可剪的覆盖镜头，何时保留一个连续镜头。
- 画面、声音和剪辑证据各自能证明什么，哪里仍未知。
- 哪种缺陷先剪辑、换参考、改运动、补音频，哪种必须重新生成。

**Prompt**应直接指导当前角色的判断，不增加五个必经角色，也不写“严格自检直到完美”。已经写出 Leader、导演、视频编译、检查修复、剪辑声音五份可试验草案，并附动作例子，见[专业提示词草案](04-architecture-skills-prompts.md#6-可试验的专业提示词草案)。它们是根据研究为本项目重新撰写的文本，并非闭源系统提示词；还没有注入正式运行。

一个最值得执行的共同要求是：**明确这个镜头必须让观众看到的结果；依据已有素材和实际相邻状态制作；发现问题时指出时间位置和最小修复对象；达到本次目标后交付。** 运行时则需要真正提供这些输入和操作，才能让要求生效。

## 7. 交互应把“创作决定”和“恢复操作”分清

用户应在少数会明显改变作品的选择上参与：无法合理推断的创作偏好、明确要求的审阅、缺少不可替代的参考或输入。一次相关修改集中展示修改内容、实际影响和建议后续，避免拆成许多孤立的确认。

连接恢复、相同任务状态查询、已完成媒体回收、格式局部修正和保存后的确定同步，应自动完成或有限退避。真正无法继续时显示具体受阻对象与原因，保留已完成内容；不能只写“请点继续”。用户主动暂停或要求确认时，按其要求停止相应工作。

制作任务应呈现实际动作，例如“已保存 4 个镜头，2 组视频生成中，正在对齐当前剪辑字幕”。这些状态来自实际执行记录。无需用额外模型轮次编写频繁进度；没有新的有效结果时，不伪造持续制作的文字。

## 8. 推荐实施顺序与验证方式

### 第一组：先减少已经确认的机械负担

共同处理工具 schema 留存、读取身份归一化、局部工作集和一个高频操作链的变更回执。同时处理明确绑定参考被过滤、Leader 职责冲突与 H3 编译格式冲突，避免仅加快一条质量不正确的链。保持当前 gpt-6-astra / xhigh、Provider 和项目输入，先用现有 Trace/Fake 检查机制，再用一段真实后期任务比较实际语言轮次与输入规模。此组不需要重新生成视频。

验收关注：同一任务能直接继续使用已发现工具；新工具仍可发现；定义更新使用当前版本；读取不同镜头/页不互相挤掉；相同当前内容不以默认参数差异重复携带；保存返回的信息足以继续下一动作。提前完整生成合法请求的离线回放只能证明协议，不能代替实际模型表现。

### 第二组：保证自动推进与局部编辑闭合

改进逐项完成通知、外部等待释放槽位、依赖范围审阅，以及字幕对齐和导演修复应用到当前内容。候选比较与检查也应使用同一明确媒体范围。用一个快速任务、一个慢 Provider 等待和一个后继任务验证调度；再用已有媒体验证局部裁切、字幕、声音、叠加、导出、暂停恢复及保留人工修改。复用本轮出现过的具体失败请求；覆盖实际桌面打包路径，避免只验证开发后端。

### 第三组：针对真实失败提高首次可用率

选少量代表性序列：双人对白、手物接触、连续持物状态、明确文字与带原声剪辑。先对已有媒体做参考/边界分析，再按需要进行少量真实生成对照。每次只改一组机制，例如实际边界输入、参考选择、动作拆分或某份专业提示词，保留相同模型/Provider 和用户要求。

| 目标 | 记录口径 |
| --- | --- |
| 观感与可用性 | 人工按故事清晰、身份空间连续、动作自然、对白声音、剪辑五方面记录具体问题；区分首个生成候选可用与最终选到可用候选 |
| 返工 | 新生成次数、重新编译次数、局部编辑次数及原因；正常创作探索与技术错误分开 |
| 交互 | 用户创作输入、明确审阅、补资料、故障恢复消息分别记录 |
| 时间 | 端到端时间，语言/Provider/本地处理在途区间，人工等待与工程修复时间；注明重叠 |
| 执行成本 | 实际模型调用、纯工具发现、输入/输出及缓存字段、已报告 Provider 用量；缺失值保持未提供 |
| 稳定性 | 无工程修改完成、恢复后完成、需工程修复完成分别记录；成功导出也检查实际播放与声音 |

小样本首先报告原始结果和差异；达到足够样本量后再使用分位数或成功率概括。当前没有证据支持“能快几倍”“返工减少多少”的数字承诺，也无需另建独立 QA 平台来开始这些对照。
