# Context Engineering、Tool 质量与运行时替换选择

日期：2026-09-11。针对“已有实现不一定好”补充研究。本文比较实际合同和执行机制，结论是待验证的工程方案；没有改代码或调用 Provider。视频制作方法见其他分报告。

## 1. 评价一个能力，应沿实际因果链检查

一个注册为 `inspect`、`compare` 或 `repair` 的 Tool，可能分别只是抽几帧、让模型选一个索引、生成一段建议。其名称不能证明已经完成检查、可用性判定或修复。

逐项检查以下行为，才可以决定保留还是替换：

| 检查环节 | 应回答的问题 | 常见实现弱点 |
| --- | --- | --- |
| 输入范围 | 是当前采用镜头、源视频整段，还是旧项目状态？时间是源媒体时间还是成片时间？ | 多镜共用一份视频却按单镜评分；旧时间线检查被当成当前结果 |
| 专业信息 | 关键参考、目标动作、相关前后状态和真实声音是否可用？ | 只给文本摘要，或把所有媒体都塞进去却没有用途 |
| 观察方法 | 工具能看到/听到支持结论的证据吗？ | 两张静帧承担完整动作、对白与口型结论 |
| 返回结果 | 下一步可以直接使用什么？ | 只有评分或长篇建议，没有时间、对象、保留内容和可执行动作 |
| 后续使用 | 比较、采用、修复是否读取该结果并修改当前项目？ | 报告存在，但未进入实际选择/生成输入/剪辑 |
| 完成与恢复 | 已完成子操作是否被记住，失败是否只修必要部分？ | 工具报告启动就当完成；每次失败重新规划整场或重复提交 |

这些要求适用于新引入的外部代码，也适用于当前代码。实现取舍应以对应链的效果和成本决定，不能把“现有系统有这个类型”当作保留理由。[本项目具体质量评审](07-implementation-quality-audit.md)沿实际代码进一步核对。

## 2. 框架能替换什么，不能替代什么

| 路线 | 已确认能力 | 本项目可能替换的边界 | 必须处理的差异 |
| --- | --- | --- | --- |
| 修订当前 Harness | 当前已有 WorkOrder、结果持久化、工具注册和项目服务 | 重写模型请求构造、工具发现留存、结果摘要、连续执行/等待调度；保持内容读取兼容 | 当前设计不因已有就合格，需用真实失败链验证重写后的表现 |
| OpenAI Agents SDK | Runner、工具执行、结构化 Agent-as-tool、输入过滤、Sessions、RunState | 可试验替换 Worker 的模型/工具循环，以及结构化专业委派 | 默认 handoff 可携带先前历史；Session 默认可读取全部历史。不是装上即得到局部工作集、H3 任务恢复和当前时间线一致性 |
| LangGraph | 持久检查点、状态通道、可配置重试/超时/恢复处理 | 可用于较明确的可恢复操作子图 | Pregel 采用分步批量更新，同一步执行期间写入到下一步才可见。直接把全部 Worker 放同一 superstep，可能保留当前等待屏障 |
| Temporal | 持久编排、Activity 外部操作及恢复边界 | 长期若需要更大部署范围，可承接外部任务调度 | 单机桌面要承担额外服务、部署和适配；不会自动修正素材、镜头、字幕或业务冲突 |
| Provider 原生工具搜索 / Programmatic Tool Calling | 按需加载；在执行环境中组合调用、过滤中间数据 | 减少 JSON 协议往返和机械数据搬运；可从少量只读组合开始比较 | 当前兼容代理对这些 API 特性的支持尚未验证；不要让产品依赖一个仅在官方文档存在、实际链路未验证的功能 |

直接依据：[Agents SDK Runner](https://openai.github.io/openai-agents-python/running_agents/)、[Handoffs](https://openai.github.io/openai-agents-python/handoffs/)、[Sessions](https://openai.github.io/openai-agents-python/sessions/)、[LangGraph Runtime](https://docs.langchain.com/oss/python/langgraph/pregel)、[持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[故障处理](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)、[Temporal 参考架构](https://go.temporal.io/platform-hub/ai-engineering/ai-reference-architecture)。

SDK 的结构化输入也要正确理解：`handoff(input_type=...)` 的参数用于交接元信息及回调，并不自动替换接收 Agent 的完整输入；需要显式过滤。`agent.as_tool(parameters=..., input_builder=...)` 才提供另一种受控子任务输入方式。[SDK 官方例子源码](https://github.com/openai/openai-agents-python/blob/1705dd62509ebfb3e85e26baedbe43e9f183580f/examples/agent_patterns/agents_as_tools_structured.py)

因此，**可以替换有问题的 Harness 层，而不用同时迁移内容模型；也可以保留运行时而改写效果差的 Tool。** 先用一条高频真实任务比较两种小实现：合法工具调用率、回合数、有效输入、恢复正确性和复杂度。如果外部 Runner 明显简化代码且通过同样任务，再扩大替换范围。单靠框架品牌没有足够理由决定全面迁移或全面保留。

## 3. 上下文应围绕下一次决策构建

当前已将 Trace 和模型输入分开，但工作集仍可能累积为接近整份生产记录。修正应发生在普通请求构造时，258k 容量和接近 200k 时的整理仅作上限机制。

### 一份镜头任务输入应该包含什么

下面是概念合同，并非新增数据库表或已经支持的 JSON 字段：

```text
固定前缀：角色职责、已选择的短方法、当前 Provider 的必要规则

当前目标：原始要求、最新要求、本次完成范围
当前对象：项目/集/镜头或生成组，用户真正选中的采用位置
已成立事实：所需人物和空间信息、明确台词、人工修改、已选媒体
必要边界：与本任务确有依赖的前后状态及对应证据
本次操作输入：此次需要读取/修改的字段，精确时间与坐标含义
当前结果：最近一次相关执行结果、具体错误、尚未解决的选择
正文引用：长内容与历史观察的位置，必要时按对象/字段/范围回读
可用工具：已加载定义与长尾能力目录
```

不同操作取不同内容。例如：调整两条字幕时，不需要整份图像制作过程；选择双人对话参考时，需要实际图像、两人身份和空间关系，不需要全部导出记录；从一段多镜视频取镜头时，需要源媒体与本镜源时间，不能只有成片上的位置。

### 读取缓存与模型输入是两件事

完整结果可以持久保存，也可以在程序侧缓存。但保存过的每个读取结果，不应自动成为每次模型决策的常驻正文。

- **身份归一化**：省略参数与显式默认值表示相同读取时，应得到相同缓存身份。
- **范围保留**：不同镜头、不同页、不同字段的读取要各自保留，不回退成全局 last-N。
- **当前内容替换**：当前对象变化时，旧正文保留在 Trace，普通输入改用当前结果；用户修改不被旧观察覆盖。
- **按操作投影**：下一步只选择必要记录和字段；已完成的机械登记可以用回执代替完整过程。
- **引用充分**：简短摘要不足以作决定时提供精确回读，不让 Worker 从短摘要猜全文。

这借鉴了 Anthropic 的[按任务组织上下文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)与[执行环境内处理工具结果](https://www.anthropic.com/engineering/code-execution-with-mcp)。具体投影仍由本项目实际数据与任务决定。

### 缓存与缩小上下文存在取舍

OpenAI 当前指南建议固定提示与工具定义顺序，将动态内容放在后面，并通过追加工具维持可复用前缀；它也说明频繁重写历史或压缩会降低缓存复用。[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching#how-to-optimize-prompt-caching)

本项目不应为了命中缓存而恢复整段历史，也不应每轮重写所有稳定说明。可以固定角色/方法/已加载工具的前缀，在后缀放当前操作切片；任务切换时重新选择工作集。比较总输入、已报告缓存输入、请求延迟与结果正确性。高缓存命中但上下文庞大，不自动等于高效；很短的输入导致连续回读也可能更慢。

官方 API 的 `defer_loading`、`additional_tools`、缓存配置与 Programmatic Tool Calling 均需在当前兼容链路验证。文档存在不能代替实际请求成功。本次保持既定 Astra/xhigh；不以降低推理强度来掩盖机械流程的问题。

## 4. Tool 定义应让模型更容易选对、填对和继续做

### 本地合同里已经看到的边界

当前 [ToolDescriptor](../../../backend/short_drama/tools/contracts.py#L52) 包括描述、输入输出 schema、effect、版本等；[ToolError](../../../backend/short_drama/tools/contracts.py#L66) 只统一定义 kind 与 message。[Registry](../../../backend/short_drama/tools/registry.py#L39) 的参数校验失败返回 Pydantic 字符串，发生在 `tool.started` 之前。因此现场报告的 87 次 `tool.finished` 失败不包含所有参数校验错误，不能当成全部工具错误率。

这并不意味着所有具体工具都没有详细错误或所有字符串错误都不可用；当前也已有 ToolAttempt 和局部修复。值得改的是高频失败的输出，让模型无需再解释错误、重建候选或重新读取无关对象。

### 一个好工具不只需要类型正确

描述应明确本次作用对象、使用情形、当前/历史数据含义、时间与单位、返回值能否直接继续使用。复杂工具附少量最小/常见/失败修复例子；例子随对应工具或 Skill 加载，不堆入公共系统提示。[Anthropic 工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)、[Tool Use Examples](https://www.anthropic.com/engineering/advanced-tool-use)

以当前字幕链为例，建议改善的结果是：工具接收当前剪辑中的指定字幕或镜头，使用实际采用原声对齐，保存相关时码，并返回改了哪些字幕、当前可读引用、是否有无法匹配的台词。不要只返回一个旧 Manifest 与长报告，要求模型再搬运整份时间线。

一般成功回执可包含当前对象引用、实际变化、已完成子操作、仍缺信息；失败可包含具体对象/字段/时间范围、问题种类、当前有效输入位置、哪些操作已完成以及是否适合重试。按真实问题增加字段，不要求每个 Tool 都返回一份大表。

### 合并与拆分的依据

**适合合并**：下一步参数可以由程序确定、中间结果不需要新的创作判断、输入来自同一对象或同一次明确操作。例如准备当前生成组的绑定文件与模式约束、应用已决定的字幕对齐、批量设置已指定的图版位置。

**应保留判断间隔**：参考是否可信、候选是否可用、该动作应拆镜还是保留、需要何种表演或局部生成。否则一个巨大“生成整片”工具会隐藏实际失败位置和必要判断。

**可以直接淘汰或替换**：长期只返回泛化评分、忽略当前对象范围、复用过期报告、名称是修复却只写建议的入口。前提是端到端核查确认其行为，不能仅因名字不好听或没有在某次运行使用就删除。

## 5. 程序组合调用值得参考，但不用先建设任意代码执行平台

Anthropic 的程序调用把循环与大结果整理放在执行环境中；OpenAI 当前也公开了 JavaScript Programmatic Tool Calling，支持独立调用并行、条件和中间结果处理。[Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)、[OpenAI](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)

本项目第一步可以用普通 Python 组合已有领域服务，得到同类收益：

```text
Agent 决定：准备当前生成组，保留现有对白和选中参考
程序执行：读取该组 → 解析本次引用 → 检查实际文件与输入约束
          → 汇总确切缺项，或返回可直接编译/提交的当前输入
Agent 判断：处理创作冲突，或选择下一次真实制作动作
```

若要进一步比较 Provider 的程序调用模式，再选择一条只读汇总链试验。当前工具是进程内 Python handler，要处理 Provider 返回的嵌套调用、持续状态和 Trace 关联；并不是打开一个参数就能直接工作。官方托管执行环境也不等于本产品可以任意访问本机文件。

异步媒体等待另由持久任务处理。轮询、下载与媒体探测本来就适合普通程序，不需要让模型生成新的等待脚本。

## 6. Agent 通信应传递能改变后续行为的事实

Worker 的结果对 Leader 最重要的内容是：本次完成了什么、当前对象在哪里、实际未满足的要求、什么后续工作现在可以执行。返回“已完成、质量良好”但没有可读结果和影响范围，会让 Leader 重新调查。

工具内部再次调用模型时，也需要显式传递当前方法、阶段和相关证据；外层 Worker 的 Skill 不会自动进入内层请求。当前嵌套导演工具固定 STORYBOARD 且未带入已选方法，便属于需要改写的通信边界，详见 [07 的 Q6](07-implementation-quality-audit.md)。

相邻 Worker 应共享必要边界，而不是聊天记录。例如视频实际末尾“餐盘仍在窗口外、未完成递交”会影响下一镜；编译过程中的长推理一般不会。参考图应传具体文件、用途与时段，不只传“阿姨参考图已完成”。

并行应按真正独立的对象划分。两个 Worker 重写同一张分镜表、相同当前时间线，可能增加冲突和往返；几个不同镜头独立制作、一个 Provider 等待时另一个后期继续，才可能缩短关键路径。增加角色数和并行度不是收益本身。

完成由当前用户目标与实际交付决定。参数错误在原任务修，媒体在途由运行时等；专业选择变化才回 Leader。检查应在有新证据或需要判断的地方使用，不把“再找一个 Agent 审一下”当作每步默认动作。

## 7. 需要补充的观察能力：精确时段与运动过程

当前 [VideoInspectionRequest](../../../backend/short_drama/models.py#L3007) 支持关注说明、前镜边界与抽帧数量，但没有显式源视频起止时间。仅在 `review_focus` 中写“检查前 4 秒”不等于程序实际只读取这个时段，也不能让后续知道报告覆盖哪里。

应先扩展现有观察入口：明确源视频区间与采用位置，对疑点做较密抽帧，接入对应音频，并将实际观察范围随结果保存。只有这样，动作是否完成、对白是否被裁断和局部图版是否正确，才有各自合适的输入。仍不能凭稀疏静帧宣称完整运动自然。

如果这些手段仍无法判断高频运动问题，可将原生视频理解作为可选观察 Provider 做小范围比较。Google 的 [Gemini 视频理解文档](https://ai.google.dev/gemini-api/docs/video-understanding)提供视频输入、时间戳定位与动态查看时间线的能力；这是候选工具能力，不是建议替换当前语言 Agent 配置。接口支持视频不代表自动具有专业导演判断，也不代表检查没有遗漏。比较同一缺陷的定位准确度、遗漏、额外时间和成本，确有收益再接入；不默认给每次生成增加一次全片模型检查。

## 8. 如何判断重写确实更好

选择已有实际失败链，保留相同输入、模型、Provider 和交付要求，分开比较：

1. 调用协议：从发现到一次有效操作，需要多少语言轮；schema 和复杂参数能否正确构造。
2. 上下文：本次必要信息是否齐全；输入减少后是否增加回读、遗漏与错误动作。
3. 领域结果：观察是否对应正确媒体/时窗；修复是否真的更新当前项目并改善对应缺陷。
4. 恢复与并行：部分成功是否保留、在途结果是否回收、无关工作是否被阻挡。
5. 作品：实际可用区间、跨镜连续、声音/字幕与最终播放是否满足目标。

离线回放和 Fake 能检查协议与恢复，不能证明创意质量或真实模型选择。后者需少量代表片段的真实对照；不预先给出无法证实的百分比。若一个改写减少轮次却降低观感，应继续调整职责与输入，而不是只追逐 token 指标。
