# 目标、方法与成功标准

## 1. 产品目标

用户可以什么都不提供、只提供若干图片、输入一句创意或一段剧本，系统生成适合抖音观看的完整短剧，同时允许用户在需要时修改，而不是把每一步都变成任务管理界面。

首版面向单个创作者或受信工作站，不建设账号系统：无注册、登录、用户/组织、角色权限、租户隔离、团队协作和分享权限。这里的“确认”只表示某个内容版本能否进入下一生产阶段，不表示谁有权操作。Provider API Key 属于外部模型调用配置，不属于产品用户身份。

首版目标建议限定为：

- 单集 30–90 秒；
- 9:16 竖屏；
- 1–3 名主要角色；
- 1–3 个场景；
- 6–15 个镜头；
- 支持真人感和漫剧两种美术方向，但每次实验只比较一种；
- 输出可播放 MP4、可编辑时间线清单、字幕文件和完整生成记录。

默认 `AUTO_DRAFT` 的首版成功标准包含无人值守生成完整草稿：规划、资产缺口处理、分镜、候选选择、QA、导演修复、时间线和导出都不要求用户中途操作。`GUIDED` 才显示可选停靠点与可忽略建议；只有把草稿标记为正式通过仍需要人工动作。

### 质量优先的资源原则

- 不为凑技术栈强制使用 GPT Image 2、H3、Azure 或任一特定模型；
- 不把 Provider 数量、模型新旧或“全 AI 自动化程度”当作质量指标；
- 只要某项能力提高成片质量，或质量持平但提高一致性、可控性、稳定性或可返工性，就允许进入默认链路；
- GPT Image 2 等图像控制不需要等 Direct 路线失败后才启用；可从第一轮就与 Direct 同样本比较；
- 若图像、外部音频或修复步骤实测造成风格转换损失、表演受限、同步变差或新瑕疵，才从对应镜头移除；
- 路线可按项目、场景或镜头选择，不强迫整片由同一模型完成；
- 闭源平台只提供可学习的产品与制片方法，不进入生产依赖。

## 2. 四种输入契约

### `AUTO_ORIGINAL`

不要求文本或图片。Story Planner 内部生成并排序可执行创意，选择一个后继续完成剧本与制片规划。系统必须保留最终采用的创意、剧本和规划来源，不能把本地回退伪装成 GPT 结果。

### `IMAGE_SEEDED`

至少输入一张图片，文本说明可选。图片作为人物、场景、道具、构图或风格线索进入规划和参考绑定；系统不能把不可见事实当作图片已经证明的内容，也不能因为用户缺少三视图而阻止继续生成。

### `IDEA_EXPANSION`

输入是一句话或简单梗概。GPT-5.6-sol 可以扩展人物、冲突、节拍、对白与结尾，但必须保存：

- `source_idea`：用户原始输入；
- `story_outline`：故事大纲；
- `script_draft`：可编辑剧本；
- `approved_script`：用户或自动规则确认后的执行版本。

### `SCRIPT_LOCKED`

输入是已有剧本。默认不改台词与语义，分别保存：

- `original_text`：原始剧本；
- `spoken_text`：实际要求说出的文本；
- `subtitle_text`：字幕文本；
- `adaptation_notes`：仅记录因镜头长度、画面可生成性或审查要求提出的建议。

任何语义重写都要生成显式 diff 并取得确认。允许自动做标点规范、说话人识别、镜头拆分和舞台说明结构化，但不得把这些变化偷偷写回原文。

## 3. 调研方法

### 资料调研

- 模型能力只采用官方 API 文档、官方模型仓库或官方产品指南；
- 闭源平台只把公开页面能证明的功能记为事实，内部机制标为 `INFERRED`；
- 开源项目以固定 commit 做源码审查，README 宣称与代码实现分开记录；
- 价格、配额和模型版本按时间快照处理，不用旧价格做预算承诺。

### 源码审查维度

1. 剧本与分镜数据模型；
2. 角色、场景、道具、服装和声线资产；
3. 连续性约束是否真正传入下游；
4. Provider 能力矩阵与异步任务状态；
5. 候选生成、选择、复核和定向重试；
6. 音频、口型、字幕和最终合成；
7. 竖屏输出与抖音安全区；
8. 可恢复性、成本记录和 Mock 工程路径；
9. 许可证和二次开发边界。

### 实验方法

- 日常制片采用持续改进：如果新 Prompt、参考绑定、镜头拆法、检查顺序或重试策略明显改善质量、减少生成次数，且没有发现对应退化，可以直接更新默认实现并继续推进；记录简短原因、适用条件和实际结果即可，不要求为每次改进先建立完整实验协议；
- 只有当两条路线孰优未知、需要形成跨项目默认策略、可能明显增加成本或会改变 Provider/架构边界时，才做同输入的受控比较。受控比较中保持主要输入和验收标准一致，并尽量一次只改变一个主要因素；
- 保存实际生产所需的请求、模型版本、生成模式、输入资产版本、任务 ID、耗时和结果，以便复现问题和回归，不为方法完整而额外制造材料；
- 可以先在当前真实镜头上修正，再把有通用价值的失败加入回归案例。明确有效的修复不必等待大样本才使用；稳定率或跨题材结论仍需足够样本支持；
- 不以最好的一次“抽卡”宣称稳定能力，但允许它作为可用 Take 进入当前成片；同时持续观察平均生成次数和选择成本；
- 调研与架构讨论结束前不提交真实生成；进入已确认的制片阶段后，不再为每次调用设置逐笔或逐批预算审批。

需要比较时，首先比较自建生产路线，而不是只比较单个模型参数：直接原生视听、关键帧辅助、音频驱动和混合修复均可成为候选。复杂路线不因步骤多而扣分；只要最终质量更好，或质量不劣且控制更稳定，就可以采用。已经从生产证据中得到清楚结论的改进可以直接沉淀，不为形式上的“实验完备”延迟制片。

## 4. 质量模型

### 剧本与叙事

| 指标 | 说明 | 首轮目标 |
| --- | --- | --- |
| 完整性 | 有开场钩子、冲突升级、结果或悬念 | 人工 4/5 以上 |
| 信息密度 | 每个镜头带来新信息、动作或反应 | 无明显冗余镜头 |
| 台词执行 | `SCRIPT_LOCKED` 不增删改核心文字 | 自动对比 + 人工逐句确认 |
| 节奏 | 前 3 秒建立人物/异常/冲突之一 | 盲评多数通过 |

### 视觉与镜头

| 指标 | 严重失败定义 |
| --- | --- |
| 角色一致性 | 脸、发型、年龄、服装或体型发生身份级漂移 |
| 场景一致性 | 同一空间的门窗、家具、光向或时间无叙事理由改变 |
| 道具连续性 | 道具消失、换手、颜色变化或状态跳变 |
| 动作接续 | 切镜前后位置、朝向、动作阶段或视线无法衔接 |
| 摄影可读性 | 运镜与主体动作冲突，镜头不稳定，构图遮挡关键信息 |
| 生成瑕疵 | 手脸异常、穿模、文字乱码、物体融化或时间闪烁 |

单镜候选应先通过“无严重失败”门槛，再比较美感。只靠一个加权总分容易让严重口型错误被画面美感抵消，因此严重失败采用硬门槛。

### 声音、口型与字幕

| 指标 | 验收方式 |
| --- | --- |
| 台词正确率 | STT 转写与 `spoken_text` 做 CER，再人工核对专名、数字和否定词 |
| 说话人正确 | 多人场景逐句确认角色归属 |
| 声线连续 | 同角色跨镜盲听是否被判断为同一人 |
| 口型同步 | 正脸、侧脸、快语速分别做 1–5 分人工评分；必要时补自动同步分 |
| 音频质量 | 无爆音、明显噪声、突兀断句和不可解释的环境音跳变 |
| 字幕 | 文本正确、时间覆盖对白、两行内、无越过抖音 UI 安全区 |

Azure STT 的 CER 只作为筛查，不单独决定是否通过。专名或情绪化表达可能被识别错，但人耳和原始音频仍然正确。

### 成片技术质量

- 统一 9:16；
- 恒定帧率，具体 24/25/30 fps 根据入选视频引擎的原始输出与发布要求确定，避免无意义转帧；
- 音频统一采样率与声道后再混合；
- 无黑帧、坏帧、静音断层和重复尾帧；
- 镜头顺序、设计时长、对白和字幕由同一 `TimelineManifest` 驱动；
- MP4 可在常用浏览器、macOS 和移动端播放器正常解码。

## 5. 生产效率指标

除成片质量外，还应记录：

- 端到端耗时；
- 每个合格镜头平均生成次数；
- 人工确认时间；
- 被重用的角色/场景资产比例；
- 因上游修改而失效的下游工件数量；
- 每秒合格成片成本和调用量，用于运营观测而不是首要选型；
- 为达到质量线启用了哪些环节，以及它们分别贡献了什么质量或控制增益。

## 6. 首轮成功定义

在一份 45–60 秒固定剧本上，连续完成三次生成，至少两次满足：

1. 剧情完整且镜头顺序正确；
2. `SCRIPT_LOCKED` 的核心台词无语义错误；
3. 主要角色没有身份级漂移；
4. 道具和动作连续性没有阻断观看的错误；
5. 对白可懂、说话人正确、正脸口型没有明显错位；
6. 字幕文本和时间可用；
7. 成片可直接播放，且所有失败镜头可以单独重做而无需整片重跑。

这是一条实验通过线，不是对外商业发布标准。
