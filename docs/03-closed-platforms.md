# 闭源平台拆解

本章只回答“公开产品形态能学到什么”，不推断厂商私有模型或训练方法。没有登录用户账号做实操，所有效果描述均为 `PRODUCT-CLAIM`，不是本轮独立评测结论。

**使用边界**：即梦、可灵、LTX Studio 和纳逗 Pro 不属于最终系统的候选执行器。方案不调用其产品、不依赖账号、不要求导入其项目文件，也不把“以后接入平台”作为架构前提；只提炼公开可观察的产品机制，再用我们自己的数据模型、Provider 和媒体工具实现。

## 1. 对比总表

## 2. 即梦

`DOC-CONFIRMED`：即梦官方主页公开了文/图生视频、运镜与速度控制、首尾帧、图像主体特征/姿势/画风保持，以及支持多图层和多元素融合的智能画布。[即梦官方主页](https://www.jimeng.com/)

### 可学习之处

- 让创作者从“画布上的素材”出发，而不是面对一串 Provider 参数；
- 首尾帧是可理解的镜头控制，不必暴露底层模型术语；
- 图像局部编辑、扩图和多元素融合紧邻生成结果，方便定妆与修复；
- 中文提示词和社区同款降低首次创作门槛。

### 不应过度推断

公开主页无法证明它已经提供完整的剧本拆分、跨镜角色圣经、多人对白、口型、字幕和最终时间线。因此本项目不应仅凭“智能画布”宣传就复制一个画布作为核心架构。

## 3. 可灵

`DOC-CONFIRMED`：可灵 VIDEO 3.0 官方用户指南描述了：

- Multi-Shot 由模型自动规划多个镜头；
- Custom Multi-Shot 可指定镜头内容、数量和时长；
- 能理解正反打、多角度覆盖、交叉剪辑、画外音等叙事表达；
- Elements 可从多图或视频构建人物/物品/场景参考；
- 人物元素可关联原声、自定义音色或音频；
- 原生音视频与最长约 15 秒生成；
- 官方宣称多语、方言、表情和口型具有自然对应关系。

来源：[Kling VIDEO 3.0 Guide](https://app.klingai.com/cn/quickstart/klingai-video-3-model-user-guide)。其网页可能因 robots 限制无法稳定抓取，最终验收仍需登录实操。

### 可学习之处

1. **Elements 是稳定生产资料**：角色不应只存在于某个 prompt 中；
2. **自动多镜与自定义多镜并存**：新手可以让模型规划，专业用户可以锁定每镜时长和内容；
3. **声线属于角色资产**：当原生视听模型参与时，角色资产应同时包含视觉和声音约束；
4. **多镜是一个生成模式，不等于完整短剧工作流**：15 秒多镜可以减少剪辑断裂，但 45–90 秒仍需项目层统一管理。

### 对自建工作流的启发

自建工作流也采用两级结构：项目层规划 6–15 个编辑镜头，再根据 H3 的能力决定哪些相邻镜头合并生成。在其 4–15 秒窗口内验证这种方法；项目时间线仍不依赖模型内切镜一定成功。

## 4. LTX Studio

`DOC-CONFIRMED`：LTX Studio 将工作流组织为 Gen Space、Canvas、Storyboard 和 Video Editor；Elements 用于跨场景复用角色、物体和地点，镜头支持相机、关键帧和视觉参考。[LTX Studio](https://website.ltx.studio/) [TV/Media Workflow](https://ltx.io/studio/solution/tv-media-networks)

其官方 2026 Audio-to-Video 资料还描述：

- 音频优先：先导入对白/配乐，再生成与其节奏匹配的画面；
- 视觉优先：先做 Storyboard，再在同一时间线加入对白、音乐和音效；
- 基于音素分析做口型；
- 多说话人可以分别分配角色、声音和口型；
- 对白、音乐、音效和视频在同一时间线调整和导出。

来源：[Audio-to-Video](https://ltx.io/blog/audio-to-video-syncing-sound-with-ai-video-generation) 与 [Top Features 2026](https://ltx.io/blog/top-ltx-studio-features)。2025 年的 [Projects 更新](https://ltx.io/blog/introducing-projects) 曾移除旧版口型入口，2026 资料显示新 Audio-to-Video 流程已重新承担相关能力；这说明闭源产品功能位置和可用性会变化。由于本项目不使用该产品，只把当前公开机制作为启发，不把可用性当成已验证事实。

### 可学习之处

- 项目、素材、Storyboard、Timeline 是同一工作区的不同视图；
- Retake 应保留上下文，只重做当前镜头或区段；
- 音频路线不必固定：原生视听、音频优先和视觉优先可以并存；
- 时间线不仅是末端剪辑器，它反过来暴露缺镜、节奏和对白长度问题；
- 角色/地点/物体都用 Element 抽象，避免只有“角色库”而场景继续漂移。

## 5. 纳逗 Pro

`DOC-CONFIRMED`：爱奇艺将纳逗 Pro 定位为覆盖脚本、图片、声音、视频和成片的一站式专业影视平台，包含编剧、导演、美术、摄录、剪辑和宣发等智能体，并接入商用模型、奇智模型、IP 库和数字资产。[纳逗 Pro 业务页](https://www.iqiyi.com/common/aqynatoopro.html)

爱奇艺的产品资料还宣传：

- 从剧本、角色/场景、构图/景别、分镜、走位、运镜到视效和剪辑的链路；
- 素材泛搜和“大片提示词”；
- 360 度全景场景用于正反打的空间、背景和光影一致；
- 文戏、武戏、感情戏和一镜到底等专业能力；
- 支持短剧、AI 真人剧、漫剧、短视频和广告。

来源：[发布说明](https://pages.iqiyi.com/m/scpr/63x0au29.html?qyc-pr=1) 与 [新功能说明](https://pages.iqiyi.com/m/scpr/63x0avkx.html?qyc-pr=1)。

### 可学习之处

- “70 个 Agent”不是重点，重点是每个专业工种交付结构化工件；
- 场景一致性需要可旋转/多视角的空间资料，不只是几张氛围图；
- 素材库、IP 库和项目产物应有明确来源与复用关系；
- 武戏和文戏需要不同的镜头/动作规划 Skill，而不是同一个通用模板；
- 专业功能可以逐步暴露，默认体验仍应是一条清楚的制作主线。

## 6. 四个平台的共同产品规律

### 资产先于镜头

成熟平台都把角色、场景、物体或风格从单次 prompt 提升为项目级资产。这是跨镜一致性的第一前提。

### 自动规划与人工锁定并存

一句话输入需要自动补全；已有剧本和专业用户需要锁台词、镜头、参考、时长和候选。两个入口共享同一组中间工件，不应做两套运行时。

### 生成结果必须可局部返工

Retake、局部编辑、单镜重生和候选比较比“再次整片生成”更重要。工作流要保存生成依赖，知道修改角色定妆后哪些镜头失效。

### 原生多镜不能取代编辑时间线

多镜模型可以改善 4–15 秒内的动作和声音连续性，但长于单次生成窗口的短剧仍需确定性的镜头顺序、字幕、音量和导出。

## 7. “为什么效果好”如何翻译成自建机制

闭源平台的优势不是某一个神秘按钮，而是把模型放进制片约束与局部返工回路。以下是可复制的部分：

| 公开可见机制 | 可能改善质量的原因 | 自建系统中的对应工件 | 如何验证不是表面功能 |
| --- | --- | --- | --- |
| Elements / 主体库 / 资产库 | 同一角色、地点、物体不再每镜从文字重猜 | `ProjectBibleVersion` + 版本化引用 | 换景别、角度、光线后仍保持身份；修改资产只失效依赖镜头 |
| 多视角或 360 场景资料 | 正反打共享空间结构、光向和背景物 | `LocationProfile` + 空间锚点/关键视角 | 门窗、家具、轴线和反打背景能对应 |
| 自动分镜 + Custom Shot | 自动补全降低门槛，锁定时长/内容保留导演控制 | `ShotPlan` + 审批状态 | 已锁台词、时长和镜头不会被后续“优化”偷改 |
| 模型内 Multi-Shot | 同一生成窗口可共享动作、表演、声线和光照上下文 | `ExecutionPlan.batch` | 连续性增益高于整组返工代价，且切镜时间可执行 |
| 原生视听或 Audio-to-Video | 音素、表情、动作和镜头节奏在同一上下文生成 | 可选音频策略 + `TimelineManifest` | 逐字、说话人、侧脸口型和跨镜声线固定输入过线 |
| Storyboard + Timeline | 画面规划与成片时钟共享同一项目事实 | `ShotPlan` + `TimelineManifest` | 改对白/时长后能精确传播，不靠人工重新对齐全部镜头 |
| Retake / 局部编辑 / 候选 | 把随机生成变成可选择、可定向重试的过程 | `Take` + `QAReport` + 依赖图 | 单个问题可局部修复，无需整片重跑；新版本不覆盖已批准候选 |
| 编剧/导演/美术/剪辑等工种 | 每一步有专业约束和明确交付物 | 一组 schema 化 Planner/Reviewer 角色 | 每个角色输出可验证工件，而不是只增加 Agent 名称和对话轮次 |

不能复制的部分包括私有训练数据、内部模型权重、隐藏评分器和平台算力调度。自建方案不假装知道这些机制；它只复用能被公开观察、源码实现和固定实验验证的制片方法。

## 8. 后续学习验证方式

不登录和使用这些闭源产品。后续只通过官方说明、公开演示和可获得的界面资料继续核对以下机制是否真实存在，以及它们如何组织用户操作：

1. 从一句话到首版分镜需要多少人工操作；
2. 是否有可复用角色/场景/声线资产；
3. 能否锁定台词与每镜时长；
4. 双人正反打、道具换手和跨镜动作是否连续；
5. 原生对白、方言、多人声线和口型；
6. 字幕是否来自真实文本而非画面内生成；
7. 单镜返工是否保留项目上下文；
8. 导出、版本、失败恢复和返工在产品中如何表达。

这些观察用于完善自建工作流，不构成平台效果排名，也不会成为外部运行依赖。
