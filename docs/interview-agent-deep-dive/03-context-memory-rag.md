# 03 上下文、Memory 与 RAG：从可恢复工作集到 NPC 长期记忆

[返回学习地图](README.md) · 前置：[运行架构](01-multi-agent-runtime.md)、[纠错与一致性](02-correction-consistency-recovery.md)

这章分成两个部分：先解释源码中已经存在的上下文与记忆，再设计游戏中的长期记忆。面试时必须把这条分界说出来。当前项目有持久记忆、全文检索和精确回读，但没有完成“玩家经历 → embedding → 向量检索 → NPC 行为 → 记忆评测”的产品闭环。

“这些记忆怎样让 Agent 接着工作”另见 [01D](01d-progress-and-next-action.md)：它逐层解释目标、checkpoint、working_notes、进度条目、工具回执与 next_owner；本章重点讨论容量、回读、检索及游戏长期记忆设计。

## 1. 先分清五种经常被统称为 Memory 的东西

| 层次 | 回答的问题 | 当前项目中的例子 | 为什么不能互相替代 |
| --- | --- | --- | --- |
| 权威业务状态 | 现在真实保存的是什么？ | ProjectDocument、当前镜头、素材绑定、时间线 | 记忆摘要不能覆盖用户刚保存的正文 |
| 执行检查点 | 任务跑到哪一步，接下来谁执行？ | WorkOrder、SpecialistTurn、next_owner、GenerationTask | 只有对话记录无法判断远端是否已提交 |
| 当前工作集 | 下一次模型决定需要看什么？ | 目标、任务范围、working_notes、按对象保存的读取观察 | 不能把所有历史请求都重复放进去 |
| 跨任务记忆 | 以前有什么决定或经验可能适用？ | ProjectMemory、DecisionMemory、ExperienceMemory | 经验是带适用条件的线索，不是当前项目事实 |
| 完整历史与证据 | 当时究竟发了什么、返回了什么？ | Trace、持久化的大结果、context_ref | 保存完整历史不要求每次输入完整历史 |

一个具体例子：工作笔记说“第 6 镜还是红杯”，当前文档已是蓝杯。正确行为是读取当前第 6 镜并淘汰旧观察；不能因为笔记更短、在 prompt 中更靠前就把它当真。反过来，查询“为什么上一次选红杯”需要历史快照，不能拿今天的蓝杯正文冒充当时输入。

“完整 Trace”指系统实际取得的请求、可见输出、动作、回执及供应商提供的用量等记录，不表示能读取模型全部内部思维过程。工具请求里的简短 reason、working_notes、reasoning.effort 配置和 reasoning token 统计也是不同信息；不要把它们统称为保存了完整思维链。

## 2. 258k 是完整请求预算，先解释算式

源码入口：[token_budget.py](../../backend/short_drama/agent_runtime/token_budget.py)、[model_input.py](../../backend/short_drama/agent_runtime/model_input.py)。这是项目设置的运行预算，不是对所有模型官方窗口的声明。

默认参数：窗口 258,000 tokens；压缩触发线 200,000；压缩目标 160,000；请求封装预留 1,024。输出上限作为预算的一部分，推理用量不能再当成窗口外的免费空间。文本使用随包提供的 o200k 编码做发送前估算；Provider usage 仍是实际统计来源。

设文本输入估算为 T、预留输出为 O、视觉预留为 V、封装预留为 E，则必须满足：

    T + O + V + E ≤ 258000
    文本硬上限 = max(0, 258000 - O - E - V)
    文本触发线 = min(200000 - V, 文本硬上限)，下限为 0
    文本压缩目标 = min(160000 - V, 文本硬上限)，下限为 0

当前每张图预留 8,192 tokens。这是保守余量，不是图片 token 的官方计算公式；也不是把 base64 字符串当文本计数。实际视觉用量由供应商报告。

例如 O=20,000，输入两张图，则 V=16,384，文本硬上限是 **220,592**，触发线是 **183,616**，目标是 **143,616**。如果文本是 190,000，即使没有撞硬上限，也应先整理。整理后若仍超过软目标但低于硬上限，要看能否继续移出可恢复内容；不能擅自删掉受保护的原始要求来满足数字。

还有一个容易踩的坑：[context.py](../../backend/short_drama/agent_runtime/context.py) 的 `DEFAULT_CONTEXT_CHARACTER_BUDGET = 24_000` 是局部 ContextPack 的紧凑投影限制，单位是字符。它不是模型完整输入预算。真正的发送前检查覆盖 instructions、序列化 payload、已加载工具定义等完整文本。只测一个 context 字段，就可能漏掉占比很高的 working_set 和 schema。

历史报告曾记录 36 次真实调用中本地估算比 Provider input 少 10 tokens，最大输入约 109,647；这说明当时封装差异较小，不证明任何模型、图片或新代理都固定差 10。极端输入 408k 左右整理到约 9k 的结果属于特定压力 fixture，不是日常请求都能节省 98%。来源：[Harness 验收记录](../agent-harness-context-and-lifecycle.md)。

## 3. 长结果移出去以后，为什么还找得回来

这里的关键机制是**先保存原文，再用可解析引用替换**，不是让模型写一个摘要然后把唯一原文删除。

`ModelInputCompiler.prepare` 的主线是：

1. 构造真正将发送的请求文本，计算 token 数及视觉余量。
2. 识别可恢复的大字段，如任务输入、计划参数、工作集观察与集合；保留目标、控制约束和必要输出合同。
3. 把完整快照持久化，得到精确 `context_ref`。
4. 在原位置放入引用与 JSON pointer，并保留 `agent.read_context` 的回读说明。
5. 重新序列化、重新计数，达到可接受范围后才发送。
6. Provider 仍拒绝上下文时，尝试更强整理；只有输入确实减少才有限重试一次，不原样撞同一个错误。

JSON pointer 回答“快照里的哪个字段”，分页参数回答“这个长列表的哪一段”。不能只给“去读之前的分镜”这种含糊指令。读取结果的 `next_offset` 允许继续取，不要求一次把移出的全部内容又塞回来。

这里需要守住两个不同保证：

- **可恢复性**：被替换掉的原文仍然存在，可按引用精确取回。
- **决策充分性**：模型知道什么时候需要回读，而且当前摘要没有遗漏会改变决定的约束。

前者可以用保存、重启、JSON pointer、分页测试确定性验证；后者必须通过任务结果和反例评测。能恢复原文不代表模型一定会主动恢复正确那一页。

进一步的风险是“整理—回读—再次整理”的往返开销。应观察每轮回读次数、回读是否带来新证据、同一范围是否反复出现，以及整理后任务正确率。只比较 prompt 长度会奖励过度压缩。

OpenAI 的相关工程文章也区分当前上下文、压缩、跨运行记忆与权威工件。这里用于理解设计，不表示项目依赖该 SDK 的相同版本实现。[官方文章：Memory and Compaction](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)

## 4. 读取工作集为什么要按对象和范围保存

假设 Worker 连续读：第 1 场、第 2 场、第 3 场，再读第 1 场第 2 页。

如果工作集用 `tool_name` 作为唯一 key，四次都叫同一个读取工具，前面的内容会被后面的覆盖。下一轮需要第 2 场时又读一次；这不是模型没有长期记忆，而是程序把有用观察淘汰错了。

当前 [production_manager.py](../../backend/short_drama/production_manager.py) 中的 `_specialist_read_observation_key`、`_specialist_working_set` 等逻辑会区分具体对象与读取范围。同一对象同一范围的重复读取更新记录；不同场次、镜头、任务切片与 context 分页各自保留。共享项目目录不再随每个镜头副本重复装配。

同时要处理失效：

| 观察 | 如何使用 |
| --- | --- |
| 当前镜头 r12，文档仍为 r12 | 可以支持本次决定，但写入前仍检查前置条件 |
| 当前镜头 r12，用户已保存 r13 | 从当前工作视图中淘汰/标记过期，重新读取需要的对象 |
| 精确历史快照中的 r12 | 仍可用于解释历史，不能据此覆盖 r13 |
| 已完成的具体媒体、检查与采用回执 | 按真实对象 ID 交接，避免新 Worker 重做相同工作 |
| 只共享一个全片计划引用的两个工单 | 不能据此把双方所有结果都算成互相相关 |

已完成交接的相关性判断尤其重要：同一 run、真实媒体或任务身份、具体 ArtifactRef 比“都属于这个项目”更精确。排除已取消、陈旧及不适用结果，才能避免省输入时把旧失败重新当现状。相关历史见[已完成工单交接](../research/2026-09-12-generation-quality/31-completed-worker-handoff.md)。

## 5. 当前四类 Memory 到底实现了什么

定义见 [agent_runtime/models.py](../../backend/short_drama/agent_runtime/models.py)，保存与查询见 [store.py](../../backend/short_drama/agent_runtime/store.py)，装配见 [context.py](../../backend/short_drama/agent_runtime/context.py)。

| 类型 | 主要字段 | 合理用法 | 不应声称的能力 |
| --- | --- | --- | --- |
| ProjectMemory | summary、constraints、artifact_refs | 项目导航、关键约束、指向权威工件 | 完整项目的另一份事实副本 |
| RunMemory | current_focus、completed_action_ids、blockers、open_questions、next_actions、refs | 跨轮恢复任务焦点与未解决决定 | 可以替代 WorkOrder/Action 状态机 |
| DecisionMemory | statement、rationale、run_id、refs | 留下某项选择及理由 | 所有旧决定永久有效或全部自动适用 |
| ExperienceMemory | summary、applicability、evidence、confidence、tags、project/skill、refs | 带范围、证据和适用条件的经验 | 已训练出的策略或自动校准的概率模型 |

`list_experiences` 当前先取全局与本项目记录，按时间排序，再按 skill/tag 条件过滤并截取；ContextPack 默认最多取 8 条经验。这里没有 embedding 相似度排名，没有向量库，也没有复杂的多因素经验推荐模型。`confidence` 字段的存在不等于做过可信度校准。

仓库另有 `planning_script_documents_fts`，使用 SQLite FTS5/BM25，限制 run/revision，必要时有元数据检索退路。这是规划剧本文档的全文检索。音频链里出现声纹 embedding，也不能拿来证明 Agent 文本记忆已经实现向量检索。要讲清对象、用途和闭环。

目前可以说：**有持久化工作记忆和带证据的经验结构，采用范围过滤与精确工件读取；语义长期记忆需要继续建设。**

## 6. 如果迁移到 NPC，先设计记忆的语义，再选向量库

以下全部是本次扩展设计。

设定：玩家昨天把钥匙交给 NPC 阿遥；今天钥匙被守卫取走；玩家现在说“钥匙一直在你这里”。系统需要分别表达：真实世界发生了什么、阿遥看到了什么、阿遥相信什么、玩家声称什么。

建议区分：

| 数据 | 权威来源 | 示例 | 更新方式 |
| --- | --- | --- | --- |
| 世界/任务状态 | 游戏引擎与任务系统 | key_17 当前属于 guard_2 | 事务与版本前置条件 |
| 情景记忆 episodic | 有感知权限的事件 | 阿遥看见玩家交出钥匙 | 保留事件、时间、参与者及来源 |
| 语义记忆 semantic | 经归纳和验证的长期事实/规律 | 玩家通常遵守与阿遥的约定 | 可修订，保留支持与反对证据 |
| 角色信念 belief | 角色已知信息与推断 | 阿遥没看见转交，以为钥匙仍在仓库 | 与世界真相分开，可错误但有来源 |
| Persona | 编剧设定与受控角色演化 | 谨慎、守诺、对陌生人保留 | 稳定底色与临时情绪分层 |
| 关系状态 | 游戏规则与已确认互动 | 信任增加，但仍不透露禁区入口 | 关键值由规则约束，解释可自然语言化 |

情景记录至少考虑：`memory_id`、`event_id`、`actor/subject/object`、发生时间与获知时间、`source`、`visibility_scope`、事实/声称/推断类型、关联实体、有效期、替代关系、提取版本和证据引用。这是设计清单，不要求每条小对话都携带一套庞大模型。

两个时间非常重要：事件昨天发生，NPC 今天才听说。用今天的入库时间回答“昨天你知道吗”，就会穿帮。`supersedes` 也不能删掉真实历史：钥匙先在阿遥手里、后归守卫，两条是状态演化；如果原来识别错了物品，才是对旧事实的纠正。

玩家一句“我改口了”只能更正自己的陈述，不能直接改写引擎中的交易记录。若是开发者修复了错误世界事件，则按明确修正事件更新派生记忆，并阻止旧摘要继续传播。世界事实与角色信念的区分，是 NPC 一致性比普通聊天记忆更难的地方。

## 7. 一条可解释的检索与更新链

建议的读取顺序：

1. **先确定范围**：NPC 身份、玩家/存档、当前任务、可见信息、查询时点。秘密剧情先过滤，不能让相关性排序决定是否泄密。
2. **精确读当前状态**：位置、背包、任务阶段、承诺期限等结构化数据直接从权威接口读取。
3. **并行召回经历**：实体与事件 ID 精确匹配；BM25 找名字、道具编号和原话；向量检索找表达不同但含义相近的经历。
4. **合并并去重**：按事件身份消除同一经历的原文、摘要、反思多份重复，不让重复次数制造虚假权重。
5. **按有效性和证据重排**：剔除被替代的当前事实；考虑查询时间、相关性、来源和适用范围。回顾历史时允许读被替代的旧状态，并说明时点。
6. **装配有限上下文**：带精确来源的事件片段、当前状态、必要角色约束；不把全存档注入。
7. **行动前重新确认**：读到“钥匙在仓库”只能形成计划，真正取钥匙仍要检查当前所有者与任务版本。

一种可实验的融合方式是 RRF：对不同检索器的结果按 `Σ 1/(c + rank)` 累加，避免直接相加不可比的 BM25 分数和向量分数。c、召回数量、是否追加 reranker 都应在验证集调参；它是本章的候选方案，不是项目已经采用的算法。

写入侧从事件中提取候选记忆，校验实体、来源和重复，再保存。反思总结也保留证据引用与适用时间，不能因模型写得肯定就升级为世界事实。纠错时更新事实的有效性，并使依赖旧事实的摘要、检索缓存和待执行计划失效。

如果以后采用异步向量索引，数据库提交和 embedding 入库并非同事务。可用本地事务内的待索引记录/outbox、幂等消费者及索引版本检查缩小丢更新窗口。读取端仍检查权威元数据：索引中暂时残留旧向量，也不能把过期记忆当有效事实。这个机制是扩展方案，当前 SQLite 项目没有因此自动变成向量记忆系统。

## 8. 向量检索必须掌握到什么深度

Embedding 把内容映射成向量，检索器寻找邻近项；它不验证事实真伪。归一化向量的内积等于余弦相似度，因此可以统一距离计算，但前提是向量确实归一化，且查询与库使用兼容的 embedding 模型。

**先建立 exact search 基线。** 小规模 NPC 个人记忆未必需要复杂 ANN。先比较同一数据上的精确 top-k，才能计算近似检索的 recall@k；“查得很快”却不知道漏掉关键承诺的比例，不能算完成。

HNSW 使用多层邻近图：上层快速定位区域，底层扩展候选完成近邻搜索。关键参数通常包括：M 控制图连接数及内存/建图取舍；`ef_construction` 影响构图搜索；`ef` 影响查询候选扩展，通常越大召回越好但延迟更高，且应不小于所求 k。k 是输出条数，ef 是内部搜索规模，二者不能混为一谈。没有“换 HNSW 就必定精确且固定对数耗时”的保证。[HNSW 论文](https://arxiv.org/abs/1603.09320) · [hnswlib 参数说明](https://github.com/nmslib/hnswlib/blob/master/ALGO_PARAMS.md)

容量也要会算：100 万条、768 维、float32，裸向量约 `1000000 × 768 × 4 = 3.072 GB`，约 2.86 GiB；图边、元数据、原文和副本还要额外空间。小型 NPC 私有记忆、全服公共知识和开发文档不应默认放进同一个不加区分的百万级索引。

上线前至少回答：

- 中文实体、同名 NPC、物品编号、别名及跨语言对话怎样检索？
- metadata filter 是搜索前还是搜索后作用？过滤后是否还够 k 条，是否损害召回？
- 新 embedding 版本上线如何重建、双读比较和切换？不能直接混用不同向量空间。
- 删除或纠错多久对检索可见？旧缓存和索引副本如何避免继续影响角色？
- 是否保留必要的相邻事件？单独一句“我答应你”缺少对象和时间，语义相似也没有用。

RAG 的核心是把检索到的外部信息用于生成；经典论文结合参数化模型与非参数文档记忆。现代 NPC 工程还需要补上可见性、时间、任务权威状态与动作前置条件，不能把“检索 + 拼 prompt”当全部架构。[RAG 原论文](https://arxiv.org/abs/2005.11401)

## 9. 与三项代表性记忆工作逐项比较

**Generative Agents** 把观察记忆、检索、反思和计划结合到小镇模拟中。论文的检索综合 recency、importance、relevance；其中 recency 依据最近被检索的时间衰减，不能随口讲成只按事件创建时间。它提供了角色经历影响行为的具体设计，但原论文的小规模模拟不等于商业游戏的实时性、权限或长期运营已经解决。对本项目的启发是记忆要进入行为决策；缺口是 NPC 信念、感知与关系语义。[论文与系统细节](https://arxiv.org/html/2304.03442v2)

**MemGPT** 用分层存储与显式数据搬运管理有限上下文，可以类比当前“活跃工作集 + 可回读外部记录”。区别在于本项目采用固定业务事实、精确工件与可恢复字段整理，不应声称直接实现了整套 MemGPT 控制器。外部存储无限扩大，也不意味着模型可以无损理解无限历史。[论文](https://arxiv.org/abs/2310.08560)

**LongMemEval** 将长对话记忆考察拆成信息提取、跨会话推理、时间推理、知识更新和拒答，并研究索引、检索与阅读三个环节。对面试最有用的是故障定位：没存进去、没召回、召回后读错，分别需要不同修复。项目现有按对象回读偏重可恢复性，仍缺跨会话语义记忆的系统评测。[论文](https://arxiv.org/html/2410.10813v2)

## 10. 记忆评测不能只报向量 recall

以下是建议增加的实验，不是现有成绩：

| 层次 | 测什么 | 典型失败 |
| --- | --- | --- |
| 写入 | 关键事件是否完整、来源是否正确、重复是否合并 | 没保存“承诺明天归还”，后续再好的检索也无用 |
| 检索 | gold evidence recall@k、排序、过期项与越权项混入率 | 召回旧的钥匙归属或其他 NPC 的秘密 |
| 阅读 | 给定正确证据后的答案/状态判断是否正确 | 把“玩家声称”读成已确认世界事实 |
| 应用 | 对话与动作是否遵守记忆、是否引用了正确时点 | 嘴上记得承诺，动作却将钥匙送给别人 |
| 系统 | 延迟、token、更新可见延迟、重读次数、纠错后旧事实继续使用率 | 压缩少 30%，却多三轮检索和一次错误交易 |

用同一问题做三组对照：正常检索；直接给 gold evidence；不给记忆。第一组差、第二组好，主要查检索；两组都差，查阅读或任务合同；两组都不如无记忆，查噪声、错误摘要或不适用经验。gold evidence 只能用于定位和上界对照，不能混进正式无泄漏评测。

本章闭卷要求：能解释“长上下文、上下文整理、工作检查点、长期记忆、RAG”五者的关系；能在用户纠错后指出哪些当前观察失效、哪些历史引用仍应保留；能设计 NPC 记忆的写入、检索、更新与评测，而不是只报一个向量数据库名字。
