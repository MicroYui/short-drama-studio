# 面向米哈游 Agent 岗位的项目深挖手册

整理日期：2026-10-22。源码基线：`e76aaa3`。对象是当前 Short Drama Studio 仓库；目标是能够解释设计、复现关键推理、应对反例，并把已有工程经验迁移到游戏 Agent。不是把视频产品改写成已经上线的 NPC 系统。

这份材料承接[原面试指南](../project-interview-guide.md)。原指南适合快速介绍和问答，本手册沿着“发生了什么 → 为什么旧方案失败 → 修改了哪个机制 → 怎样验证 → 还不能保证什么”展开。第一次阅读建议按章节顺序，第二次按最后一章的闭卷任务查缺补漏。

## 这次面试最值得建立的论点

**项目的核心是让模型在一个不断变化、具有真实副作用的环境里持续工作。** 模型负责提出目标相关的计划和动作，运行时负责持久化、调度、工具合同、控制边界与恢复；项目内容有唯一权威存储。把这个分工说清，才能继续谈 Planning、Memory、Action、Reflection。

可以这样用两分钟开场，涉及个人贡献的部分按自己的实际职责调整：

> 项目是一个本地 AI 视频制片产品。用户只写剧本时就交付剧本，要求成片时才继续生成、剪辑和导出。我重点准备的是它背后的 Agent Harness：Leader 生成可修订的依赖计划，Worker 带独立上下文执行任务，工具请求与回执都持久化。
>
> 最难的是人和多个 Agent 并行修改同一项目，同时图片、视频又是慢操作。我们把用户意图、计划归属、内容修订和供应商任务状态分开处理。旧计划的结果可以留作记录，但不能自动并入当前计划；慢操作返回后仍要检查当前内容；提交结果未知也不能直接重发。
>
> 真实制作暴露过协调者饿死 Worker、长工单占满槽位、读取快照互相覆盖和交接丢失已完成事实等问题。修复分别落在调度、公平轮换、对象级工作集和精确完成回执，不能都归结为提示词。
>
> 五部短片最终交付，但版本不同，首片有两次工程介入，效率仍是短板。后续完整请求优化也没有达到原目标。我能够解释哪些收益是离线输入缩减、哪些是实际运行观察，以及还缺什么实验。这套经验可以迁移到玩家与 NPC 同时改变世界的场景，但 NPC 的感知权限、关系记忆和实时动作层还需要单独建设。

## 与岗位六项要求的对应关系

| 岗位方向 | 当前项目可讲的证据 | 必须补充的能力或边界 |
| --- | --- | --- |
| Agent 核心能力 | 多轮目标更新、计划、工具调用、环境反馈、持续执行 | 这里的环境是制片项目与 Provider，未实现游戏世界中的实时 NPC |
| Planning / Memory / Tool / Action / Reflection / Persona / State | PlanRevision、WorkOrder、Memory、ToolRegistry、Action、检查反馈、角色方法与对象状态 | 生产角色提示不等于 NPC 人格；反馈修复不等于训练模型或固定 Reflexion 算法 |
| 记忆与数据闭环 | 结构化记忆、精确 ArtifactRef、工作笔记、Trace、回归 fixture | 玩家关系演化、可见性过滤、语义记忆检索、纠错传播评测是扩展设计 |
| 工具与评测 | typed 输入/输出、来源检查、错误分层、Fake 集成测试、真实媒体验收 | 没有固定版本大样本的统一 Agent Eval 成绩；内容质量尚有未覆盖项 |
| 向量检索 / RAG / 长期记忆 | 现有全文检索与按对象装配可解释检索边界 | 当前 Agent 记忆没有向量索引闭环；第 03 章补齐设计与原理 |
| Code / GUI / Browser / Computer Use / Multi-Agent | 产品本身有 Multi-Agent；工程记录含浏览器和原生产品验收 | 用 Computer Use 验收产品不等于研发了通用 GUI Agent；可迁移工具协议经验 |

## 阅读时使用的证据口径

全文按下面四种状态表述，不用一个“做过”覆盖所有层次：

- **当前实现**：本轮读取源码确认；给出文件、关键符号与相应用例。
- **历史观察**：来自仓库保存的实验报告；注明日期、运行版本、样本与限制。
- **已设计/未部署**：历史尝试明确未进入产品，不能计入真实收益。
- **本次扩展**：面向游戏岗位设计的方案和练习，不是项目交付记录。

当前检出未包含报告引用的 `output/harness-context/`、`output/daily-production-2026-09-17/` 等原始运行目录。因此本手册引用仓库报告中的历史统计，不声称本轮逐条复核原始 Trace 或账单。源码可支持机制判断，历史报告可支持当时记录的结果，两者不能相互替代。r21/r26/r27/r30 是历史运行包标识，不是四个 Git 提交号，也不表示本机现在运行着相应服务。

本轮只编写与校验学习材料，没有恢复《修好了》、生成新媒体或重新进行付费实验。现有后端 `.venv` 也未随当前检出提供；历史测试通过数保留原时间与范围，不记作本轮通过。

## 先记住六个反例

1. 有四个 Worker，不代表端到端一定快四倍；依赖、交接、共享写入和返工都可能吞掉收益。
2. 有 258k 窗口，不代表长程记忆正确；旧事实进入当前决策一样会出错。
3. Tool 返回失败，不代表没有副作用；输出校验失败可能发生在 handler 已经写入之后。
4. 数据库事务提交，不代表远端请求和本地记录也形成一个原子事务。
5. 文件生成成功，不代表已采用、目标完成或内容质量合格。
6. 最终五片都完成，不代表固定版本五次独立试验的成功率为 100%。

遇到细节追问，应回到“当前真实状态、动作前置条件、持久化记录、下一执行者”四件事；不要只重复框架名。
