# 07 掌握验收：能连续解释、处理反例、定位代码并设计验证

[返回学习地图](README.md)

验收的对象是理解与表达，不是阅读完成率。读过某章、背出名词或复述“加版本号和重试”都不算通过。建议先闭卷作答，再按下面要点核对；第一次允许看代码找入口，最后一次需要自己还原调用链。

## 1. 总通过标准

| 项目 | 分值 | 满分表现 |
| --- | ---: | --- |
| 用户纠错完整调用链 | 25 | 15 分钟连续解释，覆盖异步、归属、内容保存、远端任务、事件与最终回复 |
| 多 Agent 运行与长任务恢复 | 15 | 能还原交互、上下文、方法/工具、并行、进度接续与恢复；通过第 11、12 节专项验收 |
| 上下文、Memory 与 RAG | 15 | 会算完整预算、解释精确回读，并设计知识更新检索 |
| 真实迭代与实验口径 | 15 | 三个案例讲清旧方案、根因、机制、测量与限制 |
| Eval 与数据闭环 | 10 | 能写结果评分、重复试验与同预算对照，区分失败类型 |
| 游戏系统迁移 | 10 | 世界状态、角色信念、Persona、动作前置条件与导演权限清楚 |
| 源码与研究依据 | 10 | 现场找到关键符号和测试，准确说明历史借鉴与新阅读 |
| 合计 | 100 | 至少 85，且下列关键条件全部满足 |

每项可按四级自评：0=只会名词；约一半=能讲正常流程；约八成=能处理反例并定位证据；满分=能独立设计反例测试、指出剩余保证边界。分数是这套学习材料的标准，不是用人团队的录用标准。

以下任何一条答错，先回对应章节重学，不靠其他分数抵消：

- 不把旧模型输出机械改成最新 revision 后重新覆盖用户内容。
- 不把 SUBMIT_UNKNOWN、空列表或超时自动解释成“未提交，可以重发”。
- 不把暂停说成能够撤销所有已经开始的远端副作用。
- 不把本地事务、线程锁或 checkpoint 说成全系统 exactly-once。
- 不把数据库已保存、文件已生成、正式采用、质量通过和用户目标完成混为一件事。
- 不把五片历史观察、离线回放或未部署原型写成固定版本大样本成绩。
- 不把本次 NPC/RAG 设计、论文阅读写成现有项目已实现或个人已做过的工作。
- 不把角色预加载 schema 说成工具权限白名单，不把默认 Leader 委派说成 Worker 可任意递归创建子 Agent。
- 不把已存字段自动说成模型实际可见，不把独立读批说成同一 Worker 内的并行工具调用。
- 不把项目方法偏好、Run 活动方法、工单选择和实际模型输入当成同一个状态；不把 Skill 文件更新说成已实现全员热更新。
- 不把工作笔记或进度自述当作权威业务状态，不把“已恢复转写”直接等同“已完成听审”。

## 2. 核心闭卷任务：15 分钟讲完一次用户纠错

### 给定场景

用户最初要完整短片。第 6 镜 r12 是红杯，Worker W 读取后开始准备；另有 Leader 补充计划在推理。用户说“改为蓝杯，只改这镜画面，原声保留”，并在页面保存了蓝杯成为 r13。旧语言响应随后到达；一个旧 H3 请求已经取得远端 ID。最后要求交付更新成片。

在白板上同时画四条线：聊天控制线、内容状态线、工具/Provider 线、前端与最终回答线。不能把它们合并成一个“版本号变了就取消”的箭头。

### 必须连续讲出的节点

| 顺序 | 应说明的内容 | 面试官可插入的追问 |
| --- | --- | --- |
| 1 | `send` 保存 pending message，唤醒同一未完成 job；聊天还没有自动改分镜 | 此时进程退出，消息去哪了？ |
| 2 | 页面保存独立经过 expected revision/text，当前内容成为 r13 | 只有页面改动、没有聊天会怎样？ |
| 3 | 慢模型请求不保证被取消；旧输出可先成为 REQUESTED，工具执行前检查边界 | 已经 IN_PROGRESS 的复合工具怎么办？ |
| 4 | Runner 收取旧 Future，不派新工作；旧补充计划以不应用方式收尾 | Future 线程遇到 BaseException 却没设结果会怎样？ |
| 5 | 新要求成功交接/重规划后才确认消息前缀，失败保持 pending | 处理过程中又追加消息，如何避免删掉？ |
| 6 | 新计划应用验证当前计划与意图，继承动作身份；旧归属结果不合并当前完成 | source plan 与 active plan 为什么不同？ |
| 7 | 写入仍检查镜头/来源；无关字段可三方合并，同字段冲突保留已保存值 | 算法真的知道谁是“用户”吗？ |
| 8 | 说清计划归属事务、内容保存事务、审阅接受事务各覆盖什么 | 直接 save_shot 的全部业务写入都同事务吗？ |
| 9 | 已受理 H3 沿原 ID 查询，返回文件保留；检查是否仍适用于当前输入 | 本地暂停是否取消了远端？ |
| 10 | 红杯旧候选可以保留但不能自动覆盖当前蓝杯采用；根据新目标做必要补拍/采用 | 其他镜头变了，为什么不应废掉这个未变的组？ |
| 11 | 小事件通过 SSE 通知，前端按持久游标去重并重读当前内容，保留未保存草稿 | 断线恢复后只看最后一条文本够吗？ |
| 12 | 完成条件包括当前计划、无待交接工作/用户输入等；回复实际已保存、采用、导出的事实与未完成项 | 最后 job completed 与聊天事件是否一个原子写入？ |

通过要求：不靠提示完成至少上述十二点；面对三个随机追问仍能保持各条线一致；能够主动说明尚未证明的语义质量和跨系统原子性边界。

### 最后回复不能固定背一句话

若只完成分镜修改，应说明蓝杯设计已保存、视频尚未替换；若新画面已采用但导出失败，应说明采用成功与导出失败；若声音保护只是输入保持，不能声称听感已验收；若用户中途仅要求改文案并结束，不继续生成整片。

对于本题的完整交付目标，只有新画面采用、保留声音的实际检查、重新导出都成立时，才可以说“第 6 镜画面已更新，声音和其他内容保持，更新成片已导出”。旧候选是否留存也依据真实记录描述。**语言上的成功必须对应系统中的真实结果。**

参考：[第 02 章](02-correction-consistency-recovery.md)。

## 3. 八个故障插入题：说明状态、下一步与禁止动作

### 题 A：旧模型返回时，用户消息已到，但工具还没开始

必须答出：可保存请求证据；下一 Tool 边界让出；不执行过时写入；消息完成交接后按新计划继续。不要靠杀线程来解释。若已开始操作，则切换到另一条允许收尾的路径。

**验证断言：**旧写入计数为零、新要求完整保留、同一 job/run、pending 成功处理后清空；旧请求/响应是否保存依据具体路径，不强行要求不存在历史记录。

### 题 B：写工具已改了数据库，返回值不满足输出 schema

必须答出：这是 OUTPUT_VALIDATION 失败，不能当输入校验失败（当前 phase 名为 VALIDATION）；原 handler 可能已产生效果。查看真实内容和回执，再决定补救；不能立即重发同一写入来“修复 JSON”。

**验证断言：**数据库只产生预期一次业务效果，失败阶段可区分，已知 artifacts/receipt 保留，最终答复不谎称未执行。

### 题 C：提交 H3 后断线，没收到 provider_task_id

必须答出：本地 STARTED/UNKNOWN 保留；查询已有记录/对账；有界分页保留扫描范围；空结果不足以证明未创建；不能自动重发。只有确切身份才能绑定，内容相似不等于同一任务。

**验证断言：**提交计数不增加，UNKNOWN 不伪装 FAILED，原请求指纹和回执存在，列表错误与真实空页可区分。

### 题 D：工具回执已保存，下一次语言调用连接失败

必须答出：在同一任务有限退避续跑，读取已保存结果；下一次语言决定失败不撤销此前工具成功，不重复媒体操作。区分失败 usage 未知与输入估算。

**验证断言：**同一 job/run、原工具调用次数不变、原失败 Trace 保留、后续成功继续；达到有限重试后给出可见错误，不能空转。

### 题 E：计划保存时，第三个继承工单不存在

必须答出：整个 plan/run pointer/carried orders 事务回滚，不能留下新计划却只有部分工单转移归属。远端已开始任务不因此被回滚或删除。

**验证断言：**旧计划指针和所有工单归属保持，无部分新计划；媒体身份保持。

### 题 F：三方合并出现两种编辑

输入一：base 红杯/远景，saved 蓝杯/远景，proposed 红杯/近景。答案是蓝杯/近景。

输入二：proposed 改成绿杯/近景。普通合并保留蓝杯并记录杯子冲突，近景可合并；特定严格登记路径可以拒绝冲突。两者都要提醒：不同字段仍可能存在故事语义冲突，结构合并不证明语义一致。

**加问：**对方删除了对象、自己修改了它怎么办？必须去读 `merge_current_content` 的删除分支，不能只用覆盖值规则猜。按 ID 合并和按数组下标合并有什么差别？

### 题 G：第 5 个工单就绪，但四个线程全在执行

必须答出：当前同步操作不能无条件抢占；在已保存动作边界发现 ready peer 后释放槽位；等待和公平性区别于语义依赖；没有 ready peer 时不做无益轮转。不能把历史 1.064 秒说成从用户请求到工单启动的总等待。

### 题 H：数据库终态已保存，写最终聊天事件前崩溃

必须答出：当前两步并非一个总事务，可能出现内容完成而展示消息缺失；应以持久内容判定事实。可以建议终态事件同事务或可重建交付记录，但不能说这些改进已经存在。

**为什么这一题重要：**真正理解系统的人会指出已实现保证的边界，而不是把所有问题归给“重启自动恢复”。

## 4. 上下文与记忆闭卷题

1. 给定 258k 窗口、20k 输出、两张图和 1,024 封装，算文本硬上限。答案 **220,592**；触发线 **183,616**；目标 **143,616**。解释 8,192/图只是预留而非官方实际用量。
2. `ContextPack` 的 24,000 字符与完整请求 token 检查是什么关系？必须说出局部投影与最终序列化请求的区别。
3. 工具大结果变成 `context_ref` 后进程退出，如何读回原文？解释持久快照、JSON pointer、分页与当前状态的区别。
4. 两个不同镜头都调用 `artifact.read_current`，为什么按工具名只保留最后结果会引起反复读取？画出按对象/范围保存后的结构。
5. 当前 ExperienceMemory 怎么检索？答案必须包含项目/全局、skill/tag 过滤、时间顺序和数量限制；不能答向量 top-k。
6. 当前 FTS5/BM25 用在哪里？不能把剧本文档检索、声纹 embedding 和 Agent 文本记忆混称为一个 RAG 系统。
7. “昨天承诺还钥匙，今天钥匙已转交守卫”如何记？必须同时保留事件顺序、当前权威归属、角色是否知情，旧事件不因新状态被删除。
8. 正确证据直接给模型仍答错，优先改向量索引还是阅读/任务合同？说明 gold-evidence 对照如何定位故障。
9. 语义相似度最高的是已失效且 NPC 不可见的秘密，怎么办？可见性与有效性先约束，不让 reranker 决定权限。
10. `ef` 与 k 有什么区别？给 exact search 基线，描述延迟/召回曲线、过滤与数据规模；不能保证 ANN 永远精确。

通过要求：十题至少九题正确，且第 5、7、9 题不能错。写出自己的 NPC 记忆 schema 和一条查询执行顺序，标明这是扩展方案。

## 5. 三个工程故事的口述验收

从第 04 章选三个不同层面的故事，每个控制在约三分钟，面试官再随机追问五分钟。至少一个涉及运行正确性，一个涉及性能/上下文，一个涉及真实结果或失败。

每个故事要交代：触发 → 证据 → 被排除的猜测 → 修改机制 → 验证 → 结果与限制。

建议组合：

- **调度组合**：整批屏障、Leader 饥饿 Worker、长工单占槽位。必须说明三者不是同一个 bug。
- **上下文组合**：81k 输入归因、新旧工单 schema 差异、最后未部署的目录压缩。必须区分完整输入与局部字段。
- **可靠性组合**：用户纠错、UNKNOWN 对账、局部画面替换与音频保持。必须说明无法用本地事务覆盖远端。

数字核对卡：

| 可引用数字 | 必须随口带出的限定 |
| --- | --- |
| 1.064 秒 | 观察窗口内第五位“对峙”工单在平面合成结束后的启动间隔，不是原长期等待工单的受控对照或整片提速 |
| 19.02%–20.73% | 三个新工单 schema 的完整输入离线回放；旧工单收益更小 |
| 2.702% | 历史最终回放口径，对应 218,968 → 213,052；从 219,384 链首算是 2.886% |
| 36%–41% | 同案例保存中位数，15 次暖缓存单写入采样，不是 SQLite 或 UI 全面提速 |
| 27.51 秒 / 2 次语言 / 1 次读取 | 同一选中字幕小任务的一次修复后真实观察 |
| 五片交付、77–171 分钟 | 不同版本与 brief，首片两次介入，不是固定版本成功率 |
| 26 分 06.913 秒、一次 4 秒 H3 | 局部补拍任务，不是新片从零生产；只采用其中约 2.54 秒 |
| 《修好了》339 次语言、0 完整导出 | 用户暂停收束，未交付；未评估项不能记成成功 |

通过要求：所有数字说出范围；不知道的就查记录，不凑一个更好看的结果。明确至少两个“做过但未部署/未达标”的方案及停止理由。

仓库约定不引入 `unittest.mock`，优先既有 Fake service/client、真实 SQLite 与临时目录。并发测试通过 Event/barrier 控制明确交错，不靠“睡一秒大概刚好执行到这里”。不为了学习重新调用真实付费 H3。

四项练习交付：

1. **控制与恢复**：读 `test_mid_decision_user_input_supersedes_stale_write_and_is_not_truncated`、`test_pause_preserves_requested_tool_and_resume_executes_it_once`。设计“新消息在本批交接期间再次追加”的变体，写明队列前缀与尾部断言。
2. **事务与并发**：读 `test_plan_and_all_carried_orders_roll_back_when_one_order_is_missing`。再设计“内容已改，审阅决定写入触发器失败”的用例，明确哪些表必须回滚、哪些文件不是这个事务的对象。
3. **上下文**：读 `test_258k_budget_counts_whole_request_and_recovers_exact_overflow_after_restart`。设计两个同工具不同分页同时存在、其中一个对象更新后的回读用例，验证历史可读而当前不受旧观察污染。
4. **未知提交**：读分页与来源合同测试。设计第一页短页但仍有下一页、重复页、列表接口报错三个变体；说明为什么它们不应自动确认未提交。

不要求为了凑数量复制已有测试。验收重点是能写出会在某个真实缺陷下失败、修复后通过的断言，并知道测试用 Fake 验证的是程序调度，不能据此证明真实模型语义正确。

## 8. 游戏迁移与 Eval 的综合设计题

题目：阿遥答应把钥匙交给玩家，守卫在模型推理期间取走钥匙；阿遥未亲眼看到，但导演知道。玩家说“你已经把钥匙给我了”。请设计五分钟系统说明，再给十个测试场景。

必须回答：

- 世界中的钥匙所有权来自引擎；玩家的话是声称；阿遥信念来自可见观察；导演不能把全局秘密直接灌给阿遥。
- 旧 transfer 命令的 item_revision/所有权条件失效；不发生第二份钥匙或重复奖励；有明确失败回执。
- 阿遥通过合理感知/查询更新信念，再决定对白和下一目标；Persona 影响表现，不改变权威所有权。
- 记忆保存事件发生与获知时间，当前状态与历史经历可同时正确；旧索引命中仍要经过有效性判断。
- 指标覆盖实际目标、角色一致性、叙事因果、工具效果与信息边界；普通成功、纠错、重启、动作重试和无证据问题都有样例。
- 单 Agent、多 Agent、带/不带语义记忆的比较控制预算与任务集；真实用户和 Agent 都改变世界，不能只有静态聊天。

通过要求：至少三个确定性世界状态断言、两个需人工/模型 rubric 的质量项、一个 memory 检索故障定位对照；能指出哪个模块无需模型调用。参考：[第 03 章](03-context-memory-rag.md)、[第 05 章](05-game-agent-design-and-evaluation.md)。

## 9. 高频连续追问：答题要点

| 问题 | 必须命中的关键点 |
| --- | --- |
| 你的 Multi-Agent 和多个 prompt 模板有何区别？ | 独立上下文、任务身份、持久状态、依赖与所有权、真实并发及交接 |
| 为什么不是固定 workflow？ | 计划由目标语义生成/修订；程序约束执行协议，不固定所有创作阶段；轮询等确定性步骤仍由程序处理 |
| 为什么都用同一模型还要分角色？ | 隔离范围与上下文、职责和并行；不是宣称不同模型能力，也不是独立错误概率 |
| 为什么最多四个？ | 当前本地实现默认值和资源取舍；没有证明是所有任务最优值 |
| Worker COMPLETED 代表视频成功？ | 需要区分 turn、tool response、work order、generation task 和实际采用层次 |
| 返回 stale result 是丢数据吗？ | 历史保留与当前应用分开；不把旧归属结果合并当前完成 |
| 有 RLock 为什么还要版本检查？ | 读后慢操作期间锁释放，其他路径可改状态；单进程锁也不等于跨进程/远端互斥 |
| 有版本号为什么还要三方合并？ | 允许无关字段合并、保护已保存值；依赖检查和结构合并不同 |
| 为什么不在事务里等模型？ | 长占写锁、阻塞用户、放大失败；先快照、锁外慢操作、回锁验证适用范围 |
| 保存成功能否马上说用户要求全完成？ | 需要当前目标范围、实际采用/导出、未解决问题；结构成功不等于语义质量 |
| 什么错误能自动重试？ | 读/语言传输有限退避；写/外部操作先查已有效果、身份与提交阶段 |
| 为什么保留旧文件却不做版本 UI？ | 内部可追踪引用与用户内容版本功能不同；产品直接编辑当前结果 |
| 258k 能解决长期记忆吗？ | 预算只解决能否发送；检索、有效性、角色可见性与使用正确性另行解决 |
| 反思越多越好吗？ | 额外成本、同源盲点与错误经验；按有用反馈触发，用结果评测 |
| 四个 Agent 比一个快多少？ | 当前缺固定预算配对结果；依赖、关键路径、协调及返工决定，不能给虚构比例 |
| 最成功的优化是什么？ | 选择有明确范围和证据的一例；同时说明测量边界，不一定选最大百分比 |
| 最大失败是什么？ | 效率目标未达与未完整交付的暂停任务；提出有依据的后续实验，不粉饰 |
| 你从开源学到什么？ | 一个具体机制、一个本地映射、一项验证和一个没照搬的边界 |
| 如何证明 NPC 不出戏？ | Persona/知识/关系/任务状态分别定义，反例集、人工校准和长期重复，而非一句角色 prompt |
| 如果只给你一周改进？ | 选已定位的高频成本或正确性缺陷，最小修复和可判定实验；不承诺重写全系统 |

## 10. 最终验收产物

学完后应由你自己完成以下五份材料，不能直接复制本手册：

1. 一页运行架构图，标出模型决策、确定性控制、持久化与外部副作用。
2. 一份纠错时序，覆盖正常、旧响应晚到、远端已提交、提交未知四条变体。
3. 三个真实工程故事，带源码入口、历史版本、指标与限制。
4. 一个 NPC 记忆与动作方案，以及十条能失败的 Eval case。
5. 一张研究比较表：至少五项来源，分别写已借鉴机制、项目差异和待验证假设。

最后找一个人不按章节顺序连续追问 30–45 分钟。如果每个问题都只能靠重读标准答案才能接上，继续练习对应调用链；如果能从目标一路落到数据、动作、异常、恢复和验收，并主动区分事实与假设，就达到了这套材料的掌握标准。

## 11. Multi-Agent 专项验收：交互、上下文、工具与并行

先完成 [01B 的 20 分钟白板推演](01b-multi-agent-walkthrough.md)，再做下面五项。对应总表中的 15 分，每项 3 分：只会术语 0 分；能说正常流程 1 分；能处理反例 2 分；还能定位源码和设计有效验证 3 分。专项至少 12 分，且不触犯第 1 节关键条件。

### A. 交互协议：不用“大家共享 memory”含糊带过

给你一个失败 AssetPlan 请求和一个已保存图片结果，分别说明怎样交给下一 Worker。

必须区分 ArtifactRef、ToolAttemptRef、ContextManifest、AgentResult、completion receipt 与 output slot。说明谁能读哪次调用、何时补入相关完成交接、为什么项目 ID 相同不等于把全项目所有兄弟结果都广播。

反例：任务取消了，但此前有一份已经完成的媒体观察。能否使用该事实？答案必须同时处理“证据范围仍有参考价值”与“不能复活旧任务所有权”，不能一律删掉或一律认可。

### B. 上下文装配：从存储字段走到最终 payload

选 ASSET_BUILDER 和 POST 阶段 DIRECTOR，各自画出：goal、work_order、context、working_set、工具目录、已加载 schema、实际图像输入，以及 instructions 的来源。

必须解释：原始 specialist_turns 为什么排除；不同 scene/shot/page 的读取怎样同时保留；working_notes 如何更新；何时读取快照、何时读取当前项目；POST 如何影响起始 schema。

反例：只有 adjacent_boundaries.guidance 保存了“上一镜人物已拿起杯子”。不能直接答“模型当然知道”。必须检查当前投影路径，指出现状和一个最终模型 payload 级验证。再解释 `artifact.inspect_asset` 出现在预加载常量、却不在默认 Registry 时实际会发生什么。

### C. 工具能力：能还原六条真实链，不要求死背 145 个名字

任选正文保存、图像生成、本地准确文字处理、H3、剪辑导出、失败调用交接中的三条，至少说出每条 3 个相关真实工具及其输入依赖、效果、返回证据。其余三条允许查目录，但要能选对，不能用不存在的通用 Shell/Browser 接口替代。

必须解释默认 145、REAL_H3 139 的统计口径；短目录不等于完整 schema；schema request 本身不执行业务；role preload 不等于权限；`agent.delegate` 不是默认递归分工入口。

反例：模型输出合法 JSON，但引用旧版本；工具输出 schema 校验失败，但 handler 已保存文件。分别说明在哪一层处理，为什么“JSON 合法”和“执行正确”不同。

### D. 并行编排：画出五单四槽和两组后续依赖

用 01B 的 A/B/C/D/E 举例，说明 PlanGraph ready 与 Executor claim 的区别。明确一个工单已经有 REQUESTED 时怎样继续；第 5 单何时有机会运行；视频下一次轮询未到期为何不应该占住线程；什么情况下仍须等同步操作结束。

A/B/C 完成、D/E 未完成时，写出 prepare → plan → apply 三阶段。说明当前计划继承哪些动作，哪些工单切 active-plan，为什么未来产物 ID 不能靠 depends_on 自动插值。

反例：Leader 后台推理尚未结束，用户消息到达；同一工单的旧 Future 又返回。必须同时保护消息队列、计划归属和工具副作用，不把它们压成一个版本比较。

### E. 优化与验证：讲出根因，而不只说“加异步”

分别用一个具体时间线解释整批 Future 屏障、Leader 饿死 Worker、长工单占槽三类问题。说清修复位置、真实历史证据与测量限制。

必须设计一项同预算对照和一项故障注入：观测 ready-to-start、交接延迟、重复副作用、总模型成本与任务质量。只画线程数量曲线不够；只说最终文件存在也不够。

反例：四 Worker 比单 Agent 成功更多，但用了三倍 tokens。不能直接宣称多 Agent 架构优越，需要区分推理预算、上下文隔离、并行结构和具体任务可分解性。

### 专项应留下的四份可复核产物

1. 一张从用户到最终文件的架构图，箭头标明传的是任务、引用、状态还是实际媒体。
2. 两份 Worker 输入草稿，逐字段指出其来自哪里、为何保留、何时过期；不能塞入整份项目来回避选择。
3. 一张事件时间线，至少含第五工单轮换、部分完成后新增任务、一次新意图、一个已受理远端请求。
4. 一份验证设计，标明已有测试能支持什么、本次尚未运行什么、哪个剩余性质需要新增覆盖。

如果能够从最终导出反查到采用 Take、远端任务、输入媒体、上游工单和用户意图，再反向解释每次所有权变更，才算完成这一部分的深挖。

## 12. Skill 与持续进度专项：从方法文件讲到下一次正确动作

配套阅读：[01C Skill 管理](01c-skills-management.md)、[01D 持续进度与下一步](01d-progress-and-next-action.md)。这个专项单独按 20 分诊断薄弱点，不额外叠加到第 1 节总分；至少 17 分，且关键边界题不能错。

### A. 8 分钟讲通一次方法装配，5 分

给定条件：项目偏好选了 `method.drama_series`，Leader 要安排分镜导演、素材制作和后期导演三张工单。

必须连续说出：

1. 偏好保存在哪里，如何进入 Planner 输入；初始 Run 为什么不必加载全部方法正文。
2. Leader 返回哪些选择字段，计划与 Run 分别保存什么，新工单 manifest 继承什么。
3. `production_skill_role`、`production_prompt_stage` 怎样影响正文；POST 导演如何切换共享职责、跳过普通格式导演补充、加载后期章节。
4. 章节精确标题匹配、完整 role reference、共享前后文去重分别做什么；哪些重复不会自动去掉。
5. 内层导演或 H3 编译为什么要显式继承方法/阶段；Tool、Method、Provider Skill 的责任边界。

每讲通一项得 1 分。说“所有 Skill 全塞进去，模型自己看”或“选方法就有了 Blender 工具”不能通过。最好现场打开一个 manifest，指出确切文件和标题，而不是只背流程。

### B. 6 分钟处理更新与缓存反例，5 分

场景：A 已在运行，B 已建单但未启动；用户修改偏好，维护者修改一个 reference 文件；随后 Leader 追加 C；再重开服务恢复 A。

每答对一项得 1 分：

1. A/B 创建时保存的选择 ID 不会仅因偏好修改而自动变动；C 也只有在 Run 已完成相应选择更新后才会继承新选择。
2. 完整重规划和追加计划的方法选择可能是替换与合并的不同语义，不能统一说成重选全部。
3. 进程内方法库有缓存；普通文件保存不等于所有请求立即使用新正文。
4. 重开后旧工单可以仍用旧选择 ID，却加载当前文件正文；没有给每份方法正文做不可变版本钉住。
5. 最新用户目标另从 Run 进入请求；选择/正文/目标更新不是一条统一广播链。

关键反例：loader 的“修改文件再加载”测试为什么不足以证明生产服务热更新？完整 Trace 为什么有助于解释过去输入，但不能自动构成一套 Skill 发布系统？

### C. 10 分钟还原下一轮决策，5 分

场景：Worker A 已成功保存两个镜头的不同读取结果，并生成一个候选。候选存在，但尚未采用；RunMemory 还留着一次已恢复的旧报错。此时用户要求保留原声。

每讲通一项得 1 分：

1. 指出当前项目事实、历史观察、任务合同、笔记、RunMemory 的区别，不能用一句“共享 memory”包办。
2. 两个镜头读取应按对象/范围分别保留；最近观察不等于唯一观察；当前写入如何影响旧读取。
3. 工具请求先持久化为 REQUESTED，next_owner=WORKER_TOOL；工具回执保存后才能据此继续决策。
4. 候选回收、正式采用、导出、内容质量、用户目标完成分别判断；旧 blocker 不能覆盖新的有效成功证据。
5. 最新要求进入 goal，必要的大块原文可由 context_ref 回读；既有笔记和已装配上下文仍要处理时效边界。

关键反例：`RunMemory.next_actions` 写着“导出”，为什么不意味着执行器会直接调用导出 Tool？追加一条“素材完成”的 ProgressEntry，为什么不会自动完成素材计划？

### D. 10 分钟解释真实失败并设计验证，5 分

使用 r21 声音缓存案例，按“旧问题 → 恢复事实 → 接手仍出错 → 用户补充事实 → 同 run 继续”的顺序解释。必须保留工程介入，不得把它说成全自主恢复或音频质量已通过。

评分点：

1. 准确区分历史报告与本轮检查，引用原报告，不把本次静态检查冒充真实调用。
2. 提出至少两个可竞争解释，例如工作集未投影新回执、旧任务说明强化旧阻塞；知道需要看最终 payload 才能定位。
3. 设计一个有新成功回执的换 Worker 接手测试，明确 gold fact、允许动作与禁止动作。
4. 设计一个请求已保存/工具完成后的重启测试，区分不同中断位置，检查是否重复副作用。
5. 同时测恢复有效动作延迟、旧阻塞滞留、无效重做及结果质量，不只统计 tokens 变少。

### 综合验收：两次更新交错，最后怎样交付

闭卷画一张时间线，包含：方法选择更新、用户红杯改蓝杯、一个旧模型返回、一个远端已受理任务、一个无关工单继续、一次进程重开、最后导出和回答。

对每个事件必须回答四句话：

- 当前权威事实在哪里，下一次模型实际能看到什么？
- 哪个持久字段或身份负责控制下一步？
- 哪些旧结果仍可复用，哪些只能留历史，哪些需要重读？
- 这一步是方法知识、模型选择、调度规则还是业务校验在发挥作用？

应留下四份材料：方法选择到最终输入的映射表、一次 Worker 的最小充分输入草稿、带持久化边界的事件时间线、两个故障测试的预期状态表。第一遍可以对照源码，最终应能在 15 分钟内连续讲通，不借“最后再让 LLM 判断一下”跳过事务、归属或副作用问题。
