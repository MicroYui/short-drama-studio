## 2. 故事一：从“等全队完成”到部分结果驱动的增量规划

**旧做法。** Leader 委派一批任务后，等待整批收尾再规划下一段。这个做法容易实现，工单之间的依赖也容易看懂，但把真正的依赖和人为批次边界混在了一起。

**实际症状。** 9 月 12 日的一次计划有五个委派，已有三个完成，导演和纸面任务仍在运行。已完成事实已经落盘，但依赖这些事实的新任务仍不能开始。扩线程数量没有解决这个问题，因为调度条件仍是“整批结束”。

**改动。** 允许已经完成的工单触发局部补充计划，保留仍在执行的工作。已消费完成结果先记录，避免每一轮重复触发同一规划。Leader 请求分成准备快照、锁外慢调用、回锁验证应用；工单继承使用明确 action IDs，计划、运行指针及继承归属原子保存。

**为什么不能直接拼接新计划。** 当用户已改变目标，补充计划可能是按旧目标生成的；当旧工单仍在跑，重新创建相同工单可能导致重复媒体请求。必须验证当前计划、最新要求、已消费结果与仍然有效的归属，而不只是“新 JSON 能解析”。

**验证及限制。** 当时记录了 306 项相关历史测试通过，覆盖部分完成、继承、重启与冲突；这不是完成了一组真实制作速度对照。真正收益是消除了不必要的依赖屏障，端到端能省多少仍取决于关键路径。参考过 Dask 的完成顺序消费、AutoGen 的类型化消息和 Temporal 的消息处理原则；项目没有因此引入这些运行时依赖。[原设计与验收](../incremental-worker-planning.md)

面试追问：“部分完成到达两次怎么办？”回答应包含完成结果身份、消费记录、应用前的当前状态验证；不能只说队列会自动去重。

## 3. 故事二：有增量规划后，为什么 Worker 反而得不到运行机会

**旧问题不是同一个。** 增量规划解决批次屏障，却可能让控制循环反复进入 Leader：处理新结果、调用模型、又开始下一轮规划，已有 Worker 工具等待执行。

**证据。** 报告记录北京时间 02:57:11–03:00:56，旧导演/纸面工单处于需要继续工具的状态；期间执行了五个 Leader 工具，六次语言调用累计 146,421 输入、9,805 输出、219.45993 秒。模型有工作，系统也有活动日志，但真正需要推进的 Worker 没得到机会。[原观察](../research/2026-09-12-generation-quality/12-carried-worker-scheduling.md)

**修复分两层。** 第一层让 Runner 每次推进有限 Leader 步骤后就给 Team 执行机会。第二层把慢 Leader 请求放到可收集的 Future 中，让已有 Worker 在此期间继续完成和保存，避免只把饥饿方向反过来。

**随后暴露的细节。** 暂停通过 `ExecutionYielded` 这种控制异常传播，它继承 `BaseException`。如果后台包装只捕获 `Exception`，Future 可能永远不进入有结果或有异常的终态，主循环一直以为规划还在跑。修复显式把控制异常写入 Future。这里不是多加一个重试，而是修复执行完成信号。

**验收重点。** 慢 Leader 时 Worker 可完成；新用户消息到达时旧补充计划可丢弃；已开始工具回执不丢；继承工单状态不被较旧快照覆盖。该故事说明“模型正在输出”并不等于任务系统有公平进展。

口述可以概括为：“先去掉全队屏障，再发现协调者占据推进机会；于是把语义规划和运行推进解耦，并补齐控制异常的 Future 终态。”

## 4. 故事三：四个线程都有活干，第五个工单仍被饿住

**症状。** 四个长工单会在一次线程占用中连续执行多轮操作。图像操作约 99–133 秒，后续检查有 117、255、165、188 秒的记录。第五个已就绪工单至少等待 10 分 50 秒。

**错误的直觉修复。** 增加到八个线程可能增加峰值负载；假装图像接口支持异步任务 ID 则不符合真实 Provider 合同。问题是一个槽位被整个工单长期占住，调度粒度太粗。

**实际修复。** 在一个动作完成并已持久化后，如果有其他 ready 工单，就释放当前槽位；后续再按可恢复状态继续。没有 ready 同伴时仍连续推进，避免机械地每做一小步都排队。用户暂停/补充意图优先于再次分发，非就绪或被审阅阻塞的工单不能制造无效轮换。

**观察结果。** 原来长期等待的“准确文字证据”工单在恢复约 0.385 秒后实际进入执行。同一真实窗口内，另一个第五位就绪的“对峙”工单在平面合成结束后 1.064 秒启动；峰值仍为四个，窗口内十次模型启动、零次 Leader 调用、零工具失败。两条观察不是同一工单的受控前后对照；不能说它从用户提交起只等了 1.064 秒，也不能说整片减少 10 分 50 秒。正在运行的同步操作仍需结束，其他关键路径可能更长。[公平性报告](../research/2026-09-12-generation-quality/43-worker-fairness.md)

**可迁移点。** NPC 群体中也可能出现某个角色长时间推理或持续占动作资源，其他角色始终不响应。应讨论任务时间片、持久边界、资源预算及尾延迟，而不是默认更多角色就开更多无上限并发。

## 5. 故事四：输入很大，先证明重复在哪，再压缩

一次局部编辑请求本地估算 **81,531 tokens**，Provider 报告 **81,541**。工作集占 42,642，已发现的 14 个工具 schema 占 15,483。最新完整 16 镜分镜约 20,078 tokens，在观察中只出现一次；不能看到大输入就断言“所有内容重复注入了几遍”。[诊断记录](../research/2026-09-12-generation-quality/18-worker-input-redundancy.md)

随后针对素材 Worker 做的是精确优化：按实际需要暴露字段、紧凑目录、消除等价重复 pack，而不是抹去人物约束或简单截前 N 个字符。

| 真实输入回放 | 旧完整输入 | 新工单使用新 schema | 老工单仍持有已发现 schema |
| --- | ---: | ---: | ---: |
| 请求 A | 44,182 | 35,023，少 9,159（20.73%） | 41,113，少 3,069 |
| 请求 B | 45,689 | 36,546，少 9,143（20.01%） | 42,636，少 3,053 |
| 请求 C | 48,165 | 39,006，少 9,159（19.02%） | 45,096，少 3,069 |

这里“老工单”和“新工单”不能合并报一个 20%：运行中已发现的工具定义会影响收益。表格是完整请求的离线回放，不是重新付费调用同一模型后的任务质量或延迟对照。schema 缩小也可能增加后续发现与回读，需要观察完整轨迹。[素材 Worker 改进报告](../research/2026-09-12-generation-quality/25-asset-worker-context-efficiency.md)

面试关键句：“我先归因 working_set、schema、目录与真正正文，再按精确相同对象去重；同时把新旧工单的状态差异计入统计，没有只测一个变小的局部字段。”

## 6. 故事五：完成了但交接不出去，后继 Worker 就会重做

**旧现象。** 某个 Worker 已保存素材、检查或时间窗，给 Leader 的交接只剩简短状态；后继工单没拿到已确认事实，又读历史或再次检查。只保留“成功”不足以支持下一次行动。

**改动。** 从同一 run 的相关已完成结果装配具体工件、实际媒体来源、检查结论与未解决事项。大内容提供可回读引用；小而关键的事实直接可见。按精确身份判断相关性，不因多个工单共享全片计划引用就把所有结果塞给每个 Worker。

**边界。** 陈旧/取消的结果、未完整交付的部分结果不能冒充当前完成；历史检查的观察范围需要保留，“看过第一帧”不能被压缩成“视频已验收”。内容真的改变后必须重新确认，不能为了少调用强行复用旧检查。[交接修复](../research/2026-09-12-generation-quality/31-completed-worker-handoff.md)

**一个更小、可量化的相关例子。** 时间线选中字幕的只读任务，旧合同使用按镜头读取和截断结果，实际 105.70 秒、5 次语言、2 次读取。修复后同一小任务的一次观察为 **27.51 秒、2 次语言、1 次精确读取**，没有 schema-only、回读或失败；数据库 277,825 个叶值保持。改善来自选中对象的精确 ID 与完整结果交接，不能外推为整个产品普遍加速 74%。[原生验收记录](../research/2026-09-11-mature-video-production/09-implementation-delivery.md)

## 7. 故事六：结构化输出坏了，什么能修，什么绝不能猜

一次调试制作累计 144 次语言调用、4,760.78 秒语言耗时，包含九次视觉判断；112 次已执行工具。14 次 `image.advance` 属于确定性生命周期推进，不等于 14 次额外语言请求。墙钟 7,694.27 秒包含暂停，不能把模型/工具时长简单加起来解释它。[调用与 JSON 报告](../research/2026-09-12-generation-quality/20-real-call-overhead-and-json-compatibility.md)

其中八个原本已经含完整 Tool 决定的响应，有多余闭括号或唯一的尾部 notes 等兼容问题，纠正往返另耗 130.62 秒。原请求自身耗时 185.04 秒，其中有有用推理，不能全部算浪费。

**限定修复。** 只恢复能唯一确定的完整对象，保留原始响应，再经 typed 模型与工具参数验证。多个候选对象、重复关键字段、实质缺字段、真正截断的 JSON 不猜补。后来的两次真实同类响应能直接恢复并继续，证明这个路径实际触发过；不是证明所有格式错误都消失。

9 月 17 日又遇到两个必须区分的失败：

- Worker 已输出一个 739 字符的完整 Tool JSON，后接 71,369 字符纯空白，最终报告 incomplete，花了 280.154306 秒和 20,000 输出 tokens。r30 候选允许在角色当时允许 Tool 的前提下恢复完整 typed 决定，仍走 REQUESTED、来源校验和暂停边界；**没有追回旧请求时间，也没有在旧 r27 运行里重新执行那次决定**。
- Leader 的计划 JSON 真正截断，原失败 210.451965 秒。旧 r27 后来用了 113.887401 秒生成另一个更小、完整的新计划并成功执行。这个恢复不能归功于尚未加载的 r30，更不能把两个响应拼成一个“修好的计划”。

**追问答案。** 解析恢复是消除确定的表示噪声；语义补全是重新决定。两者不能混为一谈。即使决定解析成功，仍不证明工具执行安全、来源有效或目标完成。[后续失败与实际恢复](../research/2026-09-17-daily-production-goal.md)

## 8. 故事七：看起来是 SQLite 慢，测完却没有拆时间线

**问题。** 在 21 镜、42 个 clip 的现有作品副本上，当前项目 JSON 约 14.16 MB。一个小改动也会触发大对象复制、快照和验证。

**做过的改动。** 独立保存导出/审阅记录；共享资产实际不变时不写根项目；复用读取时的独立快照，当前持久内容未变时减少重复复制；并发变化时仍走三方合并。

| 操作 | 旧 P50 / P95，ms | 新 P50 / P95，ms |
| --- | ---: | ---: |
| 场次小修改 | 840.7 / 972.8 | 533.0 / 621.6 |
| 镜头小修改 | 894.7 / 1275.7 | 529.9 / 705.0 |
| 时间线小修改 | 878.9 / 1212.7 | 561.8 / 685.4 |
| 单条导出记录 | 868.5 / 935.5 | 1.30 / 3.30 |

**测量条件。** 同一案例、暖缓存、单写入者、每项两次预热与十五次正式采样。前三项中位数下降约 36%–41%。最后一行是单条仓库记录写入，不包含 UI、终态检查、事件与 FFmpeg，不是“视频导出快了 600 倍”。完整读取仍约 158 ms，未证明读取变快；保存锁仍约半秒。

**为什么没有拆时间线。** 时间线只占文档 0.76%，生产文档及历史占 93.4%；主要成本在 Python 深复制、快照和验证，SQLite 执行本身较小。于是优先删掉确认多余的工作，没把一个未经验证的架构偏好当性能优化。

**正确性如何验证。** 用真实 SQLite 触发器使后半段写入失败，验证正文、Take、事件与审阅决定一同回滚；比较历史内容完整保留；做页面修改、播放、导出与重启检查。历史记录为 120 个不同相关测试，不是本轮新跑的结果。[完整存储报告](../research/2026-09-16-storage-improvements.md)

这个故事很适合回答“你为什么没上更复杂数据库/事件系统”：因为先测清楚了瓶颈和需要保证的事务边界。

## 9. 故事八：五部影片都交付了，但不能说稳定性 100%

| 作品 | 成片编辑时长 | 用户墙钟 | LM / Tool / H3 | 版本与介入 |
| --- | ---: | --- | --- | --- |
| 打烊前的一杯 | 39.923333 秒 | 2:05:23.098 | 245 / 254 / 5 | r7→r8→r9，两次工程介入 |
| 钥匙在这里 | 35.625 秒 | 2:50:38.607 | 321 / 375 / 10 | r11，自主恢复交付 |
| 一起走一段 | 41.625 秒 | 1:16:56.582 | 228 / 229 / 4 | r16，自主恢复交付 |
| 店门开了 | 34.416667 秒 | 1:55:27.668 | 220 / 235 / 5 | r18，自主完成 |
| 早餐带上 | 43.790001 秒 | 2:40:54.788 | 493 / 472 / 10 | r18，含四次额外 H3 内容返工 |

统计从普通要求到 StudioJob 持久化 completed，保留失败、等待与介入。第二至第五片没有制作中追加创作、补图、手工剪辑或运行时重启；旁路工程投入非零且未精确计时。第五片之后加载的 r20 修复不能算成第五片收益。[五片报告](../research/2026-09-16-five-film-stability-run.md)

不能推出 100% 稳定性的原因有四个：版本不同；brief 不同；首片有工程介入；样本不是固定环境随机重复试验。可以支持的结论是“多次真实完整交付，后四片在各自版本上自行恢复并完成”，而非长期无人值守可靠率。

质量也分层：文件能完整解码、时间线有内容、声音存在，与叙事连续、听感自然、口型准确不是同一维度。第五片 SRT 只含前九句且未按时间排序，clean 文件还带源视频烘焙文字；这些问题不会因主文件看起来完成而消失。全部影片未完成全片连续视听与精确口型验收。

**反思重点。** H3 远端成功不代表内容合格；工具非成功也可能是正确拒绝过期输入。要把 Provider 失败、软件缺陷、并发保护、语义返工和能力缺项分别统计，否则“失败率下降”可能只是删掉了必要保护。

## 10. 故事九：效率目标明确失败，局部补拍却验证了另一种价值

9 月 17 日原目标包括：每片不超过 120 次语言调用、已报输入不超过 600 万、首 H3 在 15 分钟内、最后必需 H3 返回到交付不超过 10 分钟、总墙钟不超过 45 分钟。它们是观察指标，不是到点强行停止创作的运行门槛。

**r21《最后一把伞》**实际完成 36.335 秒双版导出，墙钟 **147 分 11.875 秒**；269 次语言、14,776,928 输入、541,227 输出；292 次工具中四次失败；五次图片、六次 H3 成功。首次 H3 在 **35 分 10.968 秒**，最后 H3 到完成 **54 分 50.791 秒**，五项目标全未达。期间有一次环境修复和一条资源恢复消息，不能写成全程零介入。

**为什么慢，不能只怪 Provider。** 某组准备提示 8,020 字符超过 7,000 上限，压缩后 6,825，共耗 352.576 秒，其中压缩 230.306 秒；这是语言编译成本。首组图片绑定已齐后，因全片正式化条件等待的可定位窗口为 152.276 秒，随后规划、交接、编译又用 543.833 秒。移除前一个门槛不能被宣传成省了后面所有时间。

**r26 局部补拍**完成的是另一个目标：只换《早餐带上》第 3 镜父亲反应，保留声音、字幕、其他镜头与剪点。实际 **26 分 06.913 秒**，32 次语言、39 次工具、一次 4 秒 H3，无新图片或第二条候选；采用约 2.54 秒画面。总长保持 43.790001 秒，其他 18 个 clip、九条字幕保持，完整混音输入的 **2,101,921 个 48kHz 立体声采样帧逐样本相同**。

这个音频比较证明选取与混音输入没有变化，不证明 AAC 字节相同，也不是听感验收。中途暂停重开沿原请求恢复，暂停窗口 67.791 秒保留在墙钟里；远端可继续运行，不能简单扣掉它来伪造无暂停耗时。

此处的价值是“局部修改范围可控、已完成成果可复用、恢复不重复生成”，不是从零制片速度已经达标。[完整记录](../research/2026-09-17-daily-production-goal.md)

## 11. 故事十：UNKNOWN 比失败难，空列表不能当未提交

外部 H3 提交期间连接异常，存在“远端创建成功、本地没收到 ID”的窗口。直接重试可能再扣费并生成另一条视频；只把状态改 FAILED 也会丢掉真实在途任务。

现实现记录提交阶段，UNKNOWN 走对账。Provider 列表原来只看前 50 条，目标可能在第 51 条；后来增加有界分页、去重、重复页终止和真实扫描范围。Fake 场景覆盖第 51、151、551 条；真实两次只读请求都返回空页，这验证了真实接口可调用，**没有验证在真实账号有大量历史时的翻页召回率**。[分页报告](../research/2026-09-16-h3-reconciliation-pagination.md)

《修好了》观察中有一次 61.143 秒提交未知，列表为空，系统没有重复提交。这个行为是正确保留不确定性，不是成功生成，也不是已经证明未提交。若工具允许显式确认未提交，填写 reason 只是操作记录，不能自动成为外部事实证据。

还有一个很小但真实的交接问题：仅 99 tokens 的完整候选列表/query 被通用 EXTERNAL 回执缩成空结果，Leader 又花 48.594963 秒规划回读。修复保留该工具的真实扫描查询与 candidate_count；非空大详情仍精确回读。已花掉的 48.59 秒不是未来每次必省的常量。

面试时要把这件事讲成外部副作用恢复问题：本地 fingerprint、数据库事务、查询对账各解决一部分，没有任何单个机制凭空提供端到端 exactly-once。[日常观察](../research/2026-09-17-daily-production-goal.md)

## 12. 故事十一：精确帧、相邻源窗与“无关修改不失效”

短视频系统把 Agent 的抽象推理压到了真实媒体坐标上。某帧真实时间 10.166667 秒，经错误换算后变成 10.208333 秒，恰好前进一帧；静态的“差不多十秒”对边界动作检查就可能读到另一状态。后续修复按整数 PTS/timebase 处理，源窗使用半开区间等明确约定，并测试数值边界。[日常生产中的 PTS 与来源记录](../research/2026-09-17-daily-production-goal.md)

类似地，成片前面加一秒使后面的 FILM 位置整体顺移，并没有改变某镜头的原始媒体和源窗。若整个 timeline revision 都被纳入 H3 输入有效性，所有后续候选都会无谓失效。修复排除无关绝对成片位置，同时保留真实媒体、源窗、所选对象和对白关系的检查。这里不是“取消版本检查”，而是让依赖粒度匹配实际动作。

另一次生成组要求 4 秒，动作参数却明确填 5 秒，应当拒绝。后续用户把镜头设计改到 5 秒而继承组时窗没同步，则是真实的派生状态缺陷。r30 只对时长实际改变且未明确给出新组的关联组更新；旧 r27 运行中 Agent 自行修正后的成功不能归功于后装包。

迁移到游戏后，这相当于：世界总版本增加不一定使“打开这扇门”失效，但门的锁状态、钥匙所有权或任务条件变了就必须重新验证。依赖太粗造成无谓重做，太细漏掉真实前置条件；应从动作实际读取集推导。

## 13. 故事十二：尝试过压缩目录，最后为什么决定不部署

这一段适合讲技术取舍，而不是包装一个成功案例。

| 方案与状态 | 记录结果 | 为什么不能扩写收益 |
| --- | --- | --- |
| 完整请求第一轮回放 | 219,384 → 218,968，净减 0.190% | 局部字段缩小被其他开销抵消 |
| 限定回执投影中间结果 | 210,048 | 不是计入全部合同后的终值 |
| 计入读批合同、真实序列化顺序后的结果 | **213,052**；报告记作相对 r21 净减 **2.702%** | 2.702% 对应 218,968 基线；若从链首 219,384 算，则为 2.886%，不能混用分母 |
| 14 类展开目录原型，未部署 | 约省 7.664% | 可能增加目录发现轮次 |
| 139 个精确 ID / 14 类用途原型，未部署 | 约省 7.192% | route/timeline/context 的选择出现歧义风险 |
| 活动 schema 集合设计，未部署 | 含新增指导净省 2.016% | 重新发现、缓存及真实选择效果未验证 |
| 一份真实 r27 请求的重复 source_context 别名原型，未实施 | 108,199 → 103,656，净减 4.199% | 只有一份完整输入的离线实验，没有调用、质量或账单收益 |

注意第三行的基线：本轮复算，`(218968 - 213052) / 218968 = 2.702%`，而 `(219384 - 213052) / 219384 = 2.886%`。原报告将这些数连续列出，口述时很容易混用分母。本章保留报告的 r21 比较口径，并明确链首到终值的另一个算术结果；缺少原始回放明细时不推断额外收益或改写历史统计。两个口径都远未达到原 40% 目标。[原报告](../research/2026-09-17-daily-production-goal.md)

四份完整输入的归因中，工作集占 47.41%、当前 context 11.19%、已加载 schema 16.38%、工具目录 9.41%、角色与选中 Skills 仅 3.62%。因此“删除所有方法知识就大幅降成本”没有数据依据。工具在本地注册本身不消耗模型 token，常驻简述目录与按需加载完整 schema 也不是同一回事。

用户最后明确稳定性优先，结束额外效率优化与制作观察。于是保留简述目录，没有为了一个离线比例部署会增加选择歧义的方案。可解释、可回读、少返工，比最短 prompt 更接近产品目标。

## 14. 最后一个状态必须如实交代：《修好了》没有完成

第二片 r27 从空项目开始，45 分 12.557 秒时已达 125 次语言调用、6,434,485 输入，四项阶段目标未达。用户最终结束观察，暂停响应约 4.910606 秒；至 paused 共 **140.710579 分钟**。

固定快照：339 次语言中 336 成功、3 失败；338 次有完整 usage，一次连接失败未知；22,507,969 输入、689,461 输出；455 次工具中四次失败；12 个成功 H3，另一个 ACKNOWLEDGED、一个 SUBMIT_UNKNOWN；六次图片；**完整导出为零**。

因此首次 H3、调用数、输入与墙钟记为 NOT_MET；最后 H3 返回到交付记为 NOT_EVALUABLE_NO_DELIVERY。后者没有终点，不能填零、成功或虚构失败耗时。

历史标准价已知小计约 $300.82，包含已知语言、图片与成功 H3；未知语言用量、ACK 与 UNKNOWN 费用未全部结算。它不是本轮最新报价、实际账单或费用上界。若面试不需要成本绝对值，优先讲统计原则，避免在缺少实时核价时讨论当前单价。

之后 r30 加载但保持暂停；不是在 r30 上完成了第二片。停止观察是一项用户决定，不能被改写为 Agent 成功交付。[终态与限制](../research/2026-09-17-daily-production-goal.md)

## 15. 把每个故事压成可回答的六句话

1. 触发条件是什么，用户受到了什么影响。
2. 哪条 Trace、状态或测量排除了最初的错误猜测。
3. 改动哪个最小机制，为什么它作用于根因。
4. 如何验证不丢数据、不重发外部动作、不覆盖人工修改。
5. 收益属于单元测试、离线回放、真实局部观察还是端到端结果。
6. 仍不能保证什么，下一项有信息价值的实验是什么。

准备时优先熟练讲三个故事：调度三层问题、用户纠错完整链、完整请求优化与未部署取舍。其余作为追问深度储备。不要把上述十几个案例串成“每次优化都有显著提升”；它们真正展示的是根据运行证据持续修正系统模型。
