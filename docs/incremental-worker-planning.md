# 按已完成分工补充计划

2026-09-12。修复目标是让已完成结果及时进入下一次制作判断，同时保留其他正在执行的分工。此轮只有本地 Fake 与真实持久化链路验证，没有调用媒体 Provider，也没有将当前调试项目的续跑作为稳定性验收。

## 实际问题

《一起签》的只读快照在 02:25:57 显示，当前计划有 5 个独立委派：3 个基础图分工已完成，导演和纸笔分工仍运行。计划没有后继步骤。线程执行器已经逐个回收完成结果，但 ProductionManager 只有在当前计划全部本地步骤成功后才自动重新规划。因此，如果新的工作需要根据刚产出的引用安排，Leader 无法提前作出这次判断。

既有依赖图中的后继本来就可以提前执行；这次补齐的是“部分完成后追加尚未规划的工作”。是否已有足够素材、是否值得提前开工，仍由 Leader 根据真实结果决定。几张基础图完成不等于视频输入已经准备好。

## 公开实现与取舍

| 一手来源 | 可以借鉴的机制 | 本地应用 |
| --- | --- | --- |
| [AutoGen Core：Message and Communication](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/framework/message-and-communication.html) | Agent 通过可序列化消息通信，运行时将消息交给处理器；发布和请求响应是不同交互方式 | 已完成 WorkOrder 的 ID 和落盘结果作为规划事件，不用整批线程结束充当唯一交接点。没有迁移 AutoGen 或复制其运行时 |
| [Dask：Futures](https://docs.dask.org/en/stable/futures.html) | 按完成顺序取回 Future，并允许向 `as_completed` 动态加入后续 Future；现有依赖可以继续执行 | 独立收取 Worker 结果，在 Leader 请求进行时继续调度既有就绪工作；不重新提交整个任务集合 |
| [Temporal：Handling Signals, Queries, & Updates](https://docs.temporal.io/handling-messages) | 自定义消息 ID 用于应用层去重；异步处理器可能交错执行，需要明确状态更新边界和结束条件 | 持久记录已触发规划的完成 ID；慢推理不持运行锁，计划与工单归属在短事务中一起保存；暂停或新消息到达时丢弃旧补充结果 |

这些是机制借鉴，并不表示公开框架采用了本产品的同一套规划合同。尤其不能把“每个完成事件至多触发一次可选补充请求”写成所有外部操作的 exactly-once 保证。

## 当前实现

`prepare_completion_planning` 只接受真实完成并已保存的 Worker 结果。在还有其他分工继续执行时，收集尚未消费的完成 ID，构建当前上下文，并先保存消费记录。普通媒体查询、Tool 中间结果、定时唤醒不会单独触发规划。

`plan_after_completions` 在独立线程中进行本次语言判断，不持运行锁。Leader 只提出新步骤，或说明当前没有额外可执行工作。Runner 仍然收取 Worker 结果、启动既有就绪任务，并执行原计划的读取和编辑；同一时间不会再启动另一份 Leader 补充请求。

`apply_completion_plan` 先确认计划和用户要求仍相同，再追加新步骤。旧步骤保持原文，所有进行中的 WorkOrder 原样继承。新计划通过精确 `inherited_action_ids` 识别原动作的完成和执行状态，不改写旧 Action 的来源，也不重新派发已有动作。新增步骤可以依赖旧步骤。计划、当前指针和工单的新归属在一个 SQLite 事务中保存；媒体任务 ID、供应商任务 ID、Tool 请求和结果不变。

Worker 保存及执行器的机械续跑使用同一份短运行锁，防止旧对象把刚继承的归属写回。共享项目的真实内容仍由原有读取、引用和保存校验处理，补充计划不创建另一份项目真相。

明确等待时不创建空转步骤，不追加检查点或强制检查轮。相同完成 ID 在下一次 Runner tick 或重启后不会再次触发这次补充。补充请求失败会留下失败事件，原计划与其他分工继续；下一份真实结果、用户要求和原计划完成后的正常规划仍可推动任务。它是提前安排工作的机会，不是必须通过的新阶段。

暂停和新消息等待已开始的调用结束，但不应用旧的补充建议。当前计划已被修改、工单返回失败或用户要求改变时，同样丢弃过期建议。

## 验证与尚未证明的收益

本地测试入口：

- `backend/tests/test_incremental_worker_planning.py`：部分完成后启动后继、在途媒体记录保持、原 Action 连续跨两次追加不重派、等待跨重启不重复、旧建议不能改写原步骤或覆盖新计划、慢 Leader 期间 Worker 仍可落盘、暂停与新消息丢弃旧补充。
- `backend/tests/test_incremental_plan_state.py`：继承动作参与依赖计算、旧记录兼容、工单与计划归属同事务提交和失败回滚、完成事件 ID 与工具 schema ID 不被并发旧对象覆盖。
- 既有 ProductionManager、TeamExecutor、Studio Harness、提示词任务续跑及 AgentRuntime 回归继续覆盖原有调度与恢复行为。

本轮本地验证：新增调度集成 7 项、状态与 AgentRuntime 51 项、工具上下文与规划桥接 33 项、既有 PM/Team/Studio/提示词续跑 215 项，共 306 个不同用例通过。相关 Python 文件 Pyright 无错误或警告，`git diff --check` 通过。此时新代码尚未加载到真实制作服务；新增模型字段随最终集成统一重新生成 API Schema。

新增补充判断可能增加语言调用次数。当前仅证明可以重叠执行、不会因这次补充重派已有工单，以及等待时不会按 tick 空转；尚未证明真实模型会合理选取后继、降低总耗时或提高最终影片质量。关键路径时间、额外语言用量、返工和质量需要在新的空项目视频前端到端制作中测量，不能用修复后的当前案例续跑替代。
