# Phase 14：多分钟短剧的分层 Multi-Agent 规划

## 目标

Phase 13 只区分通用视频与抖音短剧的创作策略，默认仍是约一分钟。本阶段把抖音短剧扩展为真正的多分钟剧本规划，并保持两条边界：

- 时长是用户可自由填写的规划目标，不是 3/5/10/15 分钟四档套餐；这些数值只作为快捷按钮；
- 本阶段主要验证剧本、大纲、场次、对白和分镜规划，不调用 GPT Image 2 或 MiniMax-H3，也不把视觉生成结果当作验收条件。

本阶段当时验证的界面范围是 15 秒到 30 分钟。Phase 22 已取消这个产品档位边界：当前桌面端支持不少于 4 秒的任意数值，并默认进入同一可恢复分层 PlanningRun。抖音短剧默认 5 分钟，通用视频默认 60 秒；分钟与秒可以切换，快捷值仅用于输入便利。Agent 会尽量围绕目标展开，但实际成片允许合理浮动，不形成阻止用户继续的硬门。

## 为什么改成分层规划

把 5–15 分钟的全部对白、场次、连续性和逐镜执行一次性塞给一个 Planner，会让上下文随镜头数增长，后半段更容易遗忘前文、重复对白或输出截断。当前实现采用同一进程内的分层 Agent 调用，不新增微服务：

```text
用户输入与制作类型
  → Story Architect：整集因果、人物、场景、道具、对白、场次契约
  → Script Critic：开放式审阅因果、动机、伏笔回收、重复与节奏
  → Story Architect：有必要时最多自动修订两轮并逐轮复审
  → Scene Director 01：只展开第 1 场
  → compact continuity handoff
  → Scene Director 02…N：逐场展开
  → ProductionPlan：合并场次与逐镜计划
  → 现有资产、生成、QA、时间线能力（后续阶段按需执行）
```

Story Architect 负责全局事实，不输出镜头、关键帧或 Provider Prompt。Script Critic 不拿固定答案或节拍表反向出题，只对当前大纲中有具体证据的因果矛盾、世界规则、人物动机、未回收问题、重复信息、对白功能和时长节奏提出建议。若建议需要全局改写，Story Architect 最多自动修订两轮，每轮后重新审阅；达到上限仍有问题时继续保留为用户可忽略建议，不阻断逐场规划。

每个 Scene Director 只接收：

- 整集摘要、风格和当前场涉及的人物/场景/道具；
- 当前场的叙事目的、目标时长和锁定对白索引；
- 上一场实际输出的精简连续性状态；
- 下一场预期入口。

它不会接收此前所有镜头的累积文本。场间 handoff 只保留场景状态、人物状态、道具状态、已经成立的事实和待回应问题，避免上下文无限膨胀。

## 剧本与连续性校验

结构化模型新增 `EpisodeOutline`、`PlannedSceneContract`、`SceneShotPlan` 和 `SceneContinuitySummary`。校验只保护明确的结构事实：

- 场次序号连续；
- 每句对白恰好属于一个场次；
- Scene Director 不能改变、重复或遗漏分配给本场的对白；
- `SCRIPT_LOCKED` 的说话人、原文、声音类型和顺序保持不变；
- `ScriptReviewReport` 随 `ScriptVersion` 持久化，剧本页展示优点、问题、涉及场次和建议；
- 场次只引用大纲声明的地点；
- 分镜保留所属 `scene_id`，后续 H3 Prompt 可以读取当前场上下文；
- 场次和镜头总时长围绕用户目标展开，保留宽松容差。

系统不规定每隔几秒必须有爆点、每场必须几句对白或每分钟必须多少镜头。抖音短剧的悬念、因果推进和回收仍由 Agent 根据题材判断；结构校验不会把创作建议变成硬门。

## 失败与恢复

Story Architect 首次输出无效时自动做一次结构修复；仍失败则使用本地可复现大纲。Scene Director 按场独立修复和回退，一场失败不会丢弃此前已经通过的场次。下一场使用上一场实际采用的 `continuity_out`，而不是继续相信未落地的理想状态。

Script Critic 不可用时，大纲仍可进入逐场规划并记录提示；Critic 要求修订但修订调用失败时，也保留原大纲和审阅建议。它是高自动化质量回路，不是新的审批门。

未配置 GPT-5.6-sol 时，本地回退可以按任意目标时长生成多场结构，供 API、持久化和后续流程开发使用。它只证明工程链路，不代表长篇剧本质量。

## 长流程兼容调整

虽然本阶段不调用图像或视频 Provider，已有下游接口同步消除了几个明显的长片容量问题：

- H3 路由 Agent 按场景且每批最多 20 镜处理，不再一次塞入整集；
- 显式路由请求可容纳 500 镜；
- 参考视图缺口不再只返回前 16 条；
- 时间线超过 24 镜时分段规范化后再拼接，ffmpeg 不再为整集创建一个无限增长的 filter graph；
- ffmpeg 导出在服务锁外运行，长导出不会阻塞项目读取；
- 默认自动流程不再运行声音 QA，角色参考音频输入能力继续保留；
- 镜头选择、参考计划刷新和对白归属检查移除了不必要的平方级扫描。

这些修改只是保证长剧本可以继续接入原有流水线，不构成本阶段的 H3 或 GPT Image 质量结论。

## 验证边界

本阶段的验收以本地和 Fake Language Client 为主：

- 3、5、7 分 10 秒、10、15 分钟等自定义目标均能展开为连续场次和 4–15 秒分镜；
- Story Architect 到 Scene Director 的实际连续性 handoff 可追踪；
- Script Critic 可触发最多两轮 Story Architect 修订、逐轮复审并持久化最终建议；
- 单场输出失败只局部回退；
- 多场数据正确持久化到 `StructuredScene` 与 `ShotPlan.scene_id`；
- 25 镜时间线会走分段 ffmpeg 导出路径；
- 不发出 GPT Image 2 或 MiniMax-H3 请求。

真实 GPT-5.6-sol 对不同题材的长篇剧本质量、信息密度和跨场稳定性仍需单独进行剧本审阅，不能由本地模板测试代替。

第一次 5 分钟真实剧本探针得到 7 场、36 镜、26 句对白和精确 300 秒计划，未发生结构或单场回退。人工阅读同时发现“删除未发送录音却仍宣称时间闭环”和“灯架绳损坏未回收”两类剧本问题，证明只做 Schema 校验不足；Script Critic 正是由这类通用因果与伏笔缺口驱动，而没有加入时间旅行、婚礼或灯架专用字段。

接入 Critic 后的第二次真实探针完成了 Story Architect → Critic → 修订 → 复审 → Scene Directors：第一次审阅提出 7 项问题并自动修订，原先的闭环悖论被改成“可能未来随选择覆盖”；复审仍提出 9 项建议，其中 2 项为高风险证物逻辑。这说明 Critic 确实能发现并推动修复，但单轮仍可能把问题迁移到新的因果支点，因此实现改为最多两轮。第二轮上限目前由 Fake Language Client 覆盖，尚未把一次随机真实样本写成稳定质量结论。
