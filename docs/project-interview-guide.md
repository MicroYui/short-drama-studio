## 1. 可以直接讲的项目介绍

### 90 秒口述稿

Short Drama Studio 是一个单用户、本地运行的 AI 视频制片桌面应用。用户可以用自然语言要求写剧本、制作完整短片，或者只补拍某个镜头；生成结果保存在同一个项目里，也可以继续手动剪辑。

技术上，桌面端使用 Electron、React 和 TypeScript，本地业务服务使用 Python 和 FastAPI，SQLite 保存结构化项目和任务状态，媒体保存在文件系统。桌面和剪辑能力基于 LTX Desktop 复用，语言、图片和视频通过独立 Provider 接入，当前视频主链是 MiniMax H3。

工程重点有三个。第一，基于持久化计划和工单实现 Agent 持续执行，支持独立任务并行、暂停、重启恢复，以及上下文过长时保存原文、按需回读。第二，用户编辑和模型生成可以同时进行，通过三方合并和局部修订校验保护已保存内容。第三，打通分镜、具体素材、镜头采用和时间线，支持只替换某一处画面并保留原声音、字幕及其他镜头。

项目已有真实成片、五部短片制作记录和局部补拍验收。一次存储优化在既有案例中将正文保存中位耗时降低约 36%–41%。目前主要不足是制片耗时和语言调用量较高，跨镜头质量也需要进一步改善。

## 2. 项目结构与核心链路

### 实际架构

```text
Electron 主进程：窗口、文件、Python 服务生命周期、原生能力
  ↕ preload 暴露的 electronAPI
React 工作台：剧本 / 镜头 / 成片 / 项目资产 / 制作助手
  ↕ backendFetch 请求；SSE 接收事件
FastAPI：short_drama_server.py → _routes/studio.py、short_drama.py
  → StudioWorkspaceService / ShortDramaService：内容、引用、剪辑等业务
  → StudioAgentRunner → ProductionManager → AgentRuntime / LocalTeamExecutor
  → ToolRegistry → 领域服务 → 语言 / 图片 / H3 / 可选 ComfyUI
  → Repository / AgentRuntimeStore：SQLite
  → 本地媒体文件；共享 Node / LTX / FFmpeg 导出运行时
```

这是本地模块化应用，主要运行在 Electron 和 Python 进程中；Agent Worker 是本地线程池中的逻辑分工。

## 3. 最值得准备的四个难点案例

### 案例一：模型结果晚到，用户正文已经修改

Agent 读取场次后请求模型，用户在等待期间修改了场次正文。模型返回后若覆盖整份项目，会丢失人工内容。

实现保留读取时的 `base` 快照，保存时比较 `base / proposed / saved`：只应用实际变化，稳定 ID 数组按对象合并，同字段冲突保留当前已保存值，并返回实际保存结果。编辑 API 另用预期正文或修订号拦截过期保存，前端保留草稿供显式合并。

**可讲的具体结果：**测试同时模拟“Agent 改正文和镜头运镜，用户已改正文”，最终人工正文保留，Agent 对无关运镜的修改仍保存。它验证的是合并语义，而不只是接口返回成功。

### 案例二：视频请求发出后断网，不知道远端是否建单

外部生成是有成本的副作用，HTTP 超时无法证明“没有提交成功”。

H3 路径记录请求指纹、准备 / 已开始提交状态以及远端任务 ID；同请求推进有锁，已确认提交可复用远端 ID。遇到不确定结果进入 `SUBMIT_UNKNOWN`，先查询和匹配远端任务，再决定如何恢复。查询列表为空也不能据此自动重发。

**追问重点：**本地防重与状态恢复能够降低重复执行风险，但不能宣称在不支持相应协议的外部系统上实现端到端 exactly-once。

### 案例三：只补拍 2.54 秒画面，保留全片声音

《早餐带上》的局部修改要求只换第 3 镜父亲反应，保持声音、字幕、总长和其他镜头。

实现将生成候选和正式采用分开，绑定已有剪辑位置、具体源窗和保留的声音；采用时明确 `KEEP_CURRENT_AUDIO`，新画面静音，避免把候选原声混入。真实任务一次 H3 返回后，从实际 4.46 秒源片中采用约 2.54 秒，替换全片 8.125–10.666667 秒。

**可讲的验证：**其他 18 个片段、9 条字幕和 43.790001 秒总长保持，完整混音输入的 PCM 逐样本相同。这个结果证明声音数据保留，不等于 AAC 文件字节相同，也不代表已完成主观听审。

### 案例四：保存慢，是否立即把时间线全部拆表

既有案例项目 JSON 约 14.16 MB，包含 21 个镜头、42 个片段。测量发现时间线仅占 0.76%，生产文档及历史占 93.4%，主要成本是 Python 深复制、快照和验证。

因此先将高频导出 / 审阅记录独立存表，跳过无变化的共享资产写入，并在没有并行修改时复用独立快照、减少重复复制，保留冲突时的三方合并。

**可讲的结果：**同一案例各 15 次正式采样，正文保存 P50 从约 841–895 ms 降至约 530–562 ms，降低约 36%–41%。完整读取未证明提速，优化结论也不扩大成整个制片流程的提速。

## 4. 高频问题与连续深挖

### A. 产品、架构和取舍

**Q01：这个项目主要解决什么问题？**

解决从“生成内容”到“持续制作”的断层。剧本、人物素材、视频候选和剪辑通常分散在不同工具里；这里把它们放入同一项目，使用户既能让 Agent 持续制作，也能局部修改并保留其他成果。

**Q02：它与固定工作流有什么区别？**

流程由 Agent 根据完整目标和当前内容制定，可以改计划、拆分工单或直接结束。用户只要求剧本就停在剧本，要求成片才继续。代码约束状态和工具合法性，不按关键词把用户路由到固定流水线。

**Q03：为什么采用本地桌面架构？是微服务吗？**

产品面向单用户，媒体文件、时间线、录音和 FFmpeg 都与本机紧密相关，Electron 便于复用成熟编辑能力。当前是本地模块化应用，Python 服务承载业务；没有部署成分布式微服务，也没有多租户调度系统。

**Q04：为什么前端用 TypeScript，后端用 Python？**

React / TypeScript 适合复杂交互，并能复用 LTX 编辑器；Python 适合现有模型、媒体处理和 FastAPI 领域服务。两边通过 HTTP 契约衔接，桌面能力走 IPC；已有导出逻辑则构建成 Node 运行时供 Python 调用。

**Q05：为什么使用 SQLite，而不是 PostgreSQL？**

单机单用户需要低安装成本、事务和可迁移性，SQLite 足够匹配当前规模。大媒体留在文件系统，频繁查询的状态有索引和独立记录。若未来有多机器并发写入，再评估服务端数据库；当前瓶颈不能简单归因于 SQLite。

**Q06：哪些能力是项目实现，哪些来自开源复用？**

LTX Desktop 提供桌面和剪辑基础；项目围绕制片工作台、领域模型、Agent Harness、资产绑定、局部修改、后端保存及 Provider 适配做集成和扩展。生成模型来自外部供应商，不把模型训练、完整剪辑引擎或上游代码归为个人原创。

**Q07：仓库里有 LTX、Kling 代码，是否都能实际调用？**

不能据文件存在判断能力。正式入口是 `StudioWorkspace` 和 `short_drama_server.py`，不启用或分发 LTX 模型权重。当前 Kling Worker 默认没有启用的生成 client，保留历史读取 / 取消等兼容；真实视频主链是 H3。

**Q08：“Provider-neutral”是否意味着随便换模型都没影响？**

意味着领域、调度和供应商协议分层，不保证能力完全等价。语言默认配置集中为 `gpt-6-astra / xhigh`；H3 的媒体角色、时长、数量及输出格式在适配层校验。换供应商仍需实现协议、能力映射、错误和用量处理，并重新验收。

### B. Agent 运行与可靠性

**Q09：一次自然语言请求的完整调用链是什么？**

前端提交消息和选区；Runner 创建或继续 `StudioJob`，关联 `AgentRun`；Leader 提交结构化计划，运行时推进就绪步骤并派发 Worker；Tool 调领域服务写入同一项目。保存和运行事件通过 SSE 回到界面，完成判断仍由目标和实际结果决定。

**Q10：Leader、Worker、Runner 各自做什么？**

Leader 判断目标、安排工作和后续决策；Worker 在具体范围内读取、调用工具并交回结果；Runner 管调度、暂停、消息和恢复。角色是逻辑职责，不代表每个角色必须使用不同模型或独立服务。

追问：**用了 LangGraph 或供应商原生 Function Calling 吗？** 当前是自建 Harness：语言请求发送指令与输入，本地解析结构化决定，再通过 ToolRegistry 执行。不能把接入 Responses 端点直接说成采用了供应商原生工具调用协议或托管调度。

**Q11：工单包含什么，为什么不直接给 Worker 全部聊天记录？**

`WorkOrder` 包含目标、为什么现在做、范围引用、约束、已确认决定、期望输出和验收条件，还保存工作笔记及工具轮次。这样任务边界和恢复点明确，也减少无关上下文。最新用户要求会进入后续决策，不只停留在初始工单里。

**Q12：计划依赖如何表达？怎样避免循环依赖？**

`PlanStep.depends_on` 表达依赖。Pydantic 校验步骤 ID 唯一、依赖存在、不自依赖，并通过 DFS 检测环；`PlanGraph` 只返回依赖已成功且尚未尝试的步骤。失败步骤需要明确恢复或重规划，不靠重复扫描盲目执行。

**Q13：重规划后，旧任务会全部丢弃吗？**

不会。计划可以保留仍有效的工单与动作，使用原计划身份、当前计划身份和继承动作 ID 区分归属。有效结果继续参与依赖判断，已失去归属的旧工作不能擅自推进。重规划改变安排，不代表清空成果。

**Q14：怎么判断完成？如何避免 Agent 一直做下去？**

Agent 结合原目标、最新要求、保存结果和未解决事项提出完成判断，运行时校验计划、动作及交接状态。已完成步骤后自动进入必要的后续决策；没有可推进动作时报告原因。当前没有用固定创作轮数代替语义判断，也不能承诺绝不产生无效检查。

**Q15：多 Agent 怎么并行，为什么默认四个？**

`LocalTeamExecutor` 使用线程池，默认最多四个 Worker，先认领就绪工单再提交 Future。独立镜头或素材工作可以重叠等待网络 I/O。四个是本地调度的默认上限，没有实验依据宣称它是最优并发度。

追问：**Python 有 GIL，为何还用线程？** 模型网络请求和外部媒体进程占比较高，线程能重叠等待；这不等于用线程加速纯 Python 的 CPU 密集计算。

**Q16：多个 Worker 同时写项目，锁怎么安排？**

工具区分 READ、WRITE 和 EXTERNAL 等效果。直接内容写入进入项目写通道；慢模型 / 媒体调用不长期持有项目写锁，由各服务在落盘时做短锁和当前状态校验。Repository 还有进程内锁和 SQLite 事务，职责不同。

**Q17：一个视频任务很慢，会拖住其他 Worker 吗？**

各 Worker 可以连续推进自身已保存步骤，调度器收集已完成 Future，不要求所有任务在每次模型决策后一起过屏障。存在就绪同伴时可以交还执行槽；媒体轮询使用后续可执行时间，Leader 的补充规划也可以与其他工作重叠。

**Q18：重启后从哪里继续？**

Job、Run、计划、工单、工具请求和执行结果都持久化，进程启动会整理中断状态，再继续可恢复任务。已经完成的工具结果被复用，待执行请求继续原生命周期；外部提交结果不确定则走对账。仅有内存 Future 不足以支撑恢复。

**Q19：暂停会立刻杀掉所有调用吗？**

采用协作式暂停：在下一次决策或 Tool 之前接管，已经开始的操作先完成并保存回执，再确认暂停。这样不会因为中断一个复合工具而丢失副作用。远端视频生成可能继续，暂停 Agent 与取消供应商任务是两件事。

**Q20：运行中收到新消息，怎样保证既不丢失又不重复处理？**

消息先写入 `pending_messages` 并唤醒 Runner，在既有工作交接后由 Agent 判断意图。只有新计划 / 用户输入交接成功才确认移除对应前缀，新到消息留在队尾。交接失败仍保留消息和原任务，避免“界面显示收到了，执行却没应用”。

**Q21：哪些错误可以重试？**

纯语言连接失败使用同一任务，默认按 3、8、20 秒有限退避，暂停或新消息可提前唤醒。上下文超限要先重编输入，不能原样重发；参数错误先修参数；媒体提交未知先对账。重试对象是失败的决策或明确步骤，不是整条制片流程。

**Q22：视频轮询也要每次问模型吗？**

不需要。明确类型化回执证明同一媒体任务只有一个机械后续动作时，执行器可以保存并推进准备、提交、轮询等生命周期。是否返工、改创意、采用候选和怎样恢复歧义仍交由 Agent 决定。

**Q23：模型调用了不存在的工具，或者工具执行后输出校验失败怎么办？**

注册表返回分阶段的结构化错误，区分找不到工具、入参错误、执行异常和输出校验失败。最后一种尤其重要：handler 可能已经成功写入，回执会保留已有工件并提示先查结果，避免为了修输出适配而重复写入或生成。

### C. 上下文、工具协议和 Skills

**Q24：每次模型到底看到了什么？**

主要是原始要求、当前目标、最新补充、当前任务范围、必要工件、近期状态 / 错误、未解决决定和工作笔记。完整 Trace 独立保存，既不把整份项目无限拼入提示，也不把全部历史当作当前事实。

**Q25：258k 上下文预算怎么计算？**

这是产品的请求预算。使用随包携带的 o200k 编码计算文字，满足：文字输入＋输出 / 推理预留＋1,024 封装预留＋视觉余量 ≤ 258,000。输入包含指令和实际序列化内容，不能用字符数或仅聊天正文代替。

**Q26：为什么 200k 开始整理到 160k？**

提前整理给下一次工具结果和模型输出留空间，并避免刚整理就再次触线。代码还根据输出和图片预留收紧实际阈值。这些是当前工程策略，不是声称供应商在 200k 存在某个固有性能拐点。

**Q27：所谓上下文压缩，具体丢了什么？**

主要使用可恢复的外置：先把原始 payload 保存到 SQLite，再将较大的结果块替换为 `context_ref` 和 JSON pointer，并保留必要索引。模型可通过 `agent.read_context` 分页回读；Trace 包包含原文，因此不能简单理解为把历史总结后删除。

**Q28：如果用户原始要求本身就过长，能直接截断吗？**

原始要求、当前目标和运行协议不属于可随意移出的候选。可恢复块整理后仍超限，就返回明确错误，要求缩小任务或读取范围，避免发送超限请求。Provider 边界还有预算检查，防止工具内部的嵌套语言请求绕过限制。

**Q29：这是不是 RAG？回读旧上下文是否会用错版本？**

核心是按工件 ID、JSON pointer 和范围精确读取，没有依赖向量召回。快照能回答“当时读到了什么”，不能证明对象现在没变；执行修改前仍需读取当前对象并校验来源。可恢复性与当前性要分开处理。

**Q30：怎样避免一个 Worker 读十个镜头，却只记住最后一个？**

读取观察按具体对象和规范化读取范围区分，同一范围重复读取更新原记录，不同镜头、素材任务切片及分页可以同时保留。仅按工具名覆盖会把不同读取误判为重复，导致反复回读和遗漏依赖。

**Q31：工具很多，会每轮注入所有完整 Schema 吗？**

保留完整简述目录供发现，详细 Schema 按角色起始需要及后续请求加载，并记住已加载定义。目录可见、Schema 已加载、实际已执行是三种状态。不能把“本地注册了很多工具”直接等同于每轮输入全部参数定义。

**Q32：为什么要把 Skills 分层？**

运行职责和输出协议、角色知识、任务方法、体裁补充、Provider 编译及上游来源承担不同职责。当前 27 项方法通过 manifest 映射到角色 / 阶段片段，共用内容按来源去重，避免每次把所有方法和上游原文堆进去。

**Q33：Skill、Tool、Style 有什么区别？**

Skill 提供如何制作和判断的方法；Tool 是能执行的读写、生成和媒体操作；Style 是项目的审美方向。方法提到某个外部软件，不代表系统已接通该软件，其执行条件通过 requirements 明示，也不把 Skill 当成固定审批流程。

**Q34：模型看图时，如何记录来源和计算 Token？**

附图绑定具体候选、用途和观察尺寸，只发送给需要的决策；图片在请求边界编码，不把 Base64 当历史文字。当前每图预留 8,192 tokens 作为保守余量，供应商真实视觉用量另存，二者不能混为精确计费值。

**Q35：流式 JSON 不完整，怎么展示又不污染正式内容？**

从真实增量中投影剧本、动作等创作字段，作为带调用身份的生成中草稿；完整响应解析、类型校验并通过业务保存后才更新正式内容。有限兼容只处理能无歧义恢复的完整结构，不猜补真实截断的参数，更不提前执行半条 Tool。

### D. 数据一致性与存储

**Q36：三方合并的核心规则是什么？**

以读取时 `base`、本次 `proposed`、数据库当前 `saved` 比较：本次没改的字段取 saved；数据库没改的字段取 proposed；双方都改则继续按对象递归。同一标量冲突保留 saved，并记录冲突位置，所以晚到的模型文本不会覆盖已保存编辑。

**Q37：数组怎么合并？按下标会有什么问题？**

对象数组优先按稳定的 `id / shot_id / character_id` 合并，分别处理新增、删除和变化。按下标会在插入、删除后把两个不同镜头当成同一个对象。重排也考虑当前存储是否已改顺序；没有可靠身份的数组不伪造逐项对应关系。

**Q38：后台保留 saved，前端又有合并按钮，会冲突吗？**

用途不同：后台保护已经生效的当前内容；过期编辑 API 返回 409 后，前端保留未保存草稿，由用户显式将本地变化重放到最新内容再保存。它不是无冲突的多人 CRDT，也不能声称所有修改永远自动合并。

**Q39：为什么不统一用整个项目版本号判断视频输入失效？**

别的镜头修改不应阻断已准备的当前生成组。系统核对所选组的镜头、引用、时窗及相关制作来源；组内实际变化才要求更新。剧本、制作规格等明确依赖仍需校验，不能把局部判断理解成忽略所有上游变化。

**Q40：多集共享资产怎样避免复制出多份真相？**

资产和参考图集归根项目，各集保存独立内容，读取时装配共享资产。子集保存先比较归属归一化后的共享内容，真正变化才更新根项目并发事件。修改一集正文无需反复重写根资产，也不会因旧副本覆盖另一集的共享修改。

**Q41：跨集重新定位媒体，如何保证只成功一半时不会损坏项目？**

先在事务外复制和探测文件；进入短事务后重新读取当前项目族，同步各集、Take、独立记录路径和资产事件。任一数据库操作失败整体回滚。测试使用真实 SQLite 触发器在后段制造失败，检查前面的写入也没有提交。

**Q42：文件系统与 SQLite 能放在同一个事务里吗？**

不能。这里通过准备文件、校验、数据库原子提交和失败清理组织操作，避免长文件 I/O 占住数据库锁。它没有跨文件系统的分布式事务保证；异常退出后的临时文件和媒体缺失仍要通过恢复机制处理。

**Q43：存储优化为什么没有继续拆时间线？**

测量发现时间线占比仅 0.76%，大头是生产文档及历史，主要时间花在复制和验证。先拆高频记录、跳过无效写入、减少重复快照，正文保存 P50 降低约 36%–41%。继续逐片段拆表会增加合并和迁移复杂度，当时收益依据不足。

**Q44：独立记录迁移后，旧项目还能读取吗？**

第 12 次迁移原子地把嵌入的导出 / 审阅记录移入独立表，已有独立新状态优先；默认读取再回填旧接口字段。普通旧快照不能覆盖或删掉新记录。列表用 `(created_at, id)` 游标处理同时间记录，审阅接受与正文修改共同提交。

### E. 媒体、引用与剪辑

**Q45：正文里的 @ 引用只是把名字显示成蓝色吗？**

它是结构化绑定：对象 ID、具体媒体 ID、正文所属字段和字符范围、用途、时段位置等共同定义关系。预览和生成输入都读取这份关系，换图、解除引用和正文回写同步处理。`GENERATION` 与 `EDITORIAL` 区分模型参考和剪辑图版。

**Q46：正文编辑后引用位置怎么办？中英文、emoji 会错位吗？**

前端编辑器从正文和引用节点重新提取绑定范围，按 Unicode 字符计数，与 Python 一致，不能直接用 JavaScript UTF-16 下标。Agent 新建引用也可传唯一原文锚点，重复时加前后文定位；锚点含糊或与显式偏移冲突时拒绝猜测。

**Q47：为什么不直接把“一次生成”等同于“一个镜头”？**

一个生成组可能包含多个镜头，同一个 Take 还可能在时间线上重复使用。需要分别表达镜头设计、生成组、候选 Take、镜头源窗和具体 TimelineClip。否则很容易把第二镜错误播放成源文件开头，或把一次替换传播到所有使用位置。

**Q48：设计时长、素材时长和成片时长有什么区别？**

设计时长表达叙事意图；素材时长是本镜可用的源范围；成片采用时长由裁切和速度决定。正向常速映射可写为：`源时间 = 源入点 + (成片时间 − clip 起点) × speed`。例如源窗 4 秒、2 倍速，成片占 2 秒；改设计时长不会自动改变已有视频。

**Q49：单镜头剪辑如何同步全片？**

先按指定使用位置投影本镜画面、关联声音和字幕，局部时间从 0 开始。保存时只替换该范围，计算 `delta = 新采用长度 − 旧采用长度`，将后续片段和字幕顺移。跨镜头配乐保留原长度并提示检查节拍；重复采用须明确 anchor clip。

追问：**为什么不把过滤后的局部时间线直接覆盖全片？** 因为局部视图并不包含其他镜头、跨镜声音及所有轨道设置，整份覆盖会删除范围外内容。

**Q50：同一源片里包含其他镜头，怎么防止裁切越界？**

保存时根据当前正式采用关系重建本镜允许的源区间，验证 `trimStart`、采用长度和速度，不能相信客户端声明的更宽范围。多个不连续区间不能当作一个大区间跨越。源文件存在并不意味着它的所有时间段都属于当前镜头。

**Q51：为什么 H3 需要专门的编译层？**

领域分镜描述人物、动作、对白和引用，而供应商要求特定媒体角色、排序和请求格式。编译层将二者映射，并在调用前校验时长、文件、媒体数量、首尾帧与参考模式的互斥等条件。Provider 限制只影响实际请求，不应限制整个项目资产数量。

**Q52：怎样避免重复提交同一个视频任务？**

同一请求指纹有推进锁，持久化表保存已确认的远端任务 ID，重复推进优先复用；提交前也保存准备状态。显式创作一个新候选仍是新的任务意图。幂等重试与“用户真的想再生成一次”不能混为一谈。

**Q53：为什么要单独设计 SUBMIT_UNKNOWN？**

“请求超时”只说明本地没得到明确结果，远端可能已受理。独立未知状态能阻止盲目重发，并携带时间、输入及身份进行对账。空列表可能受分页、过滤或可见性影响，不能证明未提交；证据不足就继续保留未知。

**Q54：取消和提交并发时，如何避免状态反转？**

区分 `PREPARED` 与 `STARTED`：尚未开始远端提交可本地取消，提交前再次检查；已经开始或结果未知就不能宣称本地取消成功。远端轮询与取消共享推进通道，防止较早取得的运行状态覆盖已确认取消。实际可取消阶段还受当前 H3 协议约束。

**Q55：只换画面为什么要单独建协议，直接换文件不行吗？**

需要明确保留哪份声音、哪个使用位置和什么长度，并核对这些来源仍然有效。`PICTURE_ONLY` 将补拍范围绑定到当前正式分镜和采用位置；采用时要求 `KEEP_CURRENT_AUDIO`，替换目标画面并静音新片，其他片段和字幕保持，避免重新装配全组。

**Q56：人物和道具的跨镜头连续性如何处理？**

使用共享对象、精确参考媒体、动作 / 道具出入状态，以及前一处实际采用的边界作为输入，检查具体候选。纯粹在全片上顺移位置不应误使源内容失效，但媒体、源窗或前镜边界真的变化就要重查。这能约束生成，不能保证模型绝不漂移。

**Q57：视频 QA、声音和字幕分别怎么验证？**

抽帧适合检查构图、人物和动作状态；转写、对齐和音频分析处理对白及声音时间，不能看静帧就声称听过声音。时间映射需区分源片、镜头局部和全片坐标，观察记录保存实际解码 PTS。文件解码成功也不等于表演、自然听感或口型全部合格。

### F. 前端、状态同步与导出

**Q58：前端如何划分状态？为什么不全部塞进一个全局 Store？**

工作台用 React state / Context 组织项目、范围和页面；编辑器复用既有 Zustand store，分开内容模型、播放 / 选择会话、保存状态和撤销历史。后端保存正式内容，本地仅保留交互态和草稿，不再维护另一套可独立生效的 LTX 项目。

**Q59：为什么使用 SSE？断线怎么办？**

用户指令通过 HTTP 提交，状态主要从服务端流向页面，SSE 适合这个方向。事件先存 SQLite，自带递增 ID；前端携带 `after` 游标重连、按 ID 去重排序，并用活动查询兜底。使用 fetch 读取流，便于携带 Bearer 头和 AbortSignal。

追问：**这是不是 exactly-once 推送？** 不是。连接可以中断或重放，可靠性来自事件落盘、游标和重复消费处理；断开页面连接也不会取消后端 Job。

追问：**后端使用了消息队列吗？** 当前 SSE 从持久化事件表按游标读取，空闲时等待再查；没有 Redis Pub/Sub 或 Kafka。这个简单实现符合当前本地用户规模，多客户端扩展时再测数据库轮询和推送成本。

**Q60：请求乱序、切换项目和后端断线如何防止 UI 倒退？**

刷新结果校验当前项目 / 活动通道；项目快照比较更新时间和剪辑修订，独立导出记录单独合并。切换项目清理连接和定时器。后端断线后保留已经挂载的工作台，只更新连接提示，避免未保存文本因卸载组件而消失。

**Q61：用户保存中继续编辑，保存回包会覆盖新输入吗？**

保存队列串行提交，每次捕获一个快照及预期修订，回包只确认已提交快照。若当前模型又变了，继续显示未保存或再提交最新状态。自动保存可以 drain 队列，显式局部保存可以只确认一次快照；关闭会话后不把回包应用到其他页面。

**Q62：有 IndexedDB 草稿，为什么仍说后端是唯一内容真相？**

草稿只承担未保存修改恢复，不直接成为 Agent 和导出的输入。编辑器按项目、集、时间线、镜头及使用位置建立草稿键，并保存 base、current、revision；恢复时校验当前正式内容。所有者标记防止旧会话晚到的写入破坏新草稿。

**Q63：Agent 更新剪辑后，撤销会不会把 Agent 的修改也撤掉？**

刷新不仅替换内容，还基于新内容重放原撤销 / 重做快照的局部差异，尽量保留普通撤销语义。播放位置、选择和打开的时间线按仍有效的对象保留。存在未保存冲突时先保留草稿，不静默覆盖；这也不构成用户可见的版本分支系统。

**Q64：导出中继续编辑，会导致成片前后来自不同版本吗？**

导出先校验已保存 revision，固定该次项目输入；媒体尺寸等慢检查在锁外完成，启动前重新核对修订。随后渲染使用固定输入并保存 `editorial-input.json`，导出状态独立更新。用户之后的编辑形成新的当前内容，不混入已启动的渲染。

**Q65：导出链路怎样与编辑器保持一致？**

Python 调用构建好的 Node CLI，共用项目模型和 LTX 导出基础；画面生成 FFmpeg 滤镜，音频单独解码混合，之后封装并生成 SRT / 字幕版。裁切、速度、静音和音画关联要在预览与导出两边对齐，实际媒体检查验证一致性；未支持的效果要明确拒绝。

### G. 工程验证、结果与个人表达

**Q66：Electron 与本地后端的边界如何设计？**

主进程管理窗口、文件和 Python 子进程，preload 通过 `contextBridge` 暴露明确 API；窗口启用 `contextIsolation`、关闭 `nodeIntegration`。HTTP 统一经 `backendFetch`，桌面请求使用本地 Bearer token。共享 IPC Schema 提供类型契约，但类型声明本身不等于所有输入都已运行时校验。

**Q67：AI 输出不确定，这种项目怎么测试？**

用显式 Fake client 提供可控的模型 / Provider 响应，结合真实 Repository、SQLite 和 TestClient 验证状态机。并发测试用 Event 控制时序，事务测试用触发器制造失败，媒体测试用真实 FFmpeg。另有前端逻辑、原生交互和真实制片验收，各自回答不同问题。

追问：**为什么不只测试“调用成功”？** 成功状态不足以证明没有丢正文、重发视频或污染声音；关键断言应检查最终内容、提交次数、保留范围和实际媒体。

**Q68：Trace 与普通日志有什么区别？**

Trace 把 Job、Run、工单、工具和模型调用关联起来，保存输入输出、具体动作、来源、模型配置、时间和供应商用量，线程间通过 ContextVar / 复制上下文传递关联。完整记录留作诊断和导出，界面与模型只取所需视图；缺失 usage 保持未知。

**Q69：项目怎样打包、迁移和验证工程契约？**

桌面包包含应用和所需运行时，项目包另收集各集内容、Take、媒体和 Trace，重写可移植路径，不携带凭据或自动续跑原远端请求。CI 配置检查 TypeScript、Pyright、OpenAPI 差异、后端测试及前端构建；实际原生验收以 macOS arm64 为主，配置存在不等于各平台都已验收。

追问：**备份数据库就能搬走项目吗？** 媒体是外部文件，仅复制数据库不完整；项目包按清单收集媒体，缺失文件明确报告，远程 URL 不擅自下载。应用包与用户项目包也有不同的职责和许可范围。

**Q70：怎样报告性能、耗时和成本，才不容易被追问击穿？**

明确版本、数据集、采样次数和指标边界。保存 P50 不等于端到端生成提速，工具耗时可能包含模型耗时，重叠时不能相加作为墙钟。供应商 usage 与本地 Token 估算分开，失败和返工也计入，缺失费用不能按零补齐。

**Q71：当前最大的不足是什么，下一步优先做什么？**

真实短片仍需大量语言调用和检查，跨镜头连续性与主观视听质量也不稳定。优先减少重复读取、失效误判和无必要交接，完善有明确范围的局部返工，并用同条件样本测效果。当前效率目标有未达项，不把已经停止的实验描述为优化完成。

**Q72：面试官问“这些都是你做的吗”，怎么回答？**

按实际职责区分：上游提供了什么、本人实现 / 修改了什么、怎样验证、合作或 AI 辅助到什么程度。可以说“我重点负责 X，复用了 Y，最深入处理的是 Z”，再展开对应代码和失败案例。仓库不能证明个人分工，未参与部分不要套用“全部独立研发”。

### H. 改变条件后的架构深挖

以下是基于当前设计的扩展思路，不是已交付能力。

**Q73：如果支持多人同时协作，现有方案够吗？**

不够。当前依赖单机运行、已保存内容优先和显式草稿合并。多人环境需要服务端身份与协作边界、细粒度修订 / 冲突语义；文本可能评估 OT / CRDT，但时间线剪点和媒体副作用不能直接套用文本算法。应先确定协作对象和冲突规则。

**Q74：如果项目大十倍，或者 Worker 增加到一百个呢？**

先测请求体、序列化、锁持有和媒体吞吐。内容侧可将历史正文移出当前编辑热路径、做按需加载；执行侧若跨进程 / 多机，需要持久队列、任务租约、原子认领和共享媒体存储。当前进程内锁不能替代分布式协调，单纯增大线程池会放大冲突和供应商限流。

**Q75：为什么不直接减少 Token，或者换更便宜的模型？**

减少某段文字不等于完整请求净减少，也可能增加工具发现和回读。先定位重复输入、回执和交接成本，再对固定任务比较完整用量、质量、返工及墙钟。换模型是可评估方向，但项目当前保持原模型；稳定前缀有利于缓存利用，实际命中仍要看供应商 usage。

**Q76：重新做一次，你会改变哪些工程决策？**

保留单一内容真相、可恢复任务和精确媒体引用，这些决定直接影响正确性。优先把较大的 Service / ProductionManager 按领域和运行职责继续拆分，提前建立“只换画面、重复采用、提交未知、保存中编辑”的回归场景，减少依靠完整制片才暴露问题的成本。

## 7. 最后复习：四条连续追问路线

- **数据一致性：**旧结果覆盖怎么办 → 三方合并 → 数组身份与删除 → 同字段冲突 → 事务与文件系统边界。对应 Q36–Q42。
- **Agent 可靠性：**如何持续运行 → 并发和锁 → 暂停 / 新消息 → 重启 → 重试 → 提交结果未知。对应 Q09–Q23、Q52–Q54。
- **剪辑正确性：**镜头与 Take 的关系 → 三种时长 → 局部保存和源窗 → 只换画面 → 声音验证 → 导出一致性。对应 Q47–Q57、Q64–Q65。
- **工程判断：**为何保存慢 → 为什么不拆时间线 → 如何采样 → 微基准能证明什么 → 真正制片瓶颈 → 下一步怎么验证。对应 Q43–Q44、Q70–Q71、Q74–Q76。

最值得记住的一句总结：**这个项目把模型生成接入可持续编辑的项目系统，主要工程价值在于长任务恢复、并行修改保护和媒体采用关系的正确性。**
