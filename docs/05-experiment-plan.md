# 固定输入实验与验收方案

## 1. 原则

- 本文是实验协议，不代表已经执行；
- 所有真实生成都记录 Provider、模型快照、价格和调用量，但预算不作为质量实验的主要限制；
- 先用 Mock 排除工程错误，再用代表性短镜、单镜多候选和完整短剧逐级验证；这个顺序服务于归因，不是为了少花额度；
- H3 是当前唯一视频生成模型；实验比较 H3 内部路线，不做视频模型选型。GPT Image 2、Azure 与其他音频/后期环节仍按质量增益决定是否启用；
- 闭源平台不参与生成或对照，只提供公开方法上的启发；
- 每次只比较一个主要变量；
- 失败不盲目重新 POST：先确认 Provider 是否已经创建任务；
- 不用复杂安全或密码学机制，只保存足够复现和对账的普通工程记录。

### 1.1 样本量与停止规则

- 每个条件先生成 5 个独立样本，只用于发现明显问题；可能入选的路线至少扩展到 10 个有效样本；
- 若候选路线结果接近或波动较大，每次增加 5 个样本，最多到 20；仍不稳定则结论记为 `UNKNOWN`，不强行选赢家；
- 普通镜头首轮生成 3 个 Take；对白、双人、手部道具和动作接续等高风险镜头首轮生成 5 个；
- 自动补充候选直到至少取得 2 个通过全部硬门槛的 Take；同一请求方案累计 10 次仍无法稳定通过时，停止抽卡并修改提示、参考、分组或音频路线；
- 默认路线至少有 10 个有效样本，严重失败率不高于 20%，综合硬门槛通过率不低于 70%，严格对白逐字正确率不低于 80%；
- 最终入选成片的每个 Take 必须 100% 通过全部硬门槛，路线统计阈值不能豁免单个成片错误。

严重失败包括：身份混淆、明显坏脸坏手或人物融合；空间/动作/服装/关键道具状态错误；锁定台词错漏、数字/否定词或说话人错误；明显口型错位或静默角色错误动嘴；坏帧、缺音轨、错误时长或画幅。

## 2. 固定短剧样本

已锁定美术方向：**真人都市短剧**。本样本优先暴露真人脸、肢体表演、服装与空间连续性、中文对白、声线和口型问题；漫剧不作为首个质量标杆。

首版验收范围已锁定为**单集完整闭环**。本实验只要求该集内部的角色、场景、道具、动作、声音和叙事连续；所有批准资产仍保留稳定 ID 与版本，供后续跨集实验复用。

首个固定测试剧本已锁定为真人都市悬疑短剧 **《别相信我》**。当前角色、场景、道具、五句台词和八镜结构共同构成基准输入；任何内容修改必须建立新的 `ScriptVersion`，不得静默覆盖基准。

首版语言已锁定为**普通话中文**。本轮台词、声音、口型、STT 与字幕验收均使用普通话；方言和多语言不进入首版实验矩阵。

### 2.1 故事目标

验收范围锁定为 45–60 秒、8–10 个最终剪辑镜头；本固定样片约 50 秒、8 镜。题材为都市悬疑，两名角色，一个关键道具，一个主要场景。它有意覆盖身份、空间、道具、动作、声线、多人对白、画外音和反应镜头。

### 2.2 角色

- 林夏：28 岁，短黑发，米白风衣，克制但警觉；稳定角色/声线标识 `S1`；
- 周衡：32 岁，深灰西装，左眉有浅疤，表面平静；稳定角色/声线标识 `S2`。

### 2.3 场景与道具

- 深夜便利店，冷白顶灯，玻璃门在画面右侧，收银台在左后方；
- 一只红色旧录音笔，初始在周衡右手，随后放到柜台，最后被林夏拿走；
- 门外有雨，玻璃上有蓝色霓虹反光。

### 2.4 锁定台词

1. 林夏：“你说他十点离开，可监控里，十点零三分他还在这里。”
2. 周衡：“监控会骗人。”
3. 林夏：“人也会。”
4. 录音笔中的林夏声音：“如果你听到这段话，别相信我。”
5. 周衡：“现在，你还信自己吗？”

数字、否定词“别”和说话人归属都是硬验收点。

### 2.5 建议镜头

| 镜头 | 时长 | 画面/动作 | 声音 | 连续性考点 |
| --- | ---: | --- | --- | --- |
| 1 | 5s | 雨夜便利店外，镜头推近玻璃门 | 环境音，无对白 | 9:16 氛围、空间建立 |
| 2 | 8s | 林夏近景，视线越过镜头看周衡 | 台词 1 | 正脸口型、专名数字 |
| 3 | 6s | 周衡反打，右手握红色录音笔 | 台词 2 | 轴线、道具右手、声线 S2 |
| 4 | 5s | 林夏更近特写，轻微推镜 | 台词 3 | 快短句、情绪递进 |
| 5 | 8s | 录音笔被放到柜台，指示灯亮 | 录音台词 4，人物闭嘴 | 手部、道具位置、画外音/设备音 |
| 6 | 6s | 林夏听见自己的声音，神情变化 | 环境音、呼吸 | 反应镜头、身份稳定 |
| 7 | 7s | 周衡半侧脸，玻璃反光掠过 | 台词 5 | 侧脸口型、S2 声线 |
| 8 | 5s | 林夏拿起录音笔转身出门 | 门铃/雨声，无对白 | 道具换手、动作收束 |

H3 支持模型内多镜描述，可将相邻镜头合并生成，也可逐镜生成。实验应记录“模型内多镜”与“后期拼接”的差异；最终仍由统一时间线完成整片。

## 3. Phase 0：Mock 工程全链路

### 输入

使用固定 JSON、占位图、合成色块视频和程序化音频，不调用任何 AI Provider。

### 必须走通

1. `IDEA_EXPANSION` 与 `SCRIPT_LOCKED` 两种输入；
2. 规划模型的输出 schema 用固定 fixture 替代；
3. ProjectBible、ShotPlan、ExecutionPlan、ReferencePlan、Take 和 TimelineManifest 的版本关系；
4. 每镜生成 2 个 Mock 候选并选择；
5. 单镜失败、重试、取消和恢复；
6. 视频/音频/字幕统一时间线；
7. 9:16 MP4 与 SRT 导出；
8. 修改台词后只失效相关音频、镜头和字幕；
9. 进程重启后仍能继续未完成任务；
10. 任务提交、轮询、恢复和计费记录完整，不因放宽预算而允许重复提交或失去可追踪性；
11. 图像、外部音频和口型修复三个环节都可以关闭，且不破坏主流程。

若执行双底座 Spike，同一套 fixture 分别在 LTX Desktop 与 Jellyfish 中运行：LTX Desktop 路线必须把项目元数据移出 `localStorage`、用 Mock Adapter 替代 LTX 专用 contract，并验证预览/导出一致性；Jellyfish 路线必须补最小 Take/时间线/FFmpeg 层。二者都必须通过第 1–11 项，不能用各自已有能力降低验收线。

通过 Phase 0 后才讨论真实调用。

## 4. Phase 1：自建执行路线短名单

先用同一份 `ShotPlan` 和 Mock 媒体验证四种路线是否能被数据模型表达，而不是先绑定模型：

| 路线 | 典型输入 | 何时值得进入真实探针 |
| --- | --- | --- |
| Direct audiovisual | 文本/已有参考直接生成视听镜头 | 作为判断图像/音频增强是否真正增益的基线 |
| Image-guided | 定妆/首尾帧 → 视频 | 从首轮参与；质量更好，或不劣且一致性/控制更强即可采用 |
| Audio-driven | 录音/TTS 主音频 → 视频或口型 | 与原生音频直接比较；按最终台词、声线和口型质量选择 |
| Hybrid repair | 合格主体镜头 + 局部图像/声音/口型修复 | 局部修复后总体质量更好或更稳定即可采用 |

短名单规则：Direct 是对照组，不是默认赢家。GPT Image 辅助若有合理的质量增益预期，就与 Direct 从同一批代表镜头开始比较；只要结果更好，或质量不劣且一致性、可控性与稳定性更强，就进入首选路线。路线步骤多少和调用成本只做次要记录。

结论写入 `RouteEvidence`。同一模型快照、美术风格和镜头类型后续直接复用已胜出的路线，不要求每个项目重复证明 GPT Image 2 的价值；模型或工作方式发生实质变化时再复验。

## 5. Phase 2A：GPT Image 2 图像增强基准

资产来源不限定为 AI：正式产品允许素材库导入、用户上传、GPT Image 2 新生成，以及上传/导入后由 GPT 修整。固定实验只锁定最终批准的 `AssetVersion`；为保证对照清楚，可以先用 GPT Image 2 完成受控资产，不要求在实验前实现内置素材库搜索。

本节从首轮执行，不需要等待 Direct 路线先失败。目标是判断 GPT Image 2 的定妆、场景锚点、素材修整和关键帧是否提高下游视频质量，或在画面质量不劣时提高一致性与可控性。通过后可成为全部适用镜头的默认前置，也可依据镜头类型选择覆盖范围。

### 变量

使用同一角色说明与参考：

- A：每镜独立文生图；
- B：角色定妆图作为 edit 输入；
- C：角色定妆 + 场景锚点 + 上一镜状态作为 edit 输入；
- D：Responses 多轮编辑保持同一上下文。

### 图像覆盖样本

- 林夏正面、侧面、过肩、全身；
- 周衡正面、半侧面；
- 两人同框；
- 录音笔在右手、柜台、左手三种状态；
- 同一便利店正打和反打。

### 通过线

- 无角色混脸或服装互换；
- 主要面部特征在六张图中稳定；
- 道具状态能按指定改变而不改外观；
- 正反打仍像同一空间；
- C 或 D 的视觉质量不低于 A，并在身份、空间、道具、构图或可重复性中至少一项更强。

每组至少五次并打乱盲评，不以单张最好结果下结论。下游固定使用镜头 2、3、5、8，分别覆盖正脸、侧脸/人物与道具、手部道具状态和动作接续；还要比较由批准图像驱动的 H3 视频结果，避免“静帧更美、动态反而更差”。只有动态质量不低于无图路线，并在身份、空间、道具、构图或稳定率中至少一项明显提高，GPT Image 路线才通过；最终覆盖范围按镜头类型写入 `RouteEvidence`。

## 6. Phase 2B：H3 视觉路线与连续性

### 合法路线矩阵

| 条件 | 输入 | 主要验证点 |
| --- | --- | --- |
| D | Direct：结构化文本提示 | 无视觉参考时的画质、表演与指令遵循基线 |
| F1 | Frame：批准首帧 | 构图、人物位置和动作起点 |
| F2 | Frame：批准首帧 + 尾帧 | 动作终态、剪辑点和两端约束下的动态自然度 |
| R | Reference：角色/场景/道具图片或必要视频 | 身份、空间、道具外观和跨任务复用 |

Frame roles 与 Reference roles 不得放在同一次 H3 请求中。`CapabilityValidator` 在创建付费任务前拒绝非法组合，并用 Mock/单元 fixture 验证；不通过真实调用测试已知非法请求。

### 代表镜头与扩展顺序

先比较镜头 1、2、5、8：分别覆盖空间建立、正脸人物、手部/道具状态和动作接续。每个条件保持 `ShotPlan`、台词、时长和主提示语义一致；得到初步路线后再扩展完整八镜，不根据单次最好结果决定路线。

连续性至少比较：Direct、上一镜批准尾帧作为下一镜首帧、由批准资产生成/修整的连续性首帧，以及角色/场景/道具 Reference。记录身份、空间、道具状态、动作方向、轴线/眼线、坏帧、动态自然度和镜头指令遵循。

### 固定分辨率与提示编译

PoC 的全部 H3 请求固定为 768P，不测试 1080P/2K，也不把分辨率加入实验矩阵。Context-IR 不进入完整笛卡尔积，只在代表样本上与 GPT-5.6-sol 自编译提示比较，锁定相同 `ShotPlan`、对白和参考素材。Context-IR 成功只算提示编译成功，不算视频成功。

最终结论按镜头类型写入 `RouteEvidence`，允许空间建立、对白近景、道具特写和动作衔接采用不同 H3 路线。

## 7. Phase 2C：H3 音频、口型与字幕计时探针

H3 是当前唯一视频引擎，本节必须执行。先用 768P、4–6 秒代表镜头确认可归因的能力，再扩大到完整镜头和整片；不设置逐批预算释放。

路线按问题逐级展开：先测 H3 原生音频；只有跨镜声线漂移时增加 `reference_audio`；台词、声音或控制仍不合格时，再比较真人录音与外部 TTS。Azure 只是外部 TTS/STT 的可替换实现。外部口型模型不进入本阶段，只有前三层仍无法通过时才另开实验。

### H0：无对白运动基线

- 一人正脸，轻微转头和推镜；
- 验证 9:16、时长、帧率、原生环境音和基础稳定性。

### H1：单人中文原生对白

- 台词：“监控会骗人。”；
- 同一输入连续五次；
- 检查逐字、声线、口型、表情和音频是否都有输出。

### H2：数字与否定词

- 台词 1 与台词 4 分开测试；
- 硬检查“十点零三分”和“别相信我”；
- 这是决定原生音频能否承担锁定剧本的关键门槛。

### H3：声线跨任务

- 使用同一角色 reference 和固定 speaker ID，分别生成三段不同台词；
- A：无 audio reference；
- B：reference audio 只要求迁移声线并说新台词；
- C：reference audio 要求直接复用原信号；
- 分清“复用声音内容”和“复用声线属性”。

### H4：双人说话人分配

- 两人同框或正反打，包含 S1/S2 各一句；
- 检查声音是否串角色、是否同时动嘴、静默角色是否闭嘴。

### H5：侧脸与快短句

- 林夏台词 3，周衡台词 5；
- 覆盖侧脸、推镜、短句和情绪变化。

### H6：不同视觉路线下的音画回归

- A：上一镜尾帧作为 `first_frame`；
- B：角色/场景 reference，不传首帧；
- C：用批准的 GPT Image 2 或已有素材生成兼具上一镜动作终态与角色特征的首帧，再走 frame route；
- 除动作接续、角色身份和动态质量外，复查同一句对白在三类视觉输入下的说话人、口型和声线是否退化；成本仅记录。

### 字幕时间与台词 QA

- H3 原生音频与真人录音：用可替换 STT 生成转写和词级时间候选；
- 外部 TTS：优先使用其 word-boundary；
- Provider 若返回经过实测可靠的对齐信息，优先采用；
- 自动时间不准时允许人工微调，最终 cue 回写 `TimelineManifest`；
- STT 结果只用于筛查和对齐，最终台词以锁定文本、人工听审和人物画面共同判定。

### H3 路线通过线

原生音频要成为 **H3 路线内部** 的首选音频方式，需同时满足：

- H1 五次至少四次逐字正确且口型无明显错位；
- H2 的数字和否定词不发生语义错误；
- H3 跨镜声线达到盲听多数认为同一角色；
- H4 说话人归属正确；
- 环境音/音乐不会持续盖住对白；
- 单镜合格候选平均不超过预先约定的生成次数。

最终入选 Take 的锁定台词必须逐字正确；“五次至少四次”衡量路线稳定率，不允许用一个错字版本进入成片。

若台词质量好但声线不稳，进入“原生对白 + 声线 reference”路线；若台词仍不稳或需要更强声音控制，再比较真人录音与外部 TTS 主音频；前三层都不能同时满足台词、声音和口型时才评估后期口型修复。

## 7.1 暂缓：LTX-2.x 独立模型探针

本节不属于当前实验计划。当前视频生成只使用 H3，采用 LTX Desktop 代码底座也不触发 LTX 模型测试。只有未来明确重新开放视频模型候选时，才使用届时可合法获得的当前 LTX-2.x 快照，并先确认模型 License、目标硬件和 checkpoint/API 路径；不默认沿用 Desktop `v1.1.0` 的 LTX-2.3。

使用与 H3 相同的代表镜头与锁定台词，至少比较：

- 文本直出视听视频；
- 由批准角色/场景/首帧驱动的视频；
- 外部批准音频驱动；
- 对已生成片段做局部 Retake；
- 前向/后向 Extend 后的身份、动作、声音与剪辑点；
- 中文逐字正确率、声线跨任务、多人说话人和口型；
- 同输入重复生成的严重失败率和稳定率；
- 当前本地硬件上的生成时长、显存/内存与磁盘占用。

若未来重启本节，先在模型官方 pipeline 上确认能力，再确认 Desktop 是否暴露了同一能力，避免把 UI 缺口误判成模型缺口，也避免把模型仓库宣传误判成 Desktop 已实现功能。届时再与基线按同一盲评表比较。

## 8. Phase 3：H3 路线的连续性与分组

使用固定八镜脚本比较：

- A：8 个独立 H3 任务；
- B：相邻两镜分为 `1+2 / 3+4 / 5+6 / 7+8` 四个 H3 多镜任务；
- C：按表演段落分为 `1 / 2+3 / 4+5 / 6+7 / 8` 五个任务；
- D：8 镜独立，并在适合时用上一镜批准尾帧或由批准资产生成/修整的连续性关键帧约束下一镜。

B/C 中每个任务总时长不得超过 H3 的 15 秒窗口，Prompt 使用明确的 `[Shot N] At ...` 切镜时间；超限组合在规划阶段拆开。

记录：

- 角色、服装、空间、道具、动作和声线的严重错误数；
- 模型内切镜是否按时间点执行；
- 单镜画质、表演和音画同步是否因分组下降；
- 单个局部错误是否迫使整个 15 秒任务重做；
- 每个合格编辑镜头的平均调用量和成本，作为运营指标；
- 后期裁切、换 Take 和节奏调整的可控性。

预期不是“分组越大越好”。分组只有在身份/空间/动作/声线连续性或表演明显改善，同时不显著增加严重失败、单镜质量损失和返工范围时，才进入对应镜头类型的默认规则。

当前只执行 H3 的真实能力，不为未来模型模拟不存在的模式。图像辅助组只要达到质量非劣，并提高一致性、控制力或稳定率，就可以保留。

## 9. Phase 4：端到端候选

代表性镜头已经证明路线可执行、质量方向明确后，就生成完整 45–55 秒短剧，用整片暴露跨镜和时间线问题；不等待所有可选分支逐一测试完毕。

每个普通镜头首轮生成 3 个候选，高风险对白/动作镜头生成 5 个，并按 1.1 节补充到至少两个硬通过 Take；同时记录单次通过率，避免只用 best-of-N 掩盖稳定性。同一方案到 10 次仍不稳定时改路线，QA 不通过时只重做具体镜头或分组。最终输出：

- `final-subtitled.mp4`：1080×1920、H.264 High、YUV420P、BT.709、CRF 18；
- `final-clean.mp4`：同规格、无烧录字幕；
- `subtitles.srt` 与 `subtitles.ass`；
- `timeline.json`：记录项目 fps、分辨率、安全区与所有精确素材版本；
- `project-bible.json`；
- `shot-plans.json`；
- `generation-ledger.json`；
- `qa-report.md`。

H3 原始 768P Take 保留在项目中。交付文件的一次性 1080×1920 缩放只为统一竖屏封装，不宣称增加原生细节。默认输出 30fps CFR；若实测 H3 原生 24/25fps 转换造成明显重复帧或运动损伤，则项目锁定到原生帧率，不默认插帧。音频为 AAC-LC 48kHz/192kbps，目标约 -14 LUFS、True Peak 不高于 -1 dBTP。字幕/关键内容默认安全区为上/左 8%、右 16%、下 20%，允许预览调整。

FFmpeg/ffprobe 自动检查尺寸、画幅、帧率、音轨、响度、字幕越界、字体缺失和最终时长。确定性验收关注同一 TimelineManifest 的剪辑点、字幕、音量、转场与画面结果一致，不要求跨平台编码文件逐字节相同。

### `SUBMIT_UNKNOWN`

如果网络在提交后断开，既没有明确 task ID，也没有明确失败：

1. 标记 `SUBMIT_UNKNOWN`；
2. 用 Provider 的任务列表、回调、账单或 request ID 对账；
3. 对账完成前不自动重新 POST；
4. 确认未创建任务后才允许重试。

## 11. 用量记录，而非预算闸门

记录最新单价和预计调用量是为了运营核算、识别异常计费和比较单位合格产出，不用于压缩必要样本或逐阶段卡住实验：

`预计用量/费用 = Σ(模式 × 分辨率 × 时长 × 候选数 × 最新单价) + 实际重试`

分别记录：

- 图像增强调用量与合格率；
- 视频路线调用量与合格率；
- 单镜候选数与选择率；
- 完整短剧的总用量和单位合格时长。

一旦进入已确认的实验阶段，按获得稳定结论所需的样本量执行，不做逐笔审批或分阶段额度释放。异常重复提交、失控循环和不再提供信息增益的抽卡仍应由普通工程规则阻止。

## 12. 盲评表

由 1 人负责硬门槛检查，至少 3 人进行质量盲评。评审只看匿名候选，不看路线/模式名称，播放顺序随机；第一遍按正常速度完整观看，之后才允许复看，逐帧仅用于独立技术 QA。每项 1–5 分，并单独勾选严重失败：

- 故事可懂；
- 角色一致；
- 场景/道具连续；
- 动作和剪辑流畅；
- 摄影与构图；
- 台词正确；
- 声线连续；
- 口型同步；
- 音频整体；
- 字幕；
- 是否愿意继续看。

记录评审人、候选 ID 和评分即可，不增加不必要的身份隐藏或对抗性机制。路线比较采用硬门槛、维度中位数、严重失败率与偏好共同判断，不让单个总分掩盖台词、身份或口型硬错误。

### 首版端到端通过线

1. 从同一锁定 `ScriptVersion`、ProjectBible 与资产版本独立运行 3 次 `AUTO_DRAFT`；
2. 三次都自动到达可播放时间线并成功导出，不需人工修复任务状态、项目引用或时间线结构；
3. 自动 QA 与定向重试后，至少 2/3 的完整草稿不存在严重失败；
4. 最终批准片时长 45–60 秒，五句台词逐字正确，角色、服装、场景、道具、动作和说话人连续，无明显坏帧、口型错误、缺音轨或字幕错误；
5. 故事、角色、连续性、动作/剪辑、摄影、对白、声线、口型、音频和字幕等核心项的盲评中位数均不低于 4/5，至少 2/3 评审愿意继续看；
6. 可换 Take、局部 Retake/Extend/Gap Fill 和时间线微调，但不能通过人工重建大部分镜头或项目结构来宣称自动闭环通过。
