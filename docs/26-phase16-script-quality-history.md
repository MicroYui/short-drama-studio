# Phase 16：跨剧本审稿历史与修订效果

## 目标与边界

Phase 15 已能持久化推进 Story Architect、Script Critic 和最多两轮修订，但 `PlanningRun` 只保留最新大纲与最新审稿。这会丢失两个关键问题的答案：修订究竟改了什么，以及最新版是否只是更新、而不是更好。

Phase 16 只完善剧本侧评测和 Agent 建议：

- 保留每轮整集大纲和每轮 Script Critic 报告；
- 展示初稿、修订 1、修订 2 的报告轨迹；
- 跨项目检索不同题材、输入方式和自定义时长的剧本评测；
- 当最后一轮比上一轮报告了更多问题或更多 HIGH 问题时，由 Director Agent 给出“比较最近两版”的可忽略提醒；
- 不把问题数量变化当作剧本分数，不自动宣称问题已解决，也不阻断后续规划。

本阶段不调用 GPT Image 或 MiniMax-H3。真实探针在到达 `SCENE_DIRECTOR` 边界后立即停止，不进入视觉资产、视频生成或成片。

## 持久化与 API

SQLite 新增 `planning_run_artifacts`，按 `(run_id, kind, sequence)` 幂等保存：

- `OUTLINE / revision_round=0..2`：完整 `EpisodeOutline` JSON、来源和时间；
- `REVIEW / review_round=1..3`：当前修订轮次、完整 `ScriptReviewReport` 和时间。

工件不塞回每次轮询的 `PlanningRunRecord`，避免长剧本每推进一步都重复返回三份大纲。只在显式读取剧本质量历史时返回。

新增 Product API：

- `GET /api/short-drama/planning-runs/{run_id}/script-quality`：返回该 run 的大纲、审稿历史和跨轮对比；
- `GET /api/short-drama/script-quality`：返回所有已有语义审稿的 run 摘要，供 Agent 和后续跨剧本评测工具检索。

最终 `ScriptVersion` 保留 `planning_run_id`，手动修改台词生成新 ScriptVersion 后仍可追溯原始规划审稿历史。旧项目没有该字段时按 `None` 正常加载。

## 对比语义

`ScriptQualityComparison` 记录：

- 每轮报告的总问题数和 HIGH/MEDIUM/LOW 分布；
- 初稿与末轮的数量变化；
- 最后一轮与上一轮的数量变化；
- 首末轮同名类别、末轮未再报告的类别名和末轮新报告的类别名。

这些是描述性数据，不是答案键或自动验收器。Critic 可能在复审中重命名同一问题，也可能在修复明显矛盾后发现更深的问题。因此：

- 类别名消失只表示“末轮没再以同名类别报告”，不表示已解决；
- 问题数变少不表示剧本通过；
- 最新轮次不默认优于上一轮；
- 提醒始终是 Agent 建议，用户可修改或忽略。

桌面剧本页会显示全部轮次卡片、严重度分布、类别名变化和最新轮次回退风险。最终 Script Critic 的完整建议仍按原有方式展示。

## 通用策略改进

两个不同剧本的基线探针都显示：修订会降低一部分报告问题，但最强开场异常、技术/制度规则、反派即时利益和公开场合中的自证行为仍可能留下 HIGH 问题。因此只调整 Story Architect Prompt，不扩张领域数据模型：

- 结尾机制必须精确解释开场最强异常本身，不能只解释相邻事件；
- HIGH 问题优先修改底层设置、规则、动机或后果，不只增加一句解释；
- 技术、机构权限和程序能力要在剧情依赖前建立，无法简洁建立时应简化机制；
- 观众理解所需的因果必须出现在可拍的动作、道具、屏幕或对白中，不只写进 continuity metadata；
- 单场承载的结论过多或可表演内容不足时，重分配场次时长和信息，不用停顿填满。

## 真实 GPT-5.6-sol 剧本探针

| 样本 | 输入 | 自定义时长 | 场次 | 三轮报告 `总数 / HIGH` | 初稿→末轮 |
|---|---|---:|---:|---|---|
| 《死亡证明寄到离婚前夜》 | `IDEA_EXPANSION` | 220 秒 | 5 | `7/3 → 6/2 → 6/1` | 总数 -1，HIGH -2 |
| 《午夜董事会》 | `AUTO_ORIGINAL` + 创作偏好 | 470 秒 | 8 | `8/2 → 7/1 → 5/2` | 总数 -3，HIGH 0；末轮 HIGH +1 |
| 《死亡证明寄到离婚前夜》策略复跑 | 同一句话输入 | 220 秒 | 5 | `8/4 → 5/1 → 7/1` | 总数 -1，HIGH -3；末轮总数 +2 |

结果说明：

1. 三个 run 都完整保存 `outline_rounds=[0,1,2]` 和 `review_rounds=[1,2,3]`，跨项目目录可检索 3 条评测；
2. 两个题材的初稿→末轮报告问题总数均减少，但《午夜董事会》末轮 HIGH 从 1 回到 2，证明“总数更少”不能代表高风险问题更少；
3. 同输入策略复跑在第一轮后从 `8/4` 降到 `5/1`，但第二轮后总数又回到 7。这一次样本支持“结构修订指令有帮助”的方向，但不支持“第二轮一定更好”或稳定提升的结论；
4. 真实探针都在 `SCENE_DIRECTOR` 前停止，没有创建 Project、image task、video task 或 H3/provider run。

上述三次都是单样本真实运行，不是稳定质量 benchmark。它们足以验证历史、对比、回退风险提醒和纯剧本运行边界，但题材覆盖、不同模型随机性和人类剧本评审仍待扩充。

## 工程验证

- Fake Language Client 覆盖 180/430/900 秒三个自定义时长的跨项目目录；
- 大纲和审稿工件跨 Service 重建保留；
- 手动台词版本继承 `planning_run_id` 和最终审稿；
- `4 → 2 → 3` 的非单调报告轨迹会产生可忽略的“比较最近两版”提醒，同时仍能完成 PlanningRun；
- 未配置 GPT 时正确返回“无语义审稿、无法比较”，不把本地结构回退冒充真实质量报告。

阶段出口为 712 项后端测试、Pyright、TypeScript 和 Vite/Electron 生产构建通过。
