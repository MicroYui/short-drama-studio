# 类型补充：AI 原生短剧重点

以下建议叠加于共享端到端流程。顶层十项是能力目录中展示的制作概要，后文是 Planner 实际使用的详细方法。流程和 Tool 边界可以具体，但创作风格、节奏与镜头语言只描述判断维度，由 Agent 根据用户意图和当前项目决定。Agent 可以跳过、合并、并行或重排，不构成第二套固定 workflow。

1. 锁定受众、观看场景、本集承诺、来源边界、项目 Style 和交付规格。
2. 把题材发展为具有因果推进、人物选择和情绪回报的短剧蓝图。
3. 写出可表演、可朗读、可转成视听行动的场景与对白。
4. 建立角色、场景、道具、服装、声音和视觉风格的连续性资产。
5. 把场景拆成适合竖屏阅读、生成和剪辑的 ShotPlan。
6. 为每镜选择最小充分的参考、关键帧和生成路线。
7. 编译 Provider Prompt，生成可比较候选并保存真实任务状态。
8. 按镜内、镜间、声音和剧情职责检查 Take，并做最小局部修复。
9. 组装对白、音效、音乐、字幕、转场和画面节奏。
10. 从完整单集复核承诺、推进、回报、连续性和交付结果。

## 目标与来源

Planner 首先明确：这是单集、系列首集、连续剧中段、预告还是已有剧集的局部修改；主要面对第一次刷到的冷启动观众、熟悉题材的目标受众还是已看前集的连续观众；观众对人物和世界已经知道什么；本集要让观众期待、担心、相信或获得什么；结尾是完成回报、形成新问题，还是同时做到两者。

保留用户的题材和独特设定。若项目来自锁定剧本，只提出最小必要修订；若来自一句话构想，概念策划可以比较多个实质不同的表达方向，但最终方案必须能够被角色行动和可见后果承载。

可调用：`project.get` 读取完整现状；需要新建时使用 `project.create`；长内容由 `planning.advance` 分单元推进；局部修改先使用 `change.preview`。

## 故事蓝图与单集结构

蓝图至少说明主角当前处境、具体欲望或压力、阻碍来自哪里、观众最先看到的异常/冲突/关系张力、本集的主要选择、该选择造成的结果，以及结尾对当前承诺的兑现方式。

对开场、主要变化和结尾维护简洁的观众知识状态：已经直接看见什么、能够推断什么、仍不确定什么、当前主动问题是什么、观众更接近谁，以及下一次状态变化如何推进或兑现它。允许保留答案，不允许连问题、行动目的和人物立场一起藏掉。

开场不是独立“钩子素材”，而是故事第一段。它应同时提供可理解的情境和继续观看的理由，并与后续因果直接相连。若开场只能靠字幕解释，或之后与它无关，应重写内容关系，而不是再增加更响的音效。

场景是否成立，依据其进入状态和离开状态是否不同。允许慢场景、沉默或单一长镜，但其中必须有观众可感知的等待、发现、压力、关系或决定。让“承诺 → 推进 → 局部回报/新后果”持续可追踪；不要用固定反转频率替代实际戏剧判断。

角色关系、秘密、规则和前情只解释到理解当前行动与后果所需的程度。更完整的世界设定保留在 Bible，而不是全部塞进本集对白。

## 剧本与对白

每场先写“谁想做什么、谁或什么阻止、观众进入时知道什么、场面如何变化、观众离开时多知道或误判了什么、离场时留下什么”，再写对白。对白需要与动作和反应交织，不让角色轮流朗读剧情摘要。

关键节拍分别检查叙事信息、表演动作、画面焦点和声音变化。它们可以同步，也可以有意错开；例如用稳定画面和画外声音改变人物策略，或停掉对白让动作声与反应承担落点。不要让四层从头到尾同时高强度运行。

朗读每句台词，检查说话人是否会这样说、呼吸和重音是否自然、指代在现场是否清楚、潜台词是否被过度解释。对话速度不足时，先考虑动作、打断、反应、信息差和剪辑机会，而不是机械删成短句。

使用 `script.revise_lines` 处理明确的局部台词修改；涉及人物动机、场景结果或后续镜头时，先用 `change.preview` 判断影响范围。内容审校发现的是镜位或生成问题时，应交给相应角色，不要让编剧为技术缺陷重写剧情。

## 资产与人物记忆点

角色资产只稳定当前 Style 与故事真正依赖的身份和造型锚点；这些锚点可以是轮廓、色彩、材质、表演方式、声音或项目自行声明的其他特征。只为实际镜头准备需要的参考，不预设必须具备面部、全身、服装或某种人物细节。

场景与道具资产只记录当前 Style 和实际镜头需要保持的关系，例如空间或图层组织、方向、视觉锚点、归属与剧情状态；具体维度由作品决定，不默认套用真实空间、人物活动区或手持道具语法。

优先使用 `artifact.search_catalog` 和 `artifact.import_catalog` 复用批准资产；缺少当前镜头需要的视角时用 `artifact.inspect_coverage` 判断，再决定导入、生成或编辑。新版本通过 `artifact.review_version` 记录是否可用，并通过 `artifact.add_reference_entry` 进入参考包。

不要提前生成“可能以后会用”的全部视图。资产丰富度由镜头需求驱动，避免不相关候选增加选择噪声。

## 竖屏分镜与导演设计

每个 ShotPlan 明确叙事作用、可见人物、动作/反应、景别、构图、相机、声音、时长、开场状态、结束状态和转场。重要反应和关键道具不能落在竖屏边缘或被字幕/界面遮挡。

不默认使用某一种真人摄影或动画镜头语法。Agent 根据当前 Style、人物关系和画面职责自由选择构图、覆盖、调度与运动；切镜应增加信息、改变关系、重定向注意或改善可读性，并让关键动作或反应获得足够阅读时间。

切点优先跟随目标改变、动作完成、发现、选择、关系变化等事件边界。跨镜改变机位、空间或时间时，使用动作、视线、银幕方向、空间标志或声音延续维持可理解的事件连续性；有意跳切或断裂必须承担明确的叙事或情绪职责。

不得为提高密度而机械增加镜头；镜头数量和时长由当前动作、反应、空间关系与剪辑职责决定。节奏评估分为叙事信息、表演动作、画面剪辑和声音四层，不用平均镜头时长代表整集节奏。

复杂动作要拆成有序动作节拍，明确接触点、持物手、人物朝向和终态。相邻镜头先对齐动作与屏幕方向，再决定使用尾帧续接、当前镜首帧、首尾帧或不同覆盖。

使用 `shot.update_reference_plan` 保存引用与动作关系，`shot.preview_reference_plan` 查看解析结果，`shot.compile_keyframe_brief` 生成镜头专用关键帧说明；高风险镜头可先调用 `shot.director_advice`。

## 参考与生成路线

路线由镜头风险决定：探索性镜头可从纯文本开始；身份和构图起点最重要时使用首帧；结尾姿态、道具状态或构图必须到达时考虑首尾帧；人物/场景/声音/运动复用更重要时考虑全参考；已有版本匹配且检查通过时直接复用 Take。

参考包中的每份媒体只承担明确职责。若多份参考在项目声明的身份、造型、空间、光线、视角或状态上互相冲突，应先减少、重排或合成镜头关键帧，不把冲突留给视频模型猜。

可用 `qa.rerank_reference_visuals`、`qa.compare_keyframes`、`qa.check_input_compatibility` 做生成前检查。H3 路线使用 `route.h3_capability_profile` 和 `route.plan_h3`；当前模型的时长、分辨率、媒体数量与组合限制只信 Tool Schema 和 Provider Capability，不复制进本 Playbook。

## Prompt 编译与候选生成

Provider Prompt Compiler 把已批准 ShotPlan 转成模型语法，不负责重写内容。它要忠实表达起始状态、动作发展、摄影机、声音、结束状态和媒体引用，并保留锁定对白和说话人。

H3 可使用 `route.compile_h3_prompt` 或 `route.preview_h3_probe` 预览请求，再使用 `route.execute_h3_plan` 提交；通用路径可使用 `video.enqueue`。外部状态由 `task.advance`、`task.drain`、`task.reconcile` 和 `task.recover_output` 等 Tool 推进。

首个候选生成后先检查，再决定停止、增加同路线候选、修改输入还是换路线。每次迭代尽量改变一个有意义的控制变量，并记录为什么改变；不要用相同错误输入做固定次数抽卡。

## Take 检查与局部修复

先检查文件、时长、比例和音轨，再看身份/造型、场景/道具、动作、构图、相机、表情、对白、声音来源与相邻镜头边界。一个候选更好不等于可用，比较时允许全部拒绝。

使用 `video.inspect_take` 保存观察，`video.compare_takes` 做同镜相对比较，`video.select_take` 选择版本。H3 结果可用 `route.review_h3_take` 记录路线证据。

修复时按责任层选择：故事或动机问题回到编剧；覆盖和动作问题回到导演/ShotPlan；身份、场景或关键帧问题回到资产；随机运动问题可 retake；片段不足使用 `video.extend`；局部缝隙使用 `video.gap_fill`；后期能解决的字幕、音量或剪辑问题留在时间线。

`shot.apply_director_repair` 保存明确修复决定，`shot.run_director_loop` 可执行一次导演建议与应用。不要因为整集某一处问题而重新生成所有镜头。

## 声音、字幕与剪辑

声音从剧本和镜头设计开始，而不是最后随便配一条音乐。明确画内对白、画外音、设备播放、环境声、动作声和非叙事音乐的来源与叙事作用。

原生音视频适合时可以使用，但必须检查实际说话人、台词、口型和环境音。多人对话、快速对白或复杂运动存在问题时，可以保留独立配音、字幕、音效与剪辑修复路径；未注册的 Tool 不得写成已实现能力。

字幕使用口语化显示文本，断句配合语义与呼吸，避免遮挡眼神、嘴部、手部和关键道具。音乐和音效负责建立期待、强调变化或连接剪辑，不持续覆盖表演和对白。重要变化前后允许减少声音密度或保留短暂静默，让落点产生对比。

使用 `timeline.rebuild` 组装当前选定 Takes，使用 `audio.inspect_manifest` 检查音频和字幕时间关系。相邻镜头要同时看画面终态、声音延续和剪辑点。

## 单集验收与系列连续性

整集审看回答：第一次刷到的观众能否看懂当前行动和主动问题；开场承诺是否清楚；场景是否持续改变状态；主角选择是否可理解；反转是否有依据；情绪或因果回报是否兑现；四层节奏是否有强弱变化；竖屏画面和字幕是否可读；角色、场景、道具、动作和声音是否连续；段尾是否自然形成下一步动力。

没有发布数据时，分别以冷启动观众、目标受众和连续观看观众做“观看风险预判”，标出最可能困惑或离开的具体位置，但不得写成真实留存结论。用户提供真实数据后，把快速滑走、延迟跳出、中段退出、相对时长的观看比例、重播、评论语义、收藏、分享、主动搜剧和下一集进入与具体时间段对齐；按相近受众、流量来源和曝光阶段比较，多个信号共同支持时再提出原因假设，不用单一绝对阈值判定剧本失败。

用 `qa.review_episode` 保存整集报告。问题必须附具体镜头、时间或工件依据，并指向故事、分镜、资产、生成、音频或剪辑责任层。修复后只复核受影响镜头及其相邻边界，再用 `timeline.rebuild` 和 `timeline.export` 产生当前交付版本。

系列项目还要把本集结束的人物关系、秘密暴露、道具归属、伤势/服装/地点和未完成行动写回可供下一集读取的项目状态。若已有发布反馈，先聚合同类评论和行为信号，区分人物判断、行为合理性、剧情理解、情绪回报、可传播表达与拒绝/疲劳，再对下一集做最小、可验证的调整；不要只保留一句“下集更精彩”，也不要直接追逐个别高赞评论。
